# Security

The legacy v3 code has known critical issues: unauthenticated shell command injection, no authentication on the control panel, and state-changing actions over GET. Until the security hotfix ships, run it only on a private, isolated network, never on the internet or a shared Wi-Fi.

Please report security problems by opening a private security advisory on this repository.

## The threat model of the current code (D79, 2026-10-10)

The box is a staff room controller and a VJ tool on a private network. It is not built to face the internet.

- **Someone on the same network who listens.** Over plain `http://` the PIN at pairing, the session cookies and everything the panel shows travel in the clear. With the owner's own root installed on his devices and the switch "Owner access only over the secure connection" on (System > Secure connection, `docs/HTTPS.md`), the PIN and the owner's cookie never cross the network in the clear; guests' codes and cookies still do, over `http://`, and give what they gave before (view, or live for a presenter).
- **Someone who answers for the box's name.** Over `https://` a device with the root refuses an impostor, which has no certificate from that root. Over `http://` a fake pairing page can still collect a PIN typed into it; with the switch on the real box refuses that PIN over `http://`, so it is useful to the attacker only over `https://`, where the throttle on guesses applies as before. The PIN is four digits and rotates at every start.
- **Someone who steals a box or its SD card** gets the box's key and certificate and can stand in for that one box, by its name, to devices with the root, until the certificate runs out (there is no revocation; `docs/HTTPS.md` says what to do). The root's key is never on a box, so no other box or name can be signed with what the card holds.
- **Someone who steals the root's key file** needs its passphrase; with it they can sign for `.local` names and private addresses (the root's name constraints, where the device enforces them), not for sites on the internet. The cure is a new root, every box signed again, and the old root removed from every device.
- **A guest with a code** gets view or live access over `http://`, cannot reach the certificate routes, and cannot read the root from the box.
- **Someone who finds the owner's recovery sheet** (D81) has owner access until the set is cancelled; each code is 12 symbols of 31 (about 59 bits), stored as a salted scrypt hash, redeemed through the same route, lock and throttle as the PIN, burnt on use, and every use is shown to the owners with the device's name. A box without codes answers a guess exactly as a box with them. With the owner-only switch on, a code is taken over `https://` only.
- **Someone at the box with a USB stick** can make it show a fresh owner PIN on the room's projector for two minutes (the file `pvj-recover` at the top of the stick; only the name is looked at, nothing on a stick is read or run). It is on by default and the owner can switch it off; it proves presence at the box, which already allows pulling the card. The PIN dies at its first use, at two minutes or when the stick comes out; the box writes down the showing and the use (never the digits), tags the device that used it, says who took it on the display for ten seconds, and shows the owners. A stick left in at a restart shows nothing within an hour of the last showing.
- **Not covered:** a device of the owner's that is itself compromised; anybody who can run commands on the box; a four-digit PIN guessed over `https://` (the same throttle); the clear `http://` side, which stays for guests by design (no HSTS, no redirect).

Nothing of the secure connection has run on a box or met a real phone as of 2026-10-10; nor has owner recovery (D81) met a box or a real USB stick.

## The NDI helper (D62; a draft in #94, 2026-10-11)

NDI is an optional input the owner sets up himself (`pvj-ndi-runtime install`, with NDI's own proprietary runtime, which is never in this repository or the image). The helper `pvj-ndi` runs the closed library on packets from the network, so it is treated as the part that can be taken over.

- **What a taken-over helper holds.** A client's place on the LAN: towards the panel as an unpaired stranger (`/api/hello`, `/api/pair` behind its throttle, the https probe), towards OSC when that module is on and its locks (D78) are open, towards sync when it is on, and towards every sender and every other box on the network (the box's own LAN address lies inside the private ranges the unit allows; 127.0.0.1 does not). The contents of the pipe the player reads: raw video of a size the panel set, or, when the owner has switched sound on, raw video and float PCM through mpv's Matroska reader narrowed to those two (`Player.MKV_ONLY`); the sound is off by default until it has been heard on a box. The system D-Bus as any unprivileged account (it needs avahi). 512 MB, 96 tasks, three cores, an 8 MB `/tmp`. (The tasks were 64 until 2026-10-12: measured by hand on a Pi 4, one connection used 35 and two, a picture and the box's one sound source, 46 to 47, with about five threads of the helper's own besides. A box that is set up for NDI gets the new unit at its next install or update.)
- **What it does not hold.** The player's control socket (mpv's channel can run programs), the settings, the PIN, the media, the root helpers, the internet, any device, any name in the pipe's folder: the pipe is made once by root (`/etc/tmpfiles.d/pvj-ndi.conf`, 0660 root:pvj-ndi in a 0750 root:pvj-ndi folder); the helper writes it by its group and cannot unlink, rename or replace it, and the panel loads it only as a pipe of root's in a folder of root's that nobody else may write.
- **Not done, and why.** Denying the box's own address to the helper is not static in a unit; the choice was to write this down, to recommend the OSC locks on a box with NDI, and to try on the Pi an `IPAddressDeny=` of the box's own addresses written at each install and update (`tools/DEVICE-TESTING.md`, N21). `SystemCallFilter` and `MemoryDenyWriteExecute` are not set blind on an unknown library (N20).
- **A pad follows a name at an IP address (2026-10-11).** A pad can hold an NDI source. It stores an id made from the sender's announced name and the IP address the library reports for it (not the port); nothing is typed into a pad, and a source becomes allowed only when an Operator picks it from the helper's live list (only the Owner removes one). Names are announced without authentication and an address on a LAN can be taken, so whoever holds that address and announces that name is what the pad plays; that is inside this boundary and cannot be closed by the box. What the box does: it refuses a same-named sender on another machine, refuses when two senders share an id, compares the name and the machine as well as the 48-bit id, keeps allowed sources in the helper's list of 64 so that a crowd of announced names cannot push them out, tells a Guest nothing of why a pad was refused (the reason can name an address), and never lets a Guest, or a scene started by a Guest, reach an NDI pad. What it tells the owner: on a network he does not control, give the sender's address and keep it fixed.
- **Groups and discovery servers are not a lock in the security sense (2026-10-11).** They decide which senders the box looks for. A sender that joins the same group or registers with the same discovery server is found, and the box goes on hearing mDNS announcements on its own segment (NDI documents no setting that stops a finder doing so). The discovery servers reach the library through a file the panel writes in a folder root made for it (`/run/pvj-ndi-config`, 0750 pvj-web:pvj-ndi); the helper reads it and cannot write it, and the file holds that one key.
- **The discovery server on the box (D85, 2026-10-11).** Optional, off by default, and set up only by root's own command from the owner's copy of NDI's program (never bundled, never downloaded; the copy is checked as an ELF program of this processor, root's, and its sha256 is printed). It is closed code that LISTENS on the network, so it is treated as the helper is: as the part that can be taken over. What it holds if it is: an account of its own (`pvj-ndisc`) with no capabilities; a client's place on the LAN as an unpaired stranger, like the helper's; its one port; 128 MB and one core. What it does not hold: the box's settings, keys, PIN, media, control sockets, the NDI helper's folders and pipe, the internet, 127.0.0.1, any device; it can write only its own runtime folder. NDI's program would also read a configuration of its own, `ndi-discovery-service.v1.json`, from `/etc/ndi`, `/usr/local/etc/ndi` (both hidden from it by the unit) and from the folder it lies in (root's; the supervisor does not start the program while anything but the program is in that folder). The panel talks to this project's supervisor over a Unix socket that answers only the panel's account; the supervisor starts NDI's program with two arguments it checks itself, so neither a settings file nor the panel can make it run anything else, and what the supervisor answers is checked again by the panel. Only the Owner switches or sets it, and never through remote support, of any role: a listener on the network is opened by someone in the room. **A discovery server is not authentication**: whatever can reach its port can register a sender with it and list what is registered. It is asked to bind to one chosen network's address by default (the wired one), never to every network unless the Owner chooses that, and never to the support tunnel's or another tunnel's address; whether NDI's program obeys that argument in its service mode has not been seen, so the supervisor stops a program that says it listens elsewhere and device step N27 checks it with `ss`. It is for a network the owner controls. Nothing of it has run with NDI's real program.
- **The licence.** The NDI SDK licence excludes fixed-purpose appliances and embedded Linux devices from its free terms; the owner accepted it for his own test Pi only. Accepting a third party's licence is the owner's act, never the box's.

The picture ran on the test Pi 4 on 2026-10-08 and again on 2026-10-12; the sound was measured there on 2026-10-12 (the samples leaving the sound device, the player's clocks) and has not been listened to. **The box's one sound source (D87) is held to the pad's rule above, on both sides:** the helper is told the name and the address of the one source the Owner allowed and opens, or keeps, a connection only to a single sender of that name at that machine (two under the id: neither; another name behind the id: never), looking again at every status; and the panel shows that name as playing only when the live row has it. Its limits are the pad's: whoever holds that address and announces that name is what is heard.

## OSC (the new player)

OSC is UDP, off until switched on, and only private networks may send. The box receives; it sends nothing unless the Owner switched "Send state back" on (below). It is not encrypted and cannot be: anyone who can listen on the network reads every message, and a device on the same network can forge another device's address. Three optional locks on System > OSC (a list of devices, a paired device, a key in the address; D78) reduce who may send and show who sent. OSC has no login and the panel's roles do not apply to it, so on a box where OSC was never on the paired-device lock comes on with the first switch-on (D83); a box that updates keeps its locks as they are, and while OSC is on with all three off the panel says "OSC is open: anyone on this network can control the box" on the OSC page, its row in Setup and the health page. They stop devices that are merely on the network, not someone who captures traffic or forges packets: the key is readable in a single packet and a captured packet can be replayed. Shutdown, reset, updates and passwords are not reachable over OSC at all. The details and the limits of each lock are in [pvj/OSC.md](pvj/OSC.md).

**Remote support: what a helper may do (D84).** A support session of the Owner's role may do anything that ends when the session ends, and nothing that outlives it or locks the owner out. Refused to every session whatever its role (`support.REMOTE_DENY`, each with its reason): pairing and panel sessions, invitations, everything under `/api/access` (codes, links, the controller code choice), the PIN (show, rotate, unlock) and the QR code, everything under `/api/recovery` and `/api/https`, the session's own settings, start and extend, power-off, factory reset, and (new with D84) the confirm of a network change, which only someone at the studio can give; an export with passwords stays refused too. Opened by D84 to the Owner's role only: a settings import (the recovery stick switch is dropped from the file; devices, the PIN, codes, support settings and the secure connection are no part of any settings file), adding and removing a theme (checked data, never code), the OSC key and the state targets (a target is still only a device on the box's own network, never the tunnel), the guest lock, and removing a Guest's or an Operator's device (never an Owner's). Every POST a session is answered is written into the session's entry of the support log, without values (the opened routes in words, the rest by route); what matters (the opened routes' changes, an update with its sha256, a settings file with its sha256 and what it changed, a device removed, and every refused request) is in a list of its own that routine lines cannot cap or displace, and repeats are counted. A session's imports keep their own copies of the settings and never push out the owner's; the settings from before a session's first import are kept. **What this is not:** a boundary against a dishonest helper with the Owner's role. That session can upload and start a software update, which must be signed by a key this box trusts (`pvj-update` checks `/etc/pvj/allowed_signers`; no route changes the signers), so any release of ours, an older one too, but not a program of his own; and it can point the box at other machines (Boxes in step, projectors, streams, schedule and power-up), which stays after the session. The refusals guard against a way in left behind by accident and against locking the owner out, and they make the session auditable. Also refused to a support session, by the route and by a file: adding or widening a network OSC accepts from beyond a private range the box is directly connected to (removing and narrowing are allowed), and adding or changing a MIDI control that shows an access code (removing one is allowed). **Known and left as it is:** a helper who saw or made the OSC key knows it until the owner makes a new one, which the panel says. Sessions below the Owner's role are unchanged (D80). Not tried through a real tunnel.

**State sent back (D82), off by default.** A box that answers over UDP can be made to send packets at someone else, so this one never answers "whoever sent": with the Owner's switch on it sends its state (what plays, the levels, fade and blackout) only to at most 4 devices the Owner added at the studio, each a private IPv4 address on a subnet the box is directly connected to and a port from 1024 up, checked again at every send, with a time to live of 1. No packet adds a target or decides where anything goes; a refused or malformed packet is answered with nothing. At most 20 datagrams and 12,000 bytes a second leave for one device and 60 and 36,000 for all, whatever comes in. What is left: a device on the network that forges a listed tablet's address can make the box send that tablet its full state once in 2 seconds; anyone who can listen reads clip and shader names and the names of a shader's and an effect's controls (never a PIN, a code, the key, a device's name or address); and a device that takes over a listed address is sent the state. Only the Owner switches it or changes the list: at the studio, or through a remote support session of the Owner's role (D84, logged). Not tried with a real tablet or on a box.

## Owner, Operator, Guest (the new player, D80)

Three levels: Owner (`full`), Operator (`live`), Guest (`view`). The whole policy is D80 in `project-log/DECISIONS.md`, with one row for every route; the code is `pvj/policy.py` and the one gate every request passes, `Api.gate`. What to know when judging the risk:

- **Guest controls are open by default**, by the owner's choice. A guest link or a guest code is therefore no longer "watch only": while the lock is open its holder can change what the room shows and switch projectors on and, with a second request, off. One box-wide lock (an Operator or the Owner) makes every guest read-only on the next request. Guests are limited (10 requests in 10 seconds per device, 30 for the box, refused ones too; play, blackout and a scene once in 2 seconds for all guests together; one switch-off per device and two for the box in five minutes), every guest action is logged with the device's name, and no guest request saves settings. A guest may apply every room scene but one that plays a stream, so **what a scene does is what a guest can do**, unless the scene is marked "Not for guests": a scene an Operator made that mutes a wall can be applied by a guest who could not mute directly.
- **An Operator is trusted with the room, not with the box.** He can delete every clip, change the schedule and what plays at power-up, and remove guests. He can remove other Operators (not himself, not an Owner) and edit the MIDI layout, but the server refuses him every change to a control that shows an access code (set, change, remove, by any route), and what a mapped control does runs with a presenter's old reach. He cannot reach the network, updates, the PIN, the pairing of Operators and Owners, remote support, OSC and DMX settings, the MIDI feature's switch, the settings file, streams (the box would connect outside), projector addresses and passwords, or the module switches. An Operator link or code is made by the Owner only.
- **Callers with no login do not rise with the Operator.** MIDI, OSC, DMX, room scenes and the schedule, a remote support session below `full`, are held to a list written out by hand of what a presenter could reach before (`policy.LEGACY_LIVE`); a test refuses each of them every other route. A device paired as a presenter from a controller before D80 is a Guest. A code drawn from a MIDI controller pairs a Guest; the Owner alone can set it to pair an Operator, and then **anyone who can reach the controller can become an Operator**: that is the Owner's decision about the room, and the box never makes it by itself.
- Through the remote support tunnel the lock is changed only by a session of the Owner's role (D84), and it is in that session's log. **Not covered:** the lock is not a secret and not a per-guest setting; a guest request already past the gate when the lock is set still runs (one request); the confirm for a switch-off is bound to the device and the request, not to what a scene holds at that moment (an Operator editing the scene between a guest's two taps changes what the second tap does). **Nothing of this has run on a real box.**
