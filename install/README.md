# Installer

```
sudo install/install.sh            # install or update (safe to run again)
install/install.sh --dry-run       # show what it would do
sudo install/install.sh --uninstall [--purge]
```

What it does, on Debian, Ubuntu and Raspberry Pi OS (Bookworm, Trixie) for Pi 3, 4, 5 and x86:

1. Installs `mpv` and `python3` with apt (skipped with `--offline`; it then fails if something is missing).
2. Creates group `nxlx-svc` and the player account (its home is `/var/lib/nxlx-player`; older installs are moved there without moving any files) (default: the user who ran `sudo`, else a system user `nxlx-player`), adds it to `video`, `render`, `audio`, `input`, and adds the web user to `nxlx-svc`.
3. Copies the program to `/opt/nxlx/releases/<version>` and switches `/opt/nxlx/current` to it atomically. The previous release stays in place and its path is written to `/opt/nxlx/previous`, which is the basis for rollback.
4. Writes `/etc/nxlx/nxlx.env` (media and USB folders) only if it does not exist, so your edits survive updates, and `/etc/nxlx/install.json`.
5. Installs, enables and starts `nxlx-player.service`, and links `nxlx-player` and `nxlx-selftest` into `/usr/local/bin`.

Program files are owned by root and not writable by the web user. `/var/lib/nxlx` (settings) belongs to the web user, mode 2750: the player can read its media there but cannot create or replace files, so a player compromised by a hostile file cannot change the settings. Because the web user owns that folder, the installer never follows a link in it: a link at `/var/lib/nxlx/video` is removed (the clips at its target are untouched). Root's own files (the settings copies an update keeps, and the clip stick's claim) are not kept there at all: they live in `/var/lib/nxlx-update`, root:root mode 0700, which the installer makes; files an older version left in `/var/lib/nxlx/backups` and `/var/lib/nxlx/clip-stick.json` are moved there once, on the next install or update, without following any link. To keep the video library elsewhere, point `--media <folder>` at it instead of using a link; `--media /var/lib/nxlx` itself is refused. `--uninstall` keeps `/etc/nxlx`, media, users and the group unless you add `--purge` (which removes only `/etc/nxlx`).

`--stage DIR` installs into a folder without touching users, apt or systemd; the tests and the future image build use it.

**A node with the old names** (`/opt/pvj`, `/etc/pvj`, `/var/lib/pvj`, the `pvj-*` accounts and units, group `pvj`; every node installed before rename PR 7) is converted first. The installer puts the new release into `/opt/pvj/releases/<version>` and runs `bin/nxlx-convert --run --release <version>` (D136): it backs up, arms a 15 minute undo, stops the services, renames the accounts (user and group ids stay, so no file changes owner), the folders, the units and their links, the sudoers file (checked with `visudo -cf` first), the udev rule, the tmpfiles, journald and modules-load files and the command links, points `/opt/nxlx/current` at the new release and starts the services under their new names; then the installer carries on as on any node. It refuses and changes nothing while a show plays, an update runs, the root file system is read-only, or an account to be renamed is logged in, so run it from another admin login than the deploy account (node-01: `nxlx`, node-02: `pi`). Keep the result with `sudo nxlx-convert --confirm` within 15 minutes, or it is undone by itself, back to the old names and the release the node ran before. If the conversion stops half-way, run the installer again: it reads the converter's journal (`nxlx-convert --state`) and carries the conversion on, and it never moves `current` or writes `previous` itself while a conversion waits for its confirm (it refuses to install another version then). If a line in the middle of the journal (`/var/backups/nxlx-convert/journal.jsonl`) cannot be read, every converter command refuses, the timed undo too, and says which line it is (the installer says to run `sudo nxlx-convert --state`, which prints the same message). Copy the journal aside (`cp journal.jsonl journal.jsonl.aside`), remove that line from the journal, then run `sudo nxlx-convert --undo` (or `--state` to see where it stands). A cut-off last line is not this case: it is passed over. To go back later: `sudo nxlx-convert --undo` (the updater refuses a rollback to a release with the old names). The panel's Update button cannot do the first conversion: the updater of a release with the old names refuses this release's bundle. A node that has the new folders and accounts but still holds the old variable or signing names (a release between rename steps 7 and 8) is refused by the installer before anything changes: it asks the converter (`--stale-names`, which counts only variable and signing names in nxlx.env, allowed_signers and the nxlx-* units and drop-ins, never a comment) and names the first file. The converter also rewrites the variable names (`PVJ_*` to `NXLX_*`) in `/etc/nxlx/nxlx.env` and the units, and the signing principal and namespace (`pvj-release` to `nxlx-release`) in `/etc/nxlx/allowed_signers` (the keys stay as they are); `--undo` puts them back.

**NDI is not installed by this script.** The NDI input is opt-in per box (D62): the installer adds no NDI service, account, group or avahi package, and the image does not either. One root command at the box sets it up, `sudo nxlx-ndi-runtime install "<the NDI SDK folder>"` (see [../mctl/NDI.md](../mctl/NDI.md)), and `sudo nxlx-ndi-runtime remove` takes it off. On a box that was set up, this script writes the helper's unit again at every install or update and keeps it enabled; `--uninstall` removes it and leaves `/opt/nxlx-ndi` (the owner's copy of NDI's library) unless `--purge`.

Verified: `tests/test_install.py` (stage mode) and one real-mode run in a throwaway container (user and group creation, links, uninstall). Not verified: apt installation on a real Pi, `systemctl` enable and start, and boot-time behaviour.

Not included yet: the web panel, OSC and the read-only root option; updates from a signed USB stick or the network; automated rollback command.
