# Decisions

Newest at the bottom. Format: **what**, **why**, **cost / rules out**. Never rewrite an entry; add a new one that supersedes it.

## D1. Python 3 (standard library only) replaces PHP for the new core
Why: the legacy PHP had serious security problems and targets an old OS; a small stdlib-only service installs anywhere and has nothing to keep patched. Cost: a rewrite; legacy PHP and docs stay in the tree until feature parity.

## D2. Fork without upstream permission; upstream credited, licence files untouched
Why: the upstream author is unreachable and the project is unmaintained. `LICENSE.md` and `AUTHORS.md` are never edited; the README and NOTICE credit the original. Cost: none technical; keep the credit visible.

## D3. New code is Apache-2.0; legacy code stays under the upstream licence
Why: a permissive licence with a patent grant suits an art and tools practice. Every new file has an SPDX header; `REUSE.toml` covers the rest. Copyright holder: "NXLX.Systems and contributors" (NXLX.Systems is the whole practice; NXLX is the VJ name). Rules out: relicensing legacy files.

## D4. Security hotfix first, before any new feature
Why: the legacy panel was exposed to command injection and similar. Phase 1 closed the worst holes before the rewrite. Cost: delayed features.

## D5. One long-lived mpv, controlled over JSON IPC, supervised by systemd
Why: gapless switching by `loadfile`, recovery by systemd, one process to reason about. Cost: no second player, so **no true crossfade**; only "Dip to black" and "Cut". Revisit if a crossfade is wanted (needs a second player).

## D6. The web panel is unprivileged; root work goes through a small helper
Why: a bug in the panel must not become root. The network helper (`pvj-netd`) listens on a socket in `/run/pvj` (group `pvj`), checks the caller, re-validates every request and runs only fixed commands. Cost: an extra service. Consequence: the panel cannot restart a wedged mpv.

## D7. Auth model: PIN pairing, per-device tokens, roles view / live / full
Why: simple at a gig, no passwords to type on a phone. Tokens are stored hashed; POST only with a custom header and Origin check (CSRF); strict CSP. Guest links are view-only by default.

## D8. Signed, rollback-able updates
Why: a bad update at a venue must be recoverable. Ed25519 signatures via `ssh-keygen -Y`, releases in versioned folders with a `current` link, health check and automatic rollback. Not built: fetching from the network or channels, and an update button in the panel.

## D9. NDI, SRT/RTSP/RTMP, AES67/Dante and ST 2110 are separate optional modules
Why: each has its own licence, dependencies and risk. Modules are declared by manifests in `pvj/modules.d`; unbuilt ones are listed as "Not built yet". Beta modules default to off.

## D10. Network changes are never final until confirmed
Why: changing the network of the box you control over that network can lock you out. Apply builds a separate candidate profile; Confirm swaps it in; timeout, failure, helper restart or reboot reverts. Undo retries until it works. Wired only for now (no Wi-Fi, hotspot or VLAN). **Never run against a real NetworkManager**, so it is beta and off by default.

## D11. Target platform: Raspberry Pi OS Trixie Lite, 64-bit, for the image
Why: current, supported, small. The installer also targets Bookworm and Debian/Ubuntu. The image has never been built.

## D12. Project name: nxlx.mastercontrol
Why: the old name came from the last upstream version. The `pvj` package, `pvj-*` services and commands and install paths keep their names (renaming them touches every import and existing install for no gain). The GitHub repository was renamed from `PocketVJ-CP-v3`.

## D13. Device tests run through a manual-only self-hosted runner, or by hand
Why: a cloud session cannot reach devices on a LAN. The workflow starts only by manual dispatch by the repository owner, never for pushes, pull requests or forks, so nobody else's code reaches the board. Network tests are excluded because they could cut the runner off. See `tools/DEVICE-TESTING.md`.

## D14. Working process: one PR per finished branch, short comment, merge when green
Why: keeps history readable and CI as the gate. No history rewriting. Risky features (root, network, uploads, auth) get an independent read-only review, with every finding fixed by a test that reproduces it.

## D15. The scheduler never replays missed events, and can only do four harmless things
Why: a Pi has no battery clock, so its time jumps when the network sets it; replaying "missed" entries after a jump could start clips at the wrong moment on a live stage. The scheduler fires only for minutes it watched (short stalls of up to two minutes are caught up) and can only play, stop, blackout or show. Cost: a box that was off at 18:00 does not start the 18:00 entry when it boots at 18:05; use an autostart preset for that. Beta and off by default, like the network module.

## D16. Streams accept only srt, rtsp, rtsps, rtmp and rtmps addresses, and play by saved id
Why: mpv opens many URL kinds (`file://`, `edl://`, `lavf://`, `ytdl://`), some of which read local files or run helpers, so an open URL box would be a way around the media folder rules. Logins in addresses are hidden everywhere and never round-tripped to the panel. Cost: no http/HLS/UDP streams for now, and no free-form "play this address" over OSC or the API.

## D17. DMX and MIDI input are stdlib-only, fixed maps, baseline first, and split into two modules
Why: D1 says the standard library only, so Art-Net and sACN are parsed by hand from UDP and MIDI is read from the raw ALSA device files (`/dev/snd/midiC*D*`), with no libraries to install or patch. Maps are fixed and documented (`pvj/DMX.md`, `pvj/MIDI.md`) so a show file never depends on hidden state. The first DMX frame only sets a baseline, so a console at zero cannot black out the screen; the box holds its last state when the signal stops. The device path is checked against a strict pattern, never an arbitrary file. The umbrella `control` manifest is replaced by `control-dmx` and `control-midi` (OSC has its own switch in settings). Cost: no MIDI learn or custom DMX layouts, no Art-Net discovery replies, no sACN priority merging, no MIDI output or feedback to controller lights.

## D18. Autostart runs at first sight of a player and after a player restart, never because playback stopped
Why: the goal is a box that recovers by itself after a power cut or an mpv crash, without fighting the operator. Watching the player's process id distinguishes "the player was restarted" (start again) from "someone pressed Stop" (leave it). It plays through the same API calls as the panel and OSC, so validation and the mix apply. Off by default. Cost: a box whose clip simply ends will not restart it (use loop, or the schedule); autostart from a USB drive appearing later is not covered.

## D19. The screen viewer is a shared screenshot, not a video stream
Why: the box draws with mpv straight to the display (DRM/KMS) with no desktop, so there is nothing to mirror. mpv can save its own output on request (`screenshot-to-file ... window`), which includes brightness, size and blackout. Measured on a Pi 4 at 2560x1440: about 0.7 s and 190 KB a frame. So the panel asks for one frame at a time (at most every 0.7 s, shared by every viewer) and only while someone has "Show screen" on. Any paired device may look, including view-only guests. Cost: about 1 frame a second, not live video; real-time video needs an HDMI capture device or a second encoder, which is a different design.

## D20. The screen viewer is a snapshot on request, not a live view (supersedes D19)
Why: D19 built a viewer that refreshed about once a second. Measured on a real Pi 4 playing 1080p H.264 to a 2560x1440 monitor: playback dropped 0.0 frames a second with no viewer, 4.7 a second with the continuous viewer, and still 1.3 a second with one snapshot every 5 seconds. The owner saw it as choppy playback and said to drop live view if it cannot run without impact. Each snapshot is a GPU readback of the whole window (about 0.7 s of work, about a quarter second of visible stall). So there is one snapshot per tap, nothing repeats by itself, the server allows at most one every 3 seconds, and a live picture is left to an HDMI capture device. Cost: no live preview on the panel.

## D21. MIDI reads every controller, and controls are assigned by learn; profiles come later
Why: the owner plugged in three real controllers (Korg nanoKONTROL2, Akai MIDI Mix, Novation Launchpad Mini). A recording of the Launchpad showed it sends notes 20 to 103 and CC 104 to 111, so a fixed map (notes 36 to 71 are pads) matches nothing useful, and the single chosen device could not serve three controllers. The hub now opens every `/dev/snd/midiC*D*` character device, rescans every 2 seconds, names a controller by its ALSA card id (stable across boots), and keeps a user map (a control is learned by moving it) checked before the built-in map. Mappings are validated and capped, and the same 50 commands a second cap applies. Cost: more code than a fixed map; no feedback to lights yet. Shipped per-controller profiles (like Ableton's control surface scripts) are a later step on top of this map: a profile would be a file of entries for a named controller.

## D22. The player plays media only: it does not follow references, load sidecars, scripts or youtube-dl
Why: mpv judges a file by its content, so a hostile USB drive or upload can name a playlist or EDL `x.mp4` and make the player open other files or URLs. The independent review flagged it; a test on the real Pi showed `--load-unsafe-playlists=no` alone did NOT stop a fake playlist (it played the file the playlist named) and `--access-references=no` did. The player now starts with `--access-references=no --load-unsafe-playlists=no --sub-auto=no --audio-file-auto=no --ytdl=no --load-scripts=no --load-auto-profiles=no`. Cost: no user-made playlists or HLS; sidecar subtitles are not picked up. Not covered: a file that the media demuxer itself (ffmpeg) treats as a network manifest; the streams module needs network protocols, so they are not blanket-whitelisted away.

## D23. People join with short-lived role codes shown on the display with a QR code; the full PIN is not the way in for guests
Why: the owner wants studio users to scan a QR code and get into the panel, and to toggle the PIN and guest or presenter access on the display. Putting the full-access PIN on a projector would give everyone in the room the whole box. So a full-access device makes 6 digit join codes for view (guest) or live (presenter): at most one per role, at most 4 in all, 1 to 120 minutes, 1 to 50 uses, memory only, the same brute-force throttle as the PIN, constant-time comparison. They are drawn by mpv as text plus QR bitmaps (overlay-add) in the top right, even over a clip, for a chosen time. The QR encoder is our own (`pvj/qr.py`, standard library only, byte mode, level M, versions 1 to 10), checked against the published Reed-Solomon and format values and by decoding its output with zbar, including off a snapshot of the real display. Cost: someone who photographs the screen can join with that role until the code expires or runs out; the full PIN can still be shown, after a warning.

## D24. Pictures are converted by mpv, not by our own code or a new dependency
Why: the overlay needs raw premultiplied pixels at the screen size. The image has no ffmpeg or ImageMagick, and decoding and scaling a full-screen PNG in pure Python takes many seconds on a Pi. mpv is already there and can write a single frame as raw video through a lavfi graph (scale, pad, premultiply) in about a second. It runs as the web user with `--no-config`, on a plain file name from the media folder, with a timeout and an exact-size check. Cost: one mpv process per change; a PNG that mpv cannot read is refused with a message.

## D25. Reboot, power off and the clock go through a separate root helper with three fixed commands
Why: the old panel had these buttons and ran sudo from PHP. The panel stays unprivileged (D6). `pvj-netd` only runs where NetworkManager exists and has a tight sandbox for one job, so a second helper, `pvj-sysd`, takes these: root, no capabilities of its own (it asks systemd and timedated over D-Bus), AF_UNIX only, answers only root and pvj-web (SO_PEERCRED), and runs `systemctl reboot|poweroff` (after `systemctl --dry-run` says yes, one second after answering, once) and `timedatectl` with a validated epoch (2025 to 2036), only while the clock is known not to have come from the network, switching network time back on afterwards only if it was on, checking that it is, and leaving a marker so a helper that dies half-way puts it back on at its next start. Its socket lives in its own root-only folder. The API needs a full-access device and a fixed confirmation value (it stops a blind or accidental request, not a deliberate one). OSC, MIDI and DMX cannot reach it. Cost: one more small service.

## D26. A live input is read by a separate helper and piped into the player
Why: on the real Pi 4 (mpv 0.40, a USB3 HDMI capture stick), closing a V4L2 capture inside the player crashed the player with SIGBUS or SIGSEGV in 4 of 5 switches back to a file; turning off the cache did not help. The crash is in the capture teardown, so the player never opens the device: a helper mpv, started by the web service (which gets the `video` group and `char-video4linux` in its unit), writes raw frames to a pipe in /run/pvj that the player plays with the raw video demuxer. Result on the Pi: 0 player crashes in 5 switches; 720p30 and 1080p30 without dropped frames. Cost: an extra copy of every frame (about 1.5 cores at 1080p30 in all); no sound from the input yet; 60 fps modes are not offered.

## D27. Projectors are controlled with PJLink, on private addresses only, and their passwords are never returned
Why: the old panel's Beamer On and Off buttons need a replacement, and PJLink (TCP 4352) is the one protocol most network projectors share; RS-232 would need a USB serial adapter and a per-model command table. The panel service opens the connections itself (no root needed). A target must be a private or link-local address, checked at add time and again before every command (a name could change), so the box cannot be turned into a way to reach other networks; loopback is refused. The password is kept in the settings file and never sent back (only "password set"), since a guest or presenter must not learn it. Commands to every projector run at once, each with one 10 second deadline for connect and both reads (a name lookup is not bounded), one at a time per projector; OSC and the schedule send them in the background so a dead projector never delays a cue. The metadata address 169.254.169.254 is refused. Different errors for "refused" and "timed out" are kept because they help an operator; they also let a full-access user probe ports on the private network, but nothing is sent until a PJLink greeting arrives. Cost: PJLink class 1 only (power, mute, state); its MD5 authentication is weak, so the show network must stay private; not tested on a real projector.

## D28. Projection mapping is a GPU shader in the player, driven by a precomputed warp table
Why: the old box ran ofxPiMapper (openFrameworks) beside the player and steered it with a fake keyboard; nothing of that fits an unprivileged, mouse-free box. mpv already renders on the GPU and runs GLSL user shaders on its final picture (the OUTPUT hook), so the mapping is a shader the panel writes. Measured on a Pi 4 at 2560x1440 while playing 1080p H.264: one extra full-screen pass with mpv's default 16-bit buffers dropped 8 frames a second, and none with 8-bit buffers (`fbo-format=rgba8`), which the player uses only while a mapping is shown; a direct shader that tests every cell per pixel cost more with each cell (a 4x4 grid dropped 11 a second even at 1080p). So the show uses a table, one entry every 4 pixels, built in Python in the background: two layers (top surface and the one under it) with the picture point and the signed edge distance of each, which keeps edges and overlaps smooth; the GPU reads the table and the picture, the same cost for any number of surfaces (0 dropped frames at 1920x1080 with a 64-cell grid; about 3 a second at 2560x1440, where the GPU is at its limit). Grid cells are bilinear, not perspective, so neighbouring cells agree along shared edges. While editing, the direct shader is used so changes show at once, with outlines drawn in the shader (an mpv osd-overlay did not appear in screenshots, so it could not be checked). Surfaces are in screen pixels, but the OUTPUT hook only covers the picture's own area, so while a mapping is shown the player stretches the picture to the whole screen (`keepaspect=no`; letterboxing moved every surface, seen on the Pi with a 720x576 clip). Cost: a second or two to prepare the show picture after an edit; clips are stretched while mapped; map at 1080p or less on a Pi 4; no import of old ofxPiMapper files yet.

## D29. Remote support is a session the studio starts: WireGuard out to the owner's server, panel only, time-limited
Why: boxes sit behind studios' routers and IT rules, and the owner needs to help remotely. Researched options: WireGuard to an owner-run server (in Debian, kernel built in, no third-party account), Tailscale or Headscale (best traversal, but a large root daemon from a third-party repository and a control server that can reach the whole fleet), a reverse SSH tunnel (TCP, passes more networks), RustDesk (remote desktop: this box has no desktop session, and an always-on client with full control is the opposite of what is wanted). Chosen: a session started by a full-access device at the studio (never through the tunnel), for 15 minutes to 4 hours (1 hour by default), with a role the studio picks; the box dials out with its own key; a root helper with only CAP_NET_ADMIN creates `wg-pvj` and an nftables table that lets in only the panel and ping from the support network, forwards nothing and starts nothing into the tunnel, keeps the deadline itself and removes everything at start, stop, restart and expiry (fails closed). Support signs in with an 8-character code read out by the studio, valid only through the tunnel, for that session, 3 sign-ins, throttled; the login is never stored as a device. Through the tunnel some things are refused whatever the role (these settings, sessions, devices, codes, the PIN, power off). Every device shows a banner (Stop on presenter and full devices); the panel closes any tunnel left by an earlier run of itself, a session lasts at most 8 hours however often it is extended, the helper removes the interface before its firewall table (and keeps the table if the interface will not go), only the box's own tunnel address and the panel's real port are reachable, and a support network that overlaps a network the box is on is refused (review findings). Cost: the owner runs a small server (scripts in tools/support-hub); it is trusted during a session and sees panel traffic; networks without outgoing UDP cannot use it (no TCP fallback yet); tested on the Pi only against a stand-in server.

## D30. No native SMPTE ST 2110 input; ST 2110 sources come in through a gateway
Why (research report, 2026-09-30; amends D9): nothing was built, only a planned x86-only manifest. HD ST 2110-20 video needs 1.24 Gbps (1080i59.94) to 2.6 Gbps (1080p60, 10-bit 4:2:2) on the wire, more than the Pi's 1 GbE; a Pi 4's network chip has no hardware PTP timestamping; real plants expect NMOS IS-04/IS-05 registration, managed multicast and PTP grandmasters, so plugging a box like this into one is not realistic. The people who own 2110 plants are broadcast facilities; this product's users run NDI, SRT and HDMI. A 2110-to-HDMI converter (Blackmagic 2110 IP Mini IP to HDMI, about 330 USD) feeds the capture input that already exists, and 2110 to NDI will work once NDI is built. The module manifest is removed and the docs say "through a gateway". Revisit only for x86 with a 10 GbE card if a user with a 2110 plant needs direct ingest (then GStreamer 1.30's 2110 elements or Intel MTL, plus NMOS), or if a Pi 5 is shown to receive 2110-22 (JPEG XS) in real time.

## D31. Multi-box sync: a server broadcasts its position, clients nudge their speed and jump only when far off
Why: the old boxes synced with omxplayer-sync (the "master" broadcast its position; "slaves" seeked when more than 50 ms off), which jumps visibly and took up to 10 seconds. The owner asked for server and client as the names. The server sends a small JSON message about ten times a second to each local network's broadcast address, UDP 5577: clip name, position, pause, speed, loop, blackout. A client plays the same file name from its own media (or a USB drive's top level), jumps only when more than 0.5 s off (aimed ahead by a lead it learns from each jump), and otherwise plays up to 4 percent faster or slower for a moment (mpv keeps the pitch), at the server's speed within 15 ms. No clock sync between boxes: on a wired LAN the message's age is well under a millisecond. Messages only from private addresses with the same group name, strictly checked, one server followed at a time. The video wall is the same messages plus a per-box crop (mpv's video-crop, checked on the Pi) with bezel compensation, so every box plays the whole file. Measured on a Pi 4 with two headless players: median 0 ms, at most 40 ms (one frame) after the first jump. Cost: same file names on every box; same network (broadcasts do not cross routers); not yet measured between two boxes on two screens; forged messages are possible from inside the network.

## D33. The panel starts updates through fixed template units; the signature is the gate
Why: the old panel had Update buttons (it unzipped GitHub's master over the web folder, unsigned); the manual deep dive ranked an update button high, since owners without SSH skills could not update. The panel stays unprivileged (D6): it stores an uploaded bundle, its signature and an optional checksum in `/var/lib/pvj/update-inbox` (name pattern and size checked, only the newest kept, refused while an update runs), and asks pvj-sysd to start `pvj-update-inbox@V.service` or `pvj-update-usb@V.service`, where V is the version the person confirmed (three numbers, checked by the API and again by pvj-sysd, which also refuses a second update under a lock). The units are oneshot, never started at boot, and run `pvj-update inbox|usb --version V --result /run/pvj-update/result.json` as root; `ExecStopPost` marks an update cut off by the time limit as failed. pvj-update is the gate: it opens the upload folder and every untrusted file without following links (regular files only, size limited, copied with a byte limit into a private folder), checks the signature against `/etc/pvj/allowed_signers` (the checksum is needed only for an unsigned development bundle), refuses older versions, backs up settings and rolls back by itself; a lock file stops two updates at once, from the panel or a terminal; any error ends with "failed" in the result file. An uploaded bundle is tried once and removed, inside the opened folder only. Remote support may install signed updates (helping with updates is part of support); it still cannot power the box off or change access. Cost: two more units; an owner must hold a signing key.

## D34. The panel design playground is a Node dev tool under tools/, never shipped
Why: trying layout, type and colour ideas on the real panel means editing app.css on a box or in the browser test. `tools/panel-playground` is a React and Vite page that copies the panel's class names and default values and puts knobs on them, with an export of only the changed CSS and a themes.d file. It complements the screenshot and mock-up exports in `docs/mockups`, which show the panel as it is. It is the first `package.json` in the repository (the browser tests run on Node without one); that is acceptable because it is a dev tool: nothing under `pvj/`, `bin/` or `install/` uses it, release bundles (`tools/make-release.sh`) and the image never include it, and the panel itself stays plain JavaScript with no build step. Its dependencies are React and Vite only (no component library), with `package-lock.json` committed; `node_modules/` and `dist/` are ignored. Cost: `src/panel.css` and the defaults in `src/settings.ts` are a copy of app.css and drift when the panel changes; the README says to update them together.

## D35. The system log is kept across restarts, capped at 64 MB
Why: the test Pi restarted on its own and the cause was lost, because Raspberry Pi OS keeps the journal in memory (`40-rpi-volatile-storage.conf`). The installer adds `/etc/systemd/journald.conf.d/50-pvj-persistent-log.conf` (sorts after it, so it wins): `Storage=persistent`, `SystemMaxUse=64M`, `SystemKeepFree=500M`. Cost: some writes to the SD card (journald batches them, about every 5 minutes, and the cap bounds the space). With the read-only root (pvj-rootfs) /var is in RAM, so the log is lost at a restart again. D32 was never used (a numbering gap, not a removed decision).

## D36. The box is a room controller staff can use at Leyline, and the owner's VJ tool
Why: the owner wants a system left running at Leyline so staff (not the owner) can run the projectors while the owner is away; in-house use is about equal ambience and events. The room has at least two installed projectors (main backdrop wall; a painting wall), four Epson projectors in all (X27 and X39, models to confirm), all wired to the network; consoles (Switch, PlayStation, Xbox), movies and shaders are the sources; audio routing is not decided. So the order changes: a general PJLink control system first (plan in pvj/PROJECTORS.md), then groups, scenes and a simple Room screen for staff, then ISF shaders (the owner's preference) and projectM as an optional module on boards that can run it, then painting-wall masks, then a driver for a controllable video matrix once one is chosen. Consoles do not go through the box (capture lag); they go to projector inputs or a matrix. The private NXLX network is a dedicated router, not the Pi. Cost: the remaining parity items from the manual deep dive move later.

## D37. PJLink Phase 1: details and labels in the settings without a schema change, status in memory, at most 8 threads
Why: a projector's details (what it says it is, its input list) and the labels typed for its inputs are optional keys on its settings entry (`details`, `labels`), read with defaults, so settings stay at schema 13 and an older box's file needs no migration; its status changes every few seconds and is kept in memory only. Each projector has a background worker with its own stop signal that does the status check, the first identify and the input retry, on at most 8 threads in all; a thread that ends takes over a waiting projector instead of a new one being started. One command per connection stays, although the standard allows several, so the private-address check and the 10 second deadline (which includes the wait for an earlier command) hold per command. `mute` and `unmute` keep meaning picture and sound together (OSC and old clients rely on it); the separate ones are new actions. An input can only be chosen from the projector's own INST list. Only "unavailable" (ERR3) starts the 90 second retry, and input changes to one projector go out one at a time, so the last choice stands. Labels are never pruned by a refresh. A projector that reports an error makes the box's overall health "bad", a warning "warn"; one that does not answer is "unknown" and changes nothing, since it may be switched off at the wall. Input selection from the schedule and OSC waits for Phase 3 (groups and scenes). Cost: details can be stale until Refresh details; a status up to 45 seconds old; a slow name lookup can hold one of the 8 threads; nothing here has met a real projector.

## D38. Shader sources are ISF generators drawn at mpv's NATIVE hook over a tiny black carrier; Vibes never takes the screen back
Why: the owner prefers ISF and wants one-tap ambience for the room (D36). mpv already runs GLSL user shaders, so no second program and no dependency is needed (D1, D5). The carrier is `av://lavfi:color=c=black:size=WxH:rate=30,format=rgb0`, built from whole numbers only: the same route as the test pattern, so no D22 flag changes. The shader hooks NATIVE and sets its own size, which keeps brightness (opacity, fades, Blackout) and the mapper's OUTPUT hook (D28) working; at MAIN brightness had no effect (seen in CI). Inputs are written in as constants and a fresh file is made for every change, as the mapper does; TIME is counted from mpv's frame number in high precision. The player object owns both shader layers and an epoch that goes up whenever anything is played, accepted or stopped; Vibes passes its epoch with every change and every step of its own fade, and the player compares it under its lock, so a rotation can never land on, or darken, a clip someone started (D18's rule: it ends, it does not fight). Vibes does not use the panel's Fader, which keeps a waiting play as a callback that any other use drops. A shader the GPU refuses is found through mpv's own error log and replaced by the one before it or by black. Uploaded code is checked as the compiler reads it (comments stripped, no `//!`, no includes or extensions, no own uniforms) and bounded in size. Settings need no schema change. Cost: generators only (no multi-pass, pictures or sound); TIME slows down when frames are dropped and starts anywhere; shader code from a full-access device runs on the GPU and can be slow, which nothing detects; 8-bit buffers while a source is on; not offered on a Pi 3; a sync server playing a shader stops its clients; **unmeasured on every board and not seen on a display**.

## D39. Box care is done by the unprivileged panel; what is secret in a stream address is decided in one place
Why: settings export and import, the diagnostics file and factory reset need no new root command, because the settings file and the media folder already belong to the panel's user; fewer root paths is the point of the service split. The PIN, devices, remote support and its history belong to one box and are never exported or imported (a file that holds them is refused); projector passwords and the secrets of a stream address go into an export only with a tick, and never through the support tunnel. An import is the request body itself, parsed strictly, sent through the same migrations as a load and every section's own check, and only the sections the file held before the migrations are imported; nothing changes unless all of it passes. Which parts of a stream address are secret is one function (`streams._pieces`) used by the panel's list, the player status, the export and the diagnostics: the login; for RTMP the last part of the path and the whole query; for SRT every query name not on a short list of plain connection options (an allow-list, since a streamid can carry a user name and new names appear); for RTSP query names that sound like a secret. An import keeps the box's own full address when the file holds its shortened form, so a shortened address never replaces a working stream. A reset wipes the devices, the join codes and the PIN in one step under the pairing lock and the settings lock, and a request that was already past its token check has what it made taken back. Import and reset set one flag under the lock a USB copy and an update start under, and refuse instead of waiting. Cost: an export without the tick does not play its RTMP and SRT streams on another box until they are typed in again; an RTMP address without a stream key loses its last path part too, and view-role devices no longer see a streamid; a second import or reset at the same moment gets a 409; the root-only update backups survive a reset (a rollback after a reset brings the old devices back) until a root command removes them; the checks know the settings as of schema 13 and a new top-level section fails a test until its check is added.

## D40. The room: one sender per projector that always carries the newest choice; scenes are a settings section without a schema change
Why: staff tap, and tap again. A scene or a group button therefore never sends from the request: it leaves steps for each projector, and one thread per projector (at most 8, never more however fast the taps come) sends them in the order power, source, mutes, through the Phase 1 client, so the private-address check, one command at a time and the 10 second deadline hold for every command, and a dead projector holds nobody up. Because a projector has one sender, a newer choice is always sent after an older one; a command not yet on the wire is cancelled, and a source change that Phase 1's retry is still trying for a replaced scene is stopped (`Monitor.cancel_input`), so nothing stale can land later. A scene replaces everything older, also on projectors it does not name; a group button replaces only its own kind of step, so a mute pressed during warm-up does not cancel the scene's source; Off replaces all. A button outside the room (the Projectors card, `/beameroff`, a `projector_off` schedule entry) drops the room's waiting steps of its kind before it sends (`Room.supersede`), so the last choice made anywhere stands. The source is stored as the projector's input code and shown by its label, so renaming a label never breaks a scene. What the box does in a scene is a table of existing API calls made as a presenter through `Api.handle`, so a new feature is one line (Vibes was the first). The schedule, OSC and MIDI call the same route as the Room screen. Groups and scenes are a new top-level section `room`, present in the defaults and read with defaults everywhere, so settings stay at schema 13 and an older file needs no migration; it is checked by `room.validate`, which box care uses for import. The module is separate from Projector control and requires it, so a box with one projector and no staff never sees the Room tab. A source is sent only after "is it still wanted" is asked inside the monitor's input lock, and a refused power command is done only when the projector itself, asked then, says so. Cost: a result is read from `GET /api/room`, not from the answer to the tap; a schedule entry or MIDI mapping keeps the id of a removed scene and then does nothing; no DMX (the fixed channel row has no place for a scene) and no volume (class 2); rapid tapping delays the first command until the taps stop; nothing here has met a real projector.
## D41. Wi-Fi joins the Network module with the same confirm-or-revert; the password goes only into a root-only keyfile
Why: staff phones and wall tablets at Leyline need Wi-Fi, and a box with its own hotspot can be set up with no router. A Wi-Fi change can cut the panel off as easily as a wired one, so it reuses D10: a separate candidate profile, pending until confirmed, undone on timeout, failure, helper restart or reboot. `nmcli` takes a password only as an argument, and every account can read other programs' arguments, so pvj-netd writes the candidate as a NetworkManager keyfile (root only, created new, never through a link, the SSID as a byte list) and loads it; nmcli does the rest. The password is never kept, returned, logged or saved in the helper's state. One Wi-Fi network is the box's own (`pvj-wlan0`). "Wi-Fi off" switches the radio off on confirm; a radio switched on for a change is switched off again when it is undone. The hotspot defaults to 10.43.0.1/24 so it never overlaps a wired "serve addresses" on 10.42.0.1. Not supported: 802.1X, WEP, setting the Wi-Fi country. **Never run against a real NetworkManager or Wi-Fi chip**, so it is beta with the rest of the module.

## D42. System is an index of rows with one page each; a module is switched on its own page, and every row says its state

## D43. One switch per feature; a control with one safe effect applies on tap, and Save is only for fields that change together
Why: DMX, MIDI, the schedule and OSC each had a second switch inside their card, and the index said "On, but not listening: turn it on inside". Staff who are not technical switched the page on and nothing happened. The owner said yes to one switch. Now: the page switch is a list of steps (the module, then the feature's own `enabled` flag; OSC and Remote support have only the flag) and shows On only when every step is on. Switching on runs the steps in order and always sends the flag, because what the panel last read may be old; a box in the mixed state (module on, flag off) shows Off and gets only the flag. Off is the module for DMX and MIDI, and only the flag for the schedule, so its entries can still be read. A failed second step shows its reason on the page and leaves the switch Off. A schedule with saved entries asks first, in place, because it goes live at once. ## D44. Third-party shaders are bundled as packs: unchanged, under their own licence, in the library but not in Vibes
Why: the owner wants many more shaders and pointed at Vidvox's ISF-Files. That repository is MIT as a whole (its `LICENSE` names 2018 and no holder), which allows shipping it with this project; but many ISF files anywhere are ports of other people's shaders, and a repository's licence covers only what its owner could license. Rules, so the next pack needs no new decision: (1) a pack is a folder inside `pvj/shaders.d` (`isf-files` is the first), listed after the project's own ten and before uploads, each shader with a `"pack"` name in `GET /api/shaders`; the project's own folder is searched first, so a pack can never replace one of ours, and an upload cannot take a pack's name. (2) A file goes into a pack only if the pack's licence clearly allows redistribution **and** the file's own comments do not point to code from elsewhere whose terms were not read and found compatible; when in doubt it is left out and listed in THIRD_PARTY_LICENSES.md (the rule only catches borrowing a file admits to; a well-known snippet without a credit is caught only by someone recognising it, so every candidate is also read for those), and the owner can still upload it to a box (use, not redistribution by us). (3) Files are byte for byte upstream (checksums in the pack, compared by a test); only the file name changes (`isf-` plus lower case and hyphens: the release script splits file names at spaces, and a prefix keeps ids apart from the owner's uploads of the same upstream file). Upstream's licence file sits in the pack, and so does the notice of any other project whose code is inside a file (a release carries only `pvj/`, `bin/` and `install/`, so a notice at the top of the repository does not ship); the pack is declared MIT in REUSE.toml, with the commit, the file list and the notices of code inside the files in THIRD_PARTY_LICENSES.md. (4) A bundled file must pass what the project's own shaders pass on the real player in CI, on OpenGL ES and on desktop OpenGL (taken, drawn, more than 40 colours, not dark); a file that fails either is not bundled, even if the owner's Pi would run it. (5) A pack's shaders are **not in the Vibes rotation** until a full-access device puts one in (`"included"` in the settings, a key that exists only once used; the project's own and uploads stay opt-out through `"disabled"`). Cost: 7 of 327 upstream files are bundled (36 translate; 11 left out for their origin, two of them, Worley Cells and Color Test Grid, only after the independent review; 18 for the picture check, Spiral among them once other varied inputs showed it on the line), about 35 KB in the release; the translator renames two names instead of refusing them (`out_color`, an input called `color`), reads the ASCII rule after comments are cut, and refuses `##`. Rejected: bundling the whole repository (most of it cannot run here, and some of it is not Vidvox's to license); fetching packs from the internet on the box (the box must work offline, and D22 and the update signature are how code reaches it); editing upstream files to make them pass (they would no longer be upstream's, and each edit would be ours to maintain); loosening the picture rule for flat shapes inside the same pack (a second pack with its own rule is the honest way, if the owner wants the shapes).

## D46. A shader change is a coalesced recompile; TIME comes from a carrier that counts its own frames; presets, sets and the guard are settings without a schema change
Why: the owner wants to perform with shaders. mpv's `--vo=gpu` gives a running user shader no way to take a new value (`//!PARAM` and `glsl-shader-opts` are gpu-next only; read in the source at 0.37 and 0.40), and the output is not switched (the mapping, the brightness order and the Pi measurements are on it). So a change is a new text; one worker applies the newest wish at most five times a second and exchanges only the shader file, and requests only note the wish, so a MIDI reader never waits for the GPU. A speed change without a jump of TIME needs the frame the shader is at; mpv's `frame` cannot be read from outside, so the carrier paints each frame with its number and the player's position gives the same number. Alternatives weighed: mpv's own playback speed (more GPU work above 1, capped by the display rate, collides with the Mix speed), and accepting a jump. The carrier's clock is verified in CI on three GL dialects and not on the Pi; `clock: frame` is the way back. Rotation sets, presets, the guard's notes and the switches live under `"shaders"` as defaults on read (schema stays 13): the first set is computed until someone edits it, and a box set up by the first version gets its list written as that set on the first save. The heavy two (measured) and uploads are out of the default rotation. A controller follows the playing shader's n-th input rather than a named one, so one layout works for every shader. After the independent review: a queued show carries the epoch of its request (the worker never takes the screen from what was played or stopped meanwhile, and never ends a rotation); settings are edited under their own lock, never the one held across the GPU's look at a shader; a heavy mark belongs to its drawing height and board, and the guard stops marking when two in a row fail with no healthy shader between (then it is the box, not the shaders); a damaged settings row costs only itself. With the Performance family (#74): the box starts with two sets (Ambient active, Show for the Performance shaders), and the speed control stays at 1 or below for a Performance shader unless a full-access switch lifts it, because the shaders' flash cap is counted in TIME (the simplest sound way: the cap stays in the shader's own code, the engine only refuses to multiply it).

## D45. Every service has its own runtime folder under a /run/pvj that belongs to root; paths live in pvj/paths.py
Why: `pvj-player` (the display account), `pvj-web` and `pvj-netd` (root) all declared `RuntimeDirectory=pvj`, mode 0770, `RuntimeDirectoryPreserve=yes`. systemd.exec(5): "If the specified directories already exist and their owning user or group do not match the configured ones, all files and directories below the specified directories as well as the directories themselves will have their file ownership recursively changed to match what is configured" (in the source, `setup_exec_directory` calls `path_chown_recursive`, which returns early only when the top folder already has the right owner and group). So at every start of one of the three, `/run/pvj` and everything in it went to that unit's user: seen on the Pi as root:pvj after boot, the display account after "Restart player" (with the root helper's `netd.sock` and the PIN file), and pvj-web after a reinstall. The account that plays untrusted media, or the panel's, could then replace or remove the socket the panel sends Wi-Fi passwords to, and read the full-access PIN. Nothing was removed on stop only because all three set Preserve=yes (the default removes the folder when the unit stops). Read in the source of systemd 252 (Bookworm, `src/core/execute.c`) and 257 (Trixie, `src/core/exec-invoke.c`): the same in both. By order: the owner was the user of whichever of the three started last, and when the starting unit already owned the folder the files in it kept the owners they had. At boot that is usually pvj-netd (root), which waits for NetworkManager; after "Restart player" or `systemctl restart pvj-player` the display account; after `systemctl restart pvj-web`, or an update from the panel (pvj-update restarts the player and then the panel), pvj-web; a manual `install.sh` restarts pvj-netd last and so leaves root. The last four are worked out from the units and the rule; only the three states in the first sentence were seen, and which kind of reinstall gave pvj-web was not recorded.
Now: `/run/pvj` is no unit's RuntimeDirectory. The units name `pvj/player`, `pvj/web` and `pvj/netd`; for a nested name systemd creates the parent only when it is missing, as root 0755 (`mkdir_parents_label(p, 0755)`), and gives only the innermost folder to the unit. `install/pvj-tmpfiles.conf` states the same (`d /run/pvj 0755 root root`), which also repairs a parent that already exists. Each folder is 0750 with group pvj: the group reaches what is in it, only the owner can add, replace or remove. Player: `player.sock` 0660 and `preview.jpg` (mpv writes it; the panel never removes it there, and could not: its sandbox mounts every folder but its own read-only, so even an attempt fails with "Read-only file system". It tells a new picture from the one that was there by the file's inode and its two timestamps, compared for "the same", and never serves the old one again). Panel: `pin` 0600 (it was 0640, so the player's account and any `--web-user` account could read it; root reads it for `sudo pvj-pin`, nobody else needs it), the live-input pipe, overlays, shader and mapping files 0640, the undervoltage note. Network helper: `netd.sock` 0660 root:pvj, callers still checked with SO_PEERCRED. `pvj-sysd`, `pvj-supportd` and the update units already had folders of their own with one user each and stay where they are: moving them would add a restart of the helper that starts updates and of a support session that may be doing the update, for nothing. `PVJ_RUNTIME_DIR` now always means "the folder this process writes"; the panel is told its peers with `PVJ_PLAYER_DIR` and `PVJ_NETD_DIR`; a process never creates a peer's folder, a missing one means "not running", so the services start in any order. Static tests refuse a RuntimeDirectory shared by two users, one that is group-writable, and one that is the parent of another.
Upgrade: the installer decides whether `/run/pvj` is sound: root:root 0755, a root-owned marker `/run/pvj/.d45`, and nothing in it but `player`, `web` and `netd`, each a real folder with its own owner and mode. If not (an old shared folder, an emptying that was cut short, a folder with the wrong owner, anything planted), it stops the player, the panel and the network helper, then `daemon-reload`, then chown root and 0755, removes the marker, empties the folder (or stops with a plain message; the next run finishes it), and only then lets tmpfiles write the marker; then it restarts, or with `--no-start` starts again exactly what it had stopped. Stopping first matters twice: before the reload a service that restarts by itself runs its old unit and takes the folder back, and after it systemd would chown a name planted as `/run/pvj/player`. A sound folder is left alone except for stray files directly in it. Nothing is carried over: the undervoltage note (it only lasts until the next boot anyway) is lost by an upgrade. Rule from the review, kept by a static test: root never creates, writes, chowns or chmods a name inside a folder that an unprivileged account owns, because a link planted there sends it anywhere (the first version wrote the note into the panel's folder, and a dangling link made root create its target). The one exception is the two rollback links below, made by tmpfiles with symlink(2), which never follows an existing name, with no owner or mode set. With `--no-start` (an update from the panel, which restarts only the player and the panel) the installer does `try-restart pvj-netd`, and `pvj-update` does the same from now on.
Rollback runs older code under these units: each unit gives it its own folder as `PVJ_RUNTIME_DIR`, and tmpfiles keeps two links in the panel's folder (`player.sock`, `netd.sock`) so an older panel finds both sockets. Known limits of that state, accepted because it is temporary: the older panel's preview does not work; it writes `pin` with mode 0640 again, so the display account can read it through group pvj; and when it stops a player it started itself it removes the `player.sock` link (back at the next boot, or with `sudo systemd-tmpfiles --create /etc/tmpfiles.d/pvj.conf`). No one-line change avoids the 0640: the older code sets the mode itself, and the panel's folder cannot be closed to the group because the player reads the shader, mapping and overlay files and the live-input pipe there. Install the older version with its own installer to leave that state, or go forward again.
One thing to know: systemd lets `EnvironmentFile=` win over `Environment=`, so a `PVJ_RUNTIME_DIR=` line in `/etc/pvj/pvj.env` would point a service at the wrong folder. No installer or image ever wrote one there (checked in the history), and none must be added.
Cost: three more lines of tmpfiles and two links kept only for rollback (remove them when no box can go back that far); a helper on the old path is unreachable for the seconds between the installer and the restart; a `--web-user` account can no longer read the PIN; an upgrade stops the player, the panel and the network helper for the seconds it takes, and loses the undervoltage note; one marker file in `/run/pvj`. Tested in CI by a job that runs the installer for real as root under the runner's systemd (`tests/real_install_test.sh`); not run on hardware: `tools/DEVICE-TESTING.md` has the checklist.

## D49. Controller profiles: a file per known controller, under the person's own mappings; pickup per action; no lights
Why: the owner's words, "I would like to be able to connect a controller like the Korg nanoKONTROL2 and have it automatically/preset/natively mapped to control mastercontrol." D21 left profiles for later as "a file of entries for a named controller". Now a profile is one JSON file in `pvj/controllers.d/` (shipped, read-only, checked strictly on load; a bad file is left out with a log line): what it matches, a drawing (a grid of named controls), what each control sends, and its default action. Three ship: Korg nanoKONTROL2, Akai MIDI Mix, Novation Launchpad Mini. Adding a controller is writing one file.
Matching: by the ALSA card id (D21), which is only the last word of the product name ("Mini", "Mix"), so also by the product name from `/proc/asound/cards` when it can be read; both as whole-string patterns. A Launchkey Mini is not taken for a Launchpad Mini.
Precedence, per control: the person's mapping (Learn, or a tap on the drawn control; stored in the same `map` as before, so there is one place for "mine"), then the profile if its switch is on, then the built-in map; and the built-in map is not used at all for a controller whose profile is on, because real controllers collide with it (nanoKONTROL2 knob 5 is CC 20, the built-in opacity; MIDI Mix CC 25 is "blackout while up"). A mapping for "any controller" also wins over a profile. Where both exist for one control, the controller's own mapping is the one that runs. "Back to the standard" removes only that controller's own mappings on the controls of its layout.
Pickup (soft takeover), decided per action: opacity, volume, clip speed, shader speed and shader brightness wait until the control reaches the box's value; shader controls, the colour turn, size, position and the Vibes time may jump. The value is read from memory only (the mix, the engine's `playing`), never from the player or under the engine's lock; the box keeps no volume or clip speed in memory, so for those the last value a controller set is used (100 percent and 1x before that), which is weaker and said so. Pickup applies to recognised controllers only; plain Learn mappings behave as before.
Guard: blackout and Room scenes in a profile need the same press twice within a second (0.25 to 1 s apart). A scene can switch a room's projectors off, so it counts as room-wide. The person's own mapping is not guarded: they chose the button.
New actions, each a call the API already had: previous and next clip, fade in, shader hue and brightness, Room scene 1 to 8 by its place in the list (a profile cannot carry a scene id), "nothing", and a pad of "the controllers' bank" with two actions to step it. That bank is state in the hub, not saved: there was no server-side bank (the panel's bank is per browser), and two of the three controllers have one row of eight buttons. The brief proposed one "previous" and one "next" that act on the clip or the shader, whichever plays; they are two pairs instead (clip, shader), because a button whose meaning depends on what is on the screen cannot be labelled on the drawn layout and deciding it would mean asking the player from the thread that reads the controller. The MIDI Mix has no transport buttons, so its layout has the shader pair only (clips are its pad row).
Settings: one new optional key, `control.midi.controllers` (`{"<name>": {"standard": false}}`, only for layouts switched off), read with a default, so no schema change; checked by `check_control` in boxcare with a round-trip test. `GET /api/midi` is now readable by a presenter (the drawn layout), changing stays full access.
Lights: not built. The hub stays input only (D17). The service may only read ALSA devices (`DeviceAllow=char-alsa r`, pinned by a test), a unit file does not travel with an update or a quick deploy, and nothing here could be tried on the hardware; a writer that cannot be tested, behind a sandbox change that boxes would not have, is not clean. `pvj/MIDI.md` ("Not built yet") lists what it would take, including that the nanoKONTROL2 needs its LED mode set to External in Korg's editor.
Sources, and their limits: the Launchpad numbers are from Novation's Launchpad S Programmer's Reference (X-Y layout) and agree with the one recording (D21). Korg's Parameter Guide has no table of factory CC numbers and no Akai document with numbers was found, so every nanoKONTROL2 and MIDI Mix control is marked `unverified` in its file and in the docs; their numbers are the widely reported factory ones (the Mixxx mapping; a public Live script).
Cost: about 350 lines in `pvj/midi.py`, three data files, a page that polls twice a second while it is open; one more thing that matches on names the box does not control. Not tested on any real controller: the owner's two-minute check per controller is in `pvj/MIDI.md`.
Changed after the independent review (2026-10-05): matching is by exact card id and product name and by USB id (which decides alone), with no patterns in a profile, and a card list that was read but gives no usable name does not match; a mapping the person makes on a card for blackout or a Room scene is guarded by default ("Press twice", theirs to switch off) and saving the standard stores nothing; a message after MIDI is off or the controller is gone is dropped; the API keeps the last volume and clip speed in memory (`Api.levels`) for pickup, so the sentence above about "the last value a controller set" no longer holds.
Number: the open pull requests #75 and #76 each wrote a D47, so this is D49 to stay clear of both; whichever of them merges second takes D48.

## D47. The Shaders page is an instrument: controls send values only, a card is never redrawn under a hand, sets stay out of sight until there are two, and a laptop has keys for Vibes, stepping and presets

## D48. A presenter may make, show and end the guest join code, and nothing else about access

## D61. A MIDI controller can put a one-time pairing code on the box's display: off by default, a hold that ends, and never through the API

- **Its own code, not a join code and not the PIN.** One slot in `auth.py`, apart from `_joins`: single use, 120 seconds, 6 digits, a role of presenter (`join`) or full (`owner`). ## D66. The ISF parser takes comments before the header, and an input whose name is a reserved word in another letter case; a switch's DEFAULT may be the number 0 or 1, or one of four texts in quotes

2026-10-08. The owner asked for three leniencies for ISF generators as people publish them: a published file often begins with its credit, in comments, and the parser wanted the JSON comment first. This entry says what the parser accepts and nothing else: no file from anywhere was added to the repository, and whose files a box may hold is the licence question it always was (SHADERS.md, "Adding more ISF files to a box").

What was decided:

- **Before the JSON header a file may have blank space, `//` comments and `/* */` comments, at most 4 KB of them** (`MAX_LEADING`, `find_header` in `pvj/shaders.py`). The header is the first `/* */` comment whose first character after blank space is `{`, and it is the header with no second try: if its JSON cannot be read the file is refused, and no later comment is tried. A comment that begins with anything else is a plain comment. A `/*{` inside a `//` line is comment text. Comments do not nest, so a header written inside a comment is not found, and the file is refused for having code with no header before it. Anything before the header that is neither blank space nor a comment is refused, a `#` line too. The same for filters (one parser).
- **Those comments go nowhere, and the stored file keeps them.** The text that is checked and sent to the player starts after the header, as before. The line the code starts on is counted over the whole file, so `#line` still gives the GPU the file's own line numbers. An upload is stored as its own bytes.
- **4 KB**, because credits are a few hundred bytes and a licence text one or two KB; with the header's 8 KB (counted from the header's own start, as before) 20 KB of the 32 remain for code. The search is one pass with `str.find`, no pattern, and stops at the limit.
- **A `bool` input's `DEFAULT` may be `true`, `false`, or the number 0 or 1** (0.0 and 1.0 are the same numbers). The parser took those numbers already. Every other number is refused. (As first written this entry refused all text too; the owner chose otherwise the same day, see the addition at the end.) A value set from the panel, a preset or a controller stays exactly true or false (`clean_value`); this is about the file's header only. An `event` has no default of its own. The other switches a header can hold (`PERSISTENT` and `FLOAT` of a pass, `PERSISTENT_BUFFERS`, `IMPORTED`) are read only to refuse, and anything that is not empty, false or 0 there refuses the file; they were looked at and left so, since reading them as strict switches would let a file through that is refused today.
- **One rule for an input whose name is a reserved word in some letter case** (`renamed` in `pvj/shaders.py`). If the word is GLSL's or ISF's and the name is spelled in another letter case than the word (`time`, `Date`, `Float`), the input is taken and written into the shader as `pvj_in_<name>`, every use in the code with it. If the name is the reserved word letter for letter (`TIME`, `float`, `sin`, `frame`), it is refused as before. The player's and the translator's own words (`main`, `hook`, `frame`, `random`, `input_size`, `target_size`, `tex_offset`, `pixel_size`, the `_OWN` patterns, the prefixes `gl_`, `pvj_`, `isf_`, `hooked`, a `__`) are refused in any letter case as before. `color` stays the one word that is renamed letter for letter. The panel, the API, presets and the MIDI, OSC and DMX mappings see the file's own name: only `ident()` knows the other one.

Why this way: **the comments.** A credit is the author's and belongs at the top of the file; refusing it made people cut it off. "The first comment that begins with `{`" is a rule a person can check by eye, it cannot be steered by what a comment holds further in, and it never falls back, so a broken header is reported as a broken header. A plain first comment such as `/* not json */` used to be refused with "cannot be read"; it is refused still, now for having no header, and the message says that the comment at the top was read as a plain comment. **`time`.** It was never a clash: GLSL tells letter cases apart, and the translator defines `TIME` (as a macro) and `pvj_time`, nothing called `time`. It was refused because the reserved list is compared in lower case, a caution from an earlier review, in which checks had been bypassed by letter case (LESSONS, "Check the text the compiler reads"). That caution is right for the player's own words, where mpv's wrapper text is not ours to read, and it stays there. For the language's and ISF's words the lower-case comparison refused honest names (`time`, `date`) and protected nothing. They are renamed rather than simply let through because it costs nothing and keeps a property that is easy to test: no reserved word, in any letter case, is ever an input's name in the text the GPU gets. A name that is a reserved word letter for letter cannot be renamed by replacing the word, since the code's own `TIME` or `sin(` would be replaced with it, so those stay refused. **The switch.** A number that is exactly 0 or 1 has one meaning. Text does not: taking `"1"` invites `"true"`, `"yes"` and `"on"`, and a header that says `"0"` reads as true in most languages. (That was the first reasoning. The owner chose a closed list of four texts instead: the addition at the end of this entry.)

Cost / rules out: A credit comment that itself begins with `{` is taken for the header and the file is refused ("cannot be read"): that is the price of never passing over a broken header. **Three things are refused now that were taken before** (found by the independent review of the pull request, and kept): (1) blank space before the header is five characters only (space, tab, line break, form feed, vertical tab), where the parser used to pass over everything Unicode calls blank space, so a no-break space, U+0085, U+2028, U+2029, U+3000 and the control characters U+001C to U+001F in front of the header are refused; (2) plain blank space before the header counts toward the 4 KB, so 4,097 spaces there are refused where any amount inside the 32 KB was taken; (3) the header's 8 KB is counted in bytes of UTF-8, where it was counted in characters, so a header of 2,800 euro signs (8.4 KB) is refused and one of 8,100 (24 KB) no longer passes: without this the 20 KB left for code was not true. Both limits are counted after the byte order mark is dropped and Windows line ends are made `\n`, as the header's always was; the file's 32 KB is counted on the file as it is. A comment that looks like a header but has any other character between its `/*` and its `{` (`/**{`, a no-break space) is a plain comment and is passed over without a word; if a real header follows, that one is used, and if none does the file is refused with the message about the plain comment. `Time` and `rendersize` as input names were refused and are taken (renamed) now; a test that named them was changed, and names `Frame`, `RANDOM` and `Main` in their place, which stay refused. **Not verified on a GPU from this machine:** the tests added to `tests/test_shaders_gpu.py` (a file with comments before its header, a switch with DEFAULT 1 and inputs called `time` and `Date` draws its own values; a mistake in such a file is named by its line) run in CI only, on Mesa's software GPU. Nothing was run on a Raspberry Pi.

**Addition, the owner's choice of 2026-10-08 (the same pull request): a switch's DEFAULT may also be one of four texts.** A `bool` input's `DEFAULT` may be exactly `"0"`, `"1"`, `"true"` or `"false"` in quotes, read as false, true, true and false (`_BOOL_TEXT` in `pvj/shaders.py`). Lower case, no blank space, nothing else: `"TRUE"`, `"yes"`, `"on"`, `" 1"`, `"1.0"` and `""` are refused, and the message names everything that is taken. Why: files written for other ISF hosts carry a switch written so, and were refused for it. The worry of the first version (text has more than one reading) is met by the list being closed and compared letter for letter: `"0"` is false because the list says so, never because of how a language reads text, and a typo is still an error. Nothing of the text travels: the parser turns it into true or false on the spot, and the shader only ever gets `const bool x = true;` or `false;`. What does not follow, and why: a value that is set later (the panel, a preset, a controller, the API; `clean_value`) stays exactly true or false, because those come from this project's own panel and code, which have no reason to send text, and a strict check there catches mistakes; an `event` has no default (what a file writes there is never read); `float`, `long`, `color` and `point2D` take numbers only, since a number in quotes there would need a rule for every way of writing a number; and the header's switches that only refuse (`PERSISTENT`, `FLOAT`, `PERSISTENT_BUFFERS`, `IMPORTED`) stay read as before, so the text `"false"` there still refuses the file, which errs on the side of refusing. Cost: one more thing a header may hold that the ISF specification does not describe.

## D68. The server keeps 128 connections waiting, not 5; and the page asks again for a file that did not arrive, then says so

2026-10-08. The owner's standing instruction for a technical question: research it, choose, build. The question was the lesson of the same day, "a script of the page that the box never delivers": about once in ten page loads with three browsers on the dev Mac, `room.js` came back with no answer at all and the panel drew without its Room area and said nothing. The cause was a guess then. (D65, D66 and D67 are taken by branches that were open when this was written.)

What was found, by experiment on the Mac (the numbers are in the journal entry of this day):

- **The cause is the listen queue.** `PvjServer` never set `request_queue_size`, so it asked the kernel for socketserver's five. The server speaks HTTP/1.0: every request is a connection of its own, and a browser opens six at once. One browser never overran the queue; two did; with three, 493 of 1200 requests were reset at a queue of 5, 283 at 8, none at 16 and above. Six browsers still lost requests at 16 and none at 32. In the real Edge, three windows loading the panel together at a queue of 5: 85 of 1640 requests failed with `ERR_CONNECTION_RESET`, `room.js` among them 26 times; at 128, none of 1923.
- **What it is not.** The cap of 64 connections never answered (its counter stayed 0), no handler raised, the slowest request took 71 ms, at most 22 threads ran at once; a file of the page passes no lockout and no rate limit (`do_GET` serves it before any of the API's checks); the harness serves the same class as the box. Asking for keep-alive changes nothing, the server closes every connection.
- **What is not known.** Only macOS was measured, on loopback. There the kernel resets a connection that does not fit, so the browser fails at once. Linux by default (`tcp_abort_on_overflow=0`) drops the handshake and the client asks again after about a second: on the box the same overrun would be a file that arrives a second late, not a missing one. That is how Linux is documented to behave; nobody measured it on the Pi.

What was decided:

- **`PvjServer.request_queue_size = 128`.** The traditional largest value: macOS grants no more (`kern.ipc.somaxconn`), and a Linux kernel lowers a larger request to its own limit (`net.core.somaxconn`, 4096 on today's kernels, 128 on old ones). Twice the cap of connections. A waiting connection is a finished handshake in the kernel; it costs this process no thread and no file descriptor until `accept`, and then the cap of 64 decides as before. Nothing else in the server changed: the 10 s read timeout, the 60 s lifetime timer, the cap and its 503.
- **The bounds, which the queue does not move.** Threads: two for each of at most 64 connections (the handler and its lifetime timer), plus the fixed ones. Descriptors: one for each of those connections and the files a handler has open, far under the 1024 a service gets by default. `pvj-web.service` sets no `TasksMax`, `LimitNOFILE` or `MemoryMax`; systemd's defaults apply.
- **A hostile device on the LAN, before and after.** Before: 64 connections that say nothing take every place for up to 10 s each (a trickle for up to 60 s), and everyone else gets the 503; it can do that for as long as it likes. After: the same, no more and no less. The queue itself cannot be held by a client, the server takes connections off it without waiting and refuses at the cap. What a longer queue adds for an attacker is 123 more finished handshakes held in kernel memory for the moment until the loop takes them. A flood of half-open connections is the kernel's business in both cases.
- **The page looks after itself: `pvj/web/load.js`.** The first script of the page, in the head. A script or a style sheet of the box whose element reports `error` (no answer, a cut connection, a status that is not 2xx such as the cap's 503) is asked for again in the same place, after 0.4 s and after 1.5 s more, and not a third time. If it still has not come the page says which file is missing, in a notice it draws and styles itself, with a Reload button. A script that arrives (`load`) but leaves nothing behind is a fault of the file, not of the delivery: it is not asked for again and the notice says that it is the panel's fault. Which script leaves what is said in `index.html` (`data-gives="pvjRoom"`). The panel draws itself again when a part arrives late (one line in `app.js`, the event `pvjfile`), and only on a paired page that has already drawn, so nothing is redrawn under somebody typing a PIN.
- **Nothing loads the page again by itself.** A reload would be the simplest repair, but an address that came with a code or a token in it has given that up by then, and a reload that fails the same way is a loop. Reload is a button somebody presses.

Why this way, against what else was weighed:

- *The page loading its own scripts one after another from a list* gives every file a retry in order, but takes the files away from the browser, which asks for all of them at once while it reads the page. On a phone over the venue's Wi-Fi that is four round trips in a row before the panel starts. The tags stay as they are, and the normal case is untouched.
- *An inline script*, which could not fail to arrive apart from the page: the Content-Security-Policy forbids inline script, and a hash for one in the policy would tie a constant in `server.py` to the text of `index.html`. Not worth it for the one case left over (below).
- *Keep-alive (HTTP/1.1)* would cut the number of connections at the root. It also changes what an idle connection is: a browser would hold six places of the 64 for as long as it likes to keep them, and eleven browsers would fill the cap. A change to the protection against idle clients needs its own decision and its own measurements.
- *Waiting at the cap instead of answering 503* would let a burst above 64 through, and would let 64 silent connections stall the loop that takes new ones. The cap was not reached by honest load in any measurement (24 browsers at once, 144 connections asked for, 22 threads at most).

Cost / rules out: one more small file for the page to fetch (it is in the head, so the page waits for it; a few kilobytes). If `load.js` itself is the file that does not arrive, the page is as it was before this decision: at a queue of 5 that was 4 page loads of 90 in Edge; with the longer queue no file failed at all. The notice is in the page's own words and colours, not the theme's, because `app.css` may be the file that is missing. The cap's 503 is often not seen as a 503: the server closes the connection on a request it has not read, and the kernel resets it, so of 2278 refusals at the cap the clients read 760 as 503 and 1510 as a cut connection (measured with 72 silent connections holding the places). The page treats both alike. That is older than this change and is left as it is.

## D69. A run of the tests works in a temp folder of its own and removes it; a test does not have to remember

2026-10-08. The tests left about 1,450 folders and 216 MB in the system temp folder at every run, and that filled the development Mac (LESSONS, JOURNAL of the same day). Three ways to mend it were weighed.

- **(a) Mend each line** (`self.addCleanup(shutil.rmtree, ...)` after each of about 120 lines in 46 files). It is the tidiest result and a killed run then leaves almost nothing. But it has to be remembered in every test written from now on, which is exactly what failed; it touches 46 files that three open branches also change; and many of the lines are in helpers outside a test (`make_bundle`, `box`, `make_sysfs`) that have no test to register a cleanup with.
- **(b) One guard for the whole run.** The process gets a folder of its own and it goes at the end. New tests need nothing and three files change. But a run that is killed leaves everything it made until some later run sweeps it, and the big folders stay for the whole ten minutes of a run.
- **(c) Both: the guard, and the few lines that make nearly all the bytes mended where they are.** Chosen. Seven lines in five files were 97 percent of the bytes (the copies of the source in `test_install` and `test_update`, the panel folder of `ServerBase`, the USB folder, the mapper's run folder).

What was decided:

- **`tests/tmpguard.py`, started by `tests/__init__.py`.** It makes `<temp folder>/pvj-t-XXXXXX`, writes a marker file into it (who made it, the process number), and points `TMPDIR` and `tempfile.tempdir` at it, so that `tempfile` in the tests and every program they start (mpv, shells, the helpers) work inside it. It is removed at exit, and on SIGTERM and SIGHUP where nobody else handles those (then the process dies of the signal as before, with the same exit status).
- **`tests/test_000_tmp.py` is the first test module by name and imports the package**, because `python3 -m unittest discover -s tests` does not import `tests/__init__.py` by itself. No `sitecustomize`, no wrapper script: the three ways the tests are run (that command, CI's `-t .`, `python -m tests.test_shaders_gpu`) and a single `python3 -m unittest tests.test_x` all work unchanged.
- **A Python that a test starts uses its parent's folder** (it finds `PVJ_TEST_TMP`) and only the process that made a folder removes it, so a child never takes the folder from under its parent. The folder named there is used only while the process that made it is alive: a variable left over from a dead run names a folder the next sweep removes.
- **A killed run is swept by a later one**, from any checkout (agents' worktrees are deleted, so "the same checkout" would never come back): a folder whose process is gone and whose marker is over two hours old (two days if it was kept on purpose). Two hours because CI ends a run after twenty minutes and a process in another container looks gone from here; so two runs at the same time never touch each other. **A folder whose process number is in use is left for fourteen days.** A number alone cannot tell a run that was paused for days (or a clock that jumped) from a number given out again to another program. Comparing the process's start time with the marker would tell them apart, but there is no one cheap way to read it (`/proc` on Linux, a `ps` or a system call through `ctypes` on macOS), and a sweep that starts programs or differs by system is more to go wrong than a folder that waits two weeks.
- **The sweep and the removal never stop a run.** Two runs that start together find the same old folder; the second finds it gone halfway. Everything the file system can do there is caught, and one folder that cannot be dealt with does not keep the next from being looked at.
- **Nothing is removed that is not provably the suite's**: a real folder, not a link, directly in the temp folder, named `pvj-t-*`, owned by the user, holding the marker with the suite's own text in it (a regular file, read through a handle that does not follow a link). The marker is the proof; the name only says where to look. Never `tmp*`. Links inside are removed, not followed, and the mode of what a link points to is never changed. Something on another device (a mount) inside the folder is left.
- **`PVJ_KEEP_TMP=1` keeps the folder** and prints its path, for two days after its process has gone.
- **The folder's name is short on purpose** (`pvj-t-` and six characters, 13 bytes with its slash). A socket's path may be 103 bytes on macOS, the Mac's temp folder takes 49, and tests put sockets in temp folders: the longest is then 89. A test says in plain words when the temp folder is too long for them.
- **The workflow file is not changed.** The check that a run leaves nothing is in the suite (`tests/test_000_tmp.py` runs a few modules in each of the ways above with `TMPDIR` in an empty folder and names what is left), so it runs on a desk too, where the disk is the one that fills; a CI runner is thrown away.

The rule for a new test: make temp files with `tempfile` and nothing more. If a folder has to be somewhere else (`dir="/tmp"` for a short socket path), the same function registers `self.addCleanup(shutil.rmtree, folder, True)` after it (or `addClassCleanup`, `addModuleCleanup`), naming the folder, and a test that reads the test files' syntax fails without it. If a test makes something big (a copy of a tree, megabytes), remove it in the test as well, so a killed run leaves little. To run one module, `python3 -m unittest tests.test_x`.

What it costs and what it does not do: about fourteen seconds more per run for the 26 tests that keep it. Those tests show that the run's folder goes and that nothing lands beside it; they do not show that the big sites stay mended (a new copy of a tree without a cleanup would only make a killed run's leftover bigger). Every path in a temp folder is 13 bytes longer, so a `TMPDIR` of more than about 60 bytes breaks the socket tests on macOS (and the test for it says so first). The rule about `dir=` cannot know where a `dir=` points: it asks for a cleanup for every one, also for one inside the run's folder. `discover -s tests -p one_file.py` loads neither the package nor the first module, so such a run is not guarded unless that file imports from `tests`. A program started with an environment that has no `TMPDIR` writes where it likes. SIGKILL and SIGABRT leave the folder until a later run. `tests/ui/harness.py` gets its folder the same way; that was not run (no mpv or Playwright on the Mac). Measured on the Mac only: the numbers are in the JOURNAL.

## D70. What a power cut leaves on the box is removed the next time; the updater has one lock and one place to work

2026-10-08. Found while looking for what filled the development Mac (D69, in pull request #106): the same habit in the product, a temp file beside the thing it will become, removed in a `finally` that a power cut never reaches. An independent review confirmed all five on master. A box is switched off at the wall every night in some venues, so "rare" is not never, and the largest of them is an update's work folder: the bundle and its unpacked tree, up to 300 MB each time, on a card that also holds the media.

What was decided:

- **The updater's work folder (`.update-XXXXXXXX` in the install) is removed by the next updater that holds the lock.** `main()` calls `Updater.sweep_scratch()` right after `take_lock()` succeeds, for the commands that take the lock (`check`, `apply`, `usb`, `inbox`, `rollback`). Holding the lock is the proof that no update is using such a folder. Only a real folder directly in the install, named exactly as `tempfile.mkdtemp(prefix=".update-")` names one, owned by root, is removed; a link named so is neither followed nor removed; and a sweep that fails is a line in the log, never a reason not to update. The install folder itself is resolved first and opened, and has to be a real folder of root's that neither its group nor anybody else can write, or nothing is swept. Each work folder is then opened through that descriptor without following a link, looked at through what was opened, emptied bottom up through descriptors (`os.fwalk` with `dir_fd`; a link inside is unlinked, never entered) and removed by its name in the opened install: no path is resolved a second time between the look and the removal (second review of #108; it was `rmtree` on a path, with a re-check before it that narrowed the gap and did not close it). A folder that cannot be emptied is left for the next time. So an install that is a link is swept where it really is, which is where `check()` makes the folder. `check` from a terminal takes the lock and sweeps like the others, because it makes a work folder too (both changed after the review of #108: `check` took no lock, so the proof above was not true, and a linked install was swept by nobody).
- **There is one lock file, and whoever cannot use it does not update.** `take_lock()` used to fall back to `pvj-update.lock` in the caller's own temp folder when `/run/lock/pvj-update.lock` could not be opened, so two updaters that fell back differently (or one of two) held different locks and both ran. Now there is no fallback: it raises `UpdateError`, and `main()` prints it, writes it to the result file as a failed update (the panel has already answered "started" and reads its reason there) and ends with 1. Where the lock is held and the result file says "running", the file is the running update's and is left alone; where it says anything else or is not there, the lock is held by something that writes no result (a `check` from a terminal) and the result becomes a failed update with "another update or check is running" (second review of #108). The same for root and for anybody else: a developer or a test names a file with `PVJ_UPDATE_LOCK`, as the tests already did.
- **The lock is `/run/pvj-update/update.lock`, in a folder only root can write** (changed after the review of #108; it was `/run/lock/pvj-update.lock`). `/run/lock` is world-writable with the sticky bit on Debian, so any account, the player's included, could put a link, a folder or a file of its own at the lock's name: that refused every update until a restart, and with `fs.protected_regular` off it could let two updaters run, the sweep of one removing the other's tree. `/run/pvj-update` is the update units' own `RuntimeDirectory` (root:root 0755, kept between runs); from a terminal before any unit ran, `take_lock()` makes it with that mode whatever the umask. What is opened is looked at: the folder has to belong to the effective user (root on a box) and may not be writable by its group or by others, and the lock has to be a plain file of the same user with one name, or there is no update. For a desk this means that `sudo pvj-update` with `PVJ_UPDATE_LOCK` in one's own folder is refused; the folder has to be root's then. **The old name is still taken, best effort**, only where the lock is the default one: an updater from before the move holds only the old name, so during the update that replaces the one by the other, and after a rollback to the older release, the two would otherwise not see each other. The old name counts only if it is a plain file of root's with one name (which only root can hold); a link, a folder, somebody else's file or no `/run/lock` at all is passed over and never stops an update, and `/run/lock` is never made (it used to be made with mode 755 where it was missing). If the old name is held, another update is running.
- **The work folder is in the install, or there is no update.** `check()` took the system temp folder when the install's folder did not exist, and measured the free space there: on a box `/tmp` is small or in memory, so an unpacked bundle could have filled the RAM. Now the install's folder is made (mode 755, as `install.sh` makes it a moment later with `mkdir -p`; a first install through the updater is something the tests do), and if it or the work folder cannot be made the update is refused with the reason. The free-space check therefore always measures the disk the release goes to.
- **A save of the settings: `.settings-XXXXXXXX` older than an hour is removed when settings are loaded.** Only old ones. Only the panel loads that folder (`pvj/server.py` is the one place that makes a `Settings`; this entry first said "several services", which was wrong), so nothing should be saving while it starts: the hour is caution, for a second panel started by hand, and costs nothing. A file dated more than an hour ahead of the clock is old as well: a Pi has no clock of its own, and started without a time source it believes an earlier time than its files carry. A file less than an hour ahead is kept and goes once the clock has caught up; a box that never has a time source and whose clock starts at the same value every time cannot tell the age of a file cut off in its first hour, and keeps it. Never `settings.json`, its `.bak` or anything else: the name has to match what `mkstemp` makes, whole.
- **A shader or an effect being uploaded (`.upload-<process>-<thread>`) and a theme being added (`.adding-<process>-<thread>`) are removed when the library is built**, which is the panel starting, when nothing can be uploading yet. They never counted toward the limits (64 uploads, 16 themes): the libraries list only names that begin with a letter or a digit.
- **One helper, `paths.remove_leftovers(folder, pattern, older_than)`**, for the last two: it opens the folder without following a link, and looks at and removes each name through that handle; only a regular file whose whole name matches; never raises.

Every safety check the updater had is still there (links not followed, regular files only, sizes bounded, signature, version, the inbox emptied): the diff of `pvj/update.py` adds and does not remove, except the fallback itself.

Cost and what was not done: an update on a box where the lock cannot be used now fails, with the reason in the panel, where it used to run unlocked. `pvj-update check` is refused while an update runs. An install folder that its group or others can write is not swept (`install.sh` gives the install to root and takes write away from group and others, `chown -R root:root` and `chmod -R go-w`, on every install). The old lock name is best effort by design: where a planted file makes it unusable, an updater from before the move and one from after are not excluded from each other, for as long as both exist on a box, which is the one update that brings this in and a rollback from it. A work folder left by a power cut stays until the next update or rollback, not until the next start: only the updater runs as root, and nothing was added to run at boot. **None of this was tried on a box**; it was run on the development Mac (where the installer's own tests cannot run) and in CI.

## D71. A crossfade is a still of the screen, laid over the new clip as the player's overlay and taken away by the panel; a shader cannot do it on this player
Why: the owner asked for crossfade and other transitions first (2026-10-08). The Mix transition knew "cut" and "dip". The project's own note (`pvj/SHADERS.md`, "What would unlock the rest", row 2) proposed a still of the outgoing picture as a `//!TEXTURE` block in a shader, the incoming clip live, and a progress value driven by time, and marked it unverified. It was put to the test before any design, on a throwaway branch (`transitions-spike`, two rounds, the three `effects-gpu` jobs: OpenGL ES 3.2, desktop OpenGL 4.5 core, desktop OpenGL 3.1 with GLSL 1.40; mpv 0.37.0, FFmpeg 6.1.1, Mesa 25.2.8 llvmpipe, a 1280 x 720 window). **Everything below is a software GPU on a CI machine. Nothing was run on hardware.** The three ways of drawing agreed on every answer; where numbers differ they are given as a range.

**What the spike answered.**

1. *Which still?* None gives the picture with the effect and without the mapping. `screenshot-to-file` in the modes `video` and `subtitles` gives the clip's own size (320 x 180 for such a clip, 90 x 160 for a tall one) and holds a shader hooked at MAIN (the effect's side), a shader hooked at OUTPUT (where the mapping is: a mirror there came out mirrored) and the brightness (a picture at brightness -30 came out darker by 30 of 100). Neither holds an overlay. `window` gives the window's size and everything, overlays too. So a still fed back in before the mapping would be warped twice, and before the brightness dimmed twice.
2. *What a still costs as a texture.* A `video` screenshot of a 1920 x 1080 clip as a PNG with no compression and no row filter: 69 to 83 ms, 6.2 MB; with compression 1: 79 to 122 ms, 1.3 MB; as a JPEG, which the standard library cannot read: 41 to 81 ms. Reading it in Python (zlib, then slices; no arithmetic): 1.3 to 1.5 ms. As hex text in a shader file: 1920 x 1080 RGBA 16.6 MB, written in 7.7 to 9.4 ms, drawn 431 to 457 ms after it was set; 960 x 540: 4.1 MB, 1.2 to 1.8 ms, 60 to 87 ms; 640 x 360: 1.8 MB, 0.6 to 0.9 ms, 56 to 72 ms. `rgb8` is taken in all three (3.1 MB at 960 x 540). There is no other way to hand a picture to a shader on `--vo=gpu`.
3. *A clock.* mpv's `frame` counts every frame drawn (26 in a second of a 25 a second clip, 32 at 30). It stands still while the clip is frozen, and over a still picture (also after the shader was exchanged). It never starts again: not at a seek, a `loadfile` (same size or another), a new shader text, a new `fbo-format`. A screenshot does not move it. Nothing outside the shader can read it (`pvj/effects.py` said so already). So the start cannot be a constant in the file, and over a picture or a frozen clip nothing would move at all. Progress as a new text per step: 65 to 102 ms a step here with a 960 x 540 still (377 to 408 ms with a 640 x 360 one, for a reason not looked into), and on a Pi 4 a new text was drawn 0.05 to 0.37 seconds after it was asked for (measured for the effects and the generators, 2026-10-05): three to five steps a second.
4. *Stage and order.* A blend hooked at MAINPRESUB, MAIN, SCALED or OUTPUT is not darkened by the brightness (half red stayed (50, 0, 0) at brightness -100): Blackout would not cover it. Only at NATIVE is it (black), where a video is YUV and the text would have to convert as an effect's does, for a clip that has not loaded yet. A shader at OUTPUT comes after it whichever is listed first. A generator at NATIVE followed by a blend works. And a hook draws only where the incoming picture is: a still over a tall clip was squeezed into the clip's 405 pixels with black beside it.
5. *Between `loadfile` and the first frame* the last frame stays on the screen: 37 to 64 ms for a clip that loads at once, and for a pipe nobody wrote into the old picture stayed for the whole 1.5 seconds, with the player answering all the while. No black frame was seen. `time-pos` is not a sign of the first frame (it reads 0.0 while the pipe is waited for); `seeking` is true until the first frame and false from it on, in all three.

And for the overlay (round 2, a still of the whole window): the mix is a plain one (at 191, 128, 64 and 13 of 255 the middle of the screen was within 1 of the mix worked out by hand); the player keeps its own copy of the bytes (the file rewritten without a new command changed nothing; the manual says so since 0.18.1); a higher overlay number is drawn on top (63 over the logo's 10); **the brightness does not reach it** (an opaque still under brightness -100 stayed as it was); it is drawn anew at every command over a frozen clip and over a still picture; a mirror at OUTPUT does not turn it; mpv writes a screenshot into a file that exists in a folder it may not create files in (the same file, no temp name beside it). A window screenshot of 1280 x 720 as a plain PNG: 32 to 58 ms, 2.8 MB. One step (scale the bytes, write the file, the command): 5 to 14 ms at 1280 x 720, 12 to 33 ms at 1920 x 1080. One second at twenty steps a second over a playing clip: 20 steps at 1280 x 720 with nothing dropped; with stills larger than the window, 15 to 20 at 1920 x 1080 and 5 to 20 at 2560 x 1440, the runners differing. `overlay-add` with a display size (`dw`, `dh`: a small still scaled up by the player) is **refused by mpv 0.37** ("invalid parameter"); mpv 0.40's manual has it.

**The candidates.**

- *A still as a texture in a shader, progress from the clock* (the note's proposal): dropped. No clock (3), the still is warped and dimmed twice or is not covered by Blackout (1, 4), it has the wrong shape over a clip of another shape and is not drawn while nothing plays (4), and its text depends on a clip that has not loaded.
- *The same with a new text at every step*: dropped. Three to five steps a second on a Pi 4, each one a renderer set up anew under the incoming clip.
- *mpv's `--lavfi-complex` with two inputs*, both pictures moving: dropped without a measurement. It blends in software (a mirror alone costs about half a core on a Pi 4 at 1080p, `Player.flip`), it needs both clips decoded at once, changing it starts playback again, the box runs with `--hwdec=auto-safe` whose frames a software filter cannot take, and a pipe or a generator cannot be its second input.
- *A second player*: dropped. On the box the player draws through `--gpu-context=drm`, and one process owns the display.
- *A still as the player's overlay with changing alpha*: **chosen.** The still of the window is the screen itself: the effect, the mapping, the opacity, the size and the logo are in it once, it is drawn after all of them, it covers the screen whatever the new clip's shape, and it is the same call the pairing codes and the logo already use on the box. The panel owns the clock, so the start is the new clip's first frame and a picture or a frozen clip is no special case. Nothing in the renderer is set up anew.

**What is built** (`pvj/transitions.py`; `Player.still`; `Api.play`).

- **Crossfade** is a third value of the Mix transition, with the same duration. At a play of a file or a pad: the outgoing clip is frozen (the still takes time, and a clip that played on would jump back to it), the player saves the window into a file the panel made in its own folder, the panel reads it (only an 8-bit PNG of exactly the screen's size with plain rows, and no more is unpacked than that holds) and gives it to the player as overlay 63. The clip is loaded under it. A thread waits until `seeking` is false (ten seconds at most), then sends the still again twenty times a second by the clock with every byte scaled (`bytes.translate`), and removes it. **The outgoing picture stands still for the length of the transition.**
- **It ends at once**, the still gone and the new clip there, on Blackout, Fade out, Fade in, an opacity change, Reset, Stop, any other way of playing (a list, a stream, a live input, the test pattern, a tone, a sync client's clip), a generator taking the screen, a change of the mapping and a player restart from the panel. All but the last three go through `Api._settle()`. An effect changed during it changes the clip under the still and nothing else.
- **A second play during one** takes its still of the screen as it is, the half-faded picture included, and the first stops.
- **Not started**: with the screen dark (Blackout, opacity 0, the operator's Fade out), as the dip skips itself there, and with nothing loaded in the player (after Stop, at power-up: on a box the player always runs, and takes no screenshot then); the clip starts as with a cut.
- **A Blackout while the still is being taken** darkens the picture first and ends the transition after; the still, which is not on the screen yet, sees the end and is not laid down.
- **A player that crashes or is restarted**: the still was the old player's and went with it. Every step asks the player its process number first and stops if it is another. The file goes in a `finally`.
- **The panel restarted during one**: the new panel removes overlay 63 and any `transition-<n>.png` and `overlay-63.bgra` in its folder when it starts (`Transitions.tidy`, D70's rule).
- **No still file stays.** The screenshot is unlinked as soon as it is read; the overlay's file goes with `overlay_remove`. Both are in the panel's folder, not the player's, so the panel can remove them: both units run in group `pvj` with umask 0007, the panel makes the screenshot's file (0660) before the player writes into it, and the player's unit has no sandbox that would stop it. **That the player on a box can write there was not tried**: in CI both are one account in one folder. If it cannot, every crossfade is a cut and the journal says so (check X2).
- **Vibes** keeps its own dip between shaders; it never looked at the transition's name. **A sync client** cuts, as it does under a dip: its clips come through `_start_list`. (It stands still with the server for the moment of the still, because the server says it is paused.) **Autostart and the schedule** go through `Api.play` and get the transition if something plays. **OSC, MIDI and DMX** cannot choose a transition, so nothing changed there.
- **The limits, and what the box does at them.** A screen above 2560 x 1440: dip. A still that took more than 1 second (the screenshot and the reading): that transition runs, and the box dips from then on. Fewer than 5 steps a second, or more than 5 frames a second dropped by the clip under the steps: the same. `GET /api/status` gives the reason as `mix.fallback`; choosing the transition again lets the box try again. While an access code is on the display: dip (its pixels would go into the still). A still that fails (no reply, a file that is not the screen): a cut. A step that is late is left out; the transition is never longer than asked. **These numbers were set without a board**; they are the first thing to revisit on the Pi.
- **Settings and rollback.** `pvj/settings.py` never looked at `mix`. The release before this one plays any value but "dip" as a cut, but its `set_mix` and its import refuse any value but "cut" and "dip", and the panel sends the transition's name along with every change of the duration. So the file keeps `"transition": "dip"` and names the newer one beside it: `"style": "crossfade"`. An older release reads a dip and never sees `style`. The key stays in the file there, unread, through every other save, and goes when somebody there saves the transition or its duration or imports a settings file: those write `mix` anew without it. The API takes and gives `"crossfade"`. An import takes `style`; one it does not know (a file from a newer release) is left out with a note. No schema change.
- **Other transitions** are another class beside `Crossfade` with the same `step`: what to draw of the still at this moment. See "The wipes and the slides" below.

Cost and what was not done:

- **Not run on hardware.** Not known: how long a Pi 4 takes for the still (a JPEG screenshot of 2560 x 1440 took about 0.7 seconds there; this is a plain PNG of 11 MB plus the reading), how many steps a second it makes at 8.3 MB (1920 x 1080) and 14.7 MB (2560 x 1440) a step, whether the incoming clip drops frames meanwhile, and whether `bytes.translate` on that much, which holds Python's lock, is felt by the MIDI and HTTP threads. On the owner's 2560 x 1440 rig the box may give up at its first crossfade and dip from then on. The check list is "Crossfade (D71)" in `tools/DEVICE-TESTING.md`.
- The fade is in steps by the panel's clock (twenty a second asked for), not a value per frame.
- The outgoing sound stops at the tap, where a dip lets it run for half the duration.
- The still holds a logo once and is drawn over it: right. A pairing code is kept out by dipping.
- The scaled overlay (`dw`, `dh`), which would let a Pi send a quarter of the bytes or less, is **not built**: CI's mpv refuses it, so it could not be tested, and a still drawn at a quarter of the screen would be the first thing the owner saw. Try on the Pi (mpv 0.40) first.
- Lists, slideshows, streams, live inputs and the test pattern still start with a cut, and the clips inside a playlist follow each other with a cut (the player changes those by itself).
- **ISF transition files (68 in the survey) stay out of reach on `--vo=gpu`**: they need both pictures and a progress value inside one shader. mpv's `gpu-next` output gives a shader values from outside (`//!PARAM`, D46), which would give `progress`; the still's stage and shape (1, 4) would still stand in the way. Moving the output is its own decision.
- The spike branch `transitions-spike` is left for the owner to delete.

**After the review of #111** (an independent read; no high finding, six medium, some low; all answered on the same branch, each with a test that fails without its fix).

- **Nothing waits behind a still.** `end()` took the lock a still was taken under, so Stop, Fade out, the Opacity slider and the rest waited for the screenshot (Blackout had been reordered, the others not), up to several timeouts if the player stopped answering. Now there are three locks with three jobs (`Transitions`' docstring): one still at a time; one overlay command at a time; and a mark. `end()` sets the mark and returns after at most one overlay command. The still that was being taken looks at the mark before it lays anything down and again under the overlay's lock, and is dropped. **A Stop that came while the still was taken is the newer wish: the clip is not loaded after it** (`Transitions.stops`, looked at by `Api.play`). After a Blackout, a fade or an opacity change the clip still plays, without the blend.
- **A controller's play does not hold its own Blackout back.** MIDI, OSC, DMX and a Room scene each run their calls one after the other on one thread, so a pad's play that waited for its still held the same controller's next action behind it. For those callers (`api.CONTROLLERS`) the still and the clip are another thread's, and the call answers at once, as a play under a dip always has. A clip that then does not start is a line in the journal, not an answer to the controller. MIDI itself is unchanged. A play from the panel still waits and still hears of a clip that does not start.
- **A hold has its own token.** `hold()` returns it and `run(token, ...)` does nothing if another play or an `end()` came since. Before, `run()` took whatever token was current, so two plays close together could start two workers on one still, sending different alpha in turn.
- **Every failure is cleaned up.** `hold()` caught three kinds of exception; a still file cut inside its header (`struct.error`) or a `MemoryError` left the clip frozen and answered 500. Now any exception there, and any between a good still and its steps in `Api.play`, takes the still off and lets the old clip play on. A file cut anywhere is a `StillError`.
- **A still or a step that fails makes the box give up**, with the reason in `mix.fallback`: before, a still slower than the player's two-second answer time, or one that failed every time, froze and cut at every play and never reached the documented dip. Not when an `end()` was the cause, and not when the player went away or was restarted (that is not the box being slow).
- **The clock for "the still took too long" starts after the still's turn came**, not while it waited behind another play's still: a double tap could make the box give up for the rest of a show.
- **Memory.** Reading the still held about five times the picture at its end (the file, its parts, the joined parts, the rows, the rows without their first bytes, the result and a copy of it). Now the file goes before the result is made and the rows are copied into it through a view: 2.3 times the picture at most by `tracemalloc`, about 34 MB for 2560 x 1440. The crossfade's `bytes.translate` of the whole still at every step is as it was (the wipes and slides have none); what it does to the other threads on a Pi is not measured.
- **Lows.** A clip the operator froze after a good crossfade is no longer unfrozen by a later play that fails. A status request asks the player nothing (`fallback()` reads what the last play saw; `look()` asks). An access code that comes up while the still is taken: the still is not laid down (it is looked for a second time after the screenshot; the file with its pixels is unlinked at once either way).
- **Open, recorded and not fixed.** A panel that dies between freezing the outgoing clip and loading the new one leaves the player frozen until the next play (every way of playing unfreezes); the new panel does not know whether an operator froze it, so it does not touch it. Two panels started by hand in one runtime folder on a desk would take each other's still away at start; a box has one. Whether mpv answers a Stop or a Blackout *while it takes a screenshot* is the player's own matter and can only be seen on a board.

**The wipes and the slides** (the owner asked for "crossfade and other transitions"; built after the review's fixes, as separate commits).

- **What.** Eight more names: `wipe-from-left`, `wipe-from-right`, `wipe-from-top`, `wipe-from-bottom` (the still stays where it is and is cut away on the side the new picture comes in from) and `slide-left`, `slide-right`, `slide-up`, `slide-down` (the still moves off that way and uncovers the new clip). A slide is not a push: the new clip cannot be moved, it is the player's picture.
- **How.** `overlay-add` takes a file, an offset in bytes, a width, a height and a stride. With the stride of the whole still, an offset and a smaller size name any rectangle of it; the position says where it is drawn. So the still's bytes are written into a file once (`transition-<pid>.bgra` in the panel's folder, by a rename, removed with the still, swept at start), and a step is one command that names a part (`class Move`, `Player.overlay_part`). No negative position is needed: a slide to the left draws the still's right part at 0. The file is one row longer than the picture, because the player maps the offset plus the height in whole rows, and a part that begins in the middle of a row would end past the file otherwise.
- **Cost.** Nothing is rewritten and nothing is worked out in Python at a step; the player copies the part that is still to be seen, which shrinks to nothing. Thirty steps a second are asked for (an edge that jumps shows more than a level of alpha does). The still itself costs what the crossfade's costs, and the same limits and the same giving up apply.
- **mpv 0.37 against 0.40.** The arguments used here are the same in both manuals. 0.40 adds a display size (`dw`, `dh`), not used. CI ran these on 0.37 only.
- **Stored** as the crossfade is: `transition: "dip"` with `style: "<name>"`. An older release reads a dip.

- **A generator after a live input: the player goes by what it loaded, and by mpv's word, both.** `Player._play_pipe` does not wait for mpv's `path` to follow the load, and `Player.play_source` decided "the carrier already plays" from `path` alone. The record is the one the player already had (`_carrier`, cleared by every other load, by the clear and by the restart, and tied to the process by `_source_pid`); the carrier is now left alone only if **the record and `path` agree**. ## D74. An effect goes on over a generator shader: the generator first in the player's list, the effect filtering what it drew

**The spike, before any design** (run 37943294827, the three `effects-gpu` jobs, mpv 0.37, Mesa's software GPU, a 320 x 180 window; `tests/test_pair_gpu.py` at the branch's first commit handed both texts to the player through its socket with nothing in `pvj/` changed). All three ways of drawing agreed on every answer:

1. *Is it the effect of the generator's picture?* Yes. An invert over a gradient generator is the exact negative of the generator alone (largest difference 0 of 255), the right way up, half way at Amount 0.5, and the generator itself at Amount 0, where the effect's pass is not drawn.
2. *Which hook, and what decides the order?* Both hook NATIVE. The order of `glsl-shaders` decides: generator then effect is the negative; effect then generator is the generator alone, since it draws over what the effect made. Of the effect's two hooks the one for RGB runs (the carrier is `rgb0`), the one for LUMA is left out.
3. *Do the carrier and the effect's sampling meet?* The effect meets the generator's drawing: `HOOKED_size` read 321 x 181 for a 320 x 180 generator and 638 x 361 for 640 x 360 (an 8-bit reading, good to 4 pixels). The player's own word about the picture stays the carrier's: 64 x 36, RGB, full range, 30 a second.
4. *Effect detail against Picture detail?* A cap at or above the generator's lines changes nothing: a checkerboard of single pixels came through an effect that changes nothing with a difference of 0, so it is neither scaled twice nor blurred.
