## 2026-11-06, a screen that comes after the player starts brings back pvj-render

- Seen on the test node: it booted with no screen, pvj-render exited 2 ("no screen is connected"), the player fell back to classic mpv (D95), and 80 minutes later, with a screen connected and `renderer.json` saying new, it was still on classic. At a show the Pi boots before the projector warms up, so this is the normal order.
- New `pvj/latescreen.py`. When the fallback is a pvj-render that ended with exit 2 ("did not start (exit 2)", or "ended twice in a row (exit 2)" for a screen that went away while it drew, e.g. a TV switched off at night) and no screen is usable now, the player logs "watching for one" and starts a small detached watcher before it becomes mpv. A screen is usable when its status is connected AND the kernel lists a mode for it: a projector says connected before its EDID is read, and pvj-render takes only a connector with modes (`render/src/out.c`, `pick_connector`), so a switch at "connected" alone would exit 2 again. The watcher reads the connectors through `hardware.drm_connectors` (every card and connector, none named in the code), and when a screen has stayed usable for 3 s it ends the player's process with SIGTERM, but only if the pid still has the start time it was given (a pid reused by something else is never signalled). `Restart=always` starts the service by its normal path, so the mode is chosen as at any start and pvj-render is tried again under the same gate (D105).
- Any other end stays on classic as before: another exit code, a signal, "did not answer", "not built", "could not be started", and exit 2 with a usable screen present. Also not watched: a board whose /sys lists no connector, classic chosen, and a player not run by systemd (no INVOCATION_ID).
- Bounded by a growing wait, with no total: after a switch the next waits 30 s, then 60 s, 120 s, and 300 s from the fourth on, counted from the previous switch. A switch more than 10 minutes old no longer counts (pvj-render has drawn since), so the waits start again. A no-screen fallback is not a crash, so a loose cable only makes the box wait longer and never leaves it on classic for the rest of the boot (the first version stopped after 4). The first switch of a boot has no wait: it comes within a few seconds of the screen settling.
- Where the count lives. The switch times are in `late-screen.json`, keyed by boot id. The player account cannot write /var/lib/pvj (the panel's 2750 folder), and its run folder is removed when the service restarts, so the unit has `StateDirectory=pvj-player/late-screen` (mode 0750), i.e. `/var/lib/pvj-player/late-screen`, named by `paths.player_state_dir()` (env `PVJ_PLAYER_STATE_DIR`). Why a subfolder: `/var/lib/pvj-player` is the player account's home on an install by install.sh, with its own files (.cache and others). Per systemd.exec, a StateDirectory= is created if missing and, when its owner is not the unit's User=, changed to User= and Group= together with what is in it; with `pvj-player/late-screen` that applies to the leaf only. The parent is only created if absent (owned by root, 0755) and its ownership is left alone, so nothing of the home, or of any other service, changes owner. This is from the documentation, not seen on a node (LS4c looks).
- The watcher writes the file when it starts. Only if that fails (an older unit file without the folder, a full disk) does it log that once and keep a floor of 30 s after its own start for every switch, so a count that cannot be kept never allows a quick loop. `RuntimeDirectoryPreserve` is not used. Each switch is logged in plain words, with the next wait.
- Review of f81262a, answered: connected-without-modes (fixed in both the fallback check and the watcher), the killing code untested (the guard, the double fork and what the watcher is handed are now tested with `start_time`, `os.fork` and `os.kill` patched), the exit-code prefix (exactly exit 2 now), a screen lost while pvj-render draws (handled as above), one log line at the watcher's start, and `ServeTest.serve` in `tests/test_renderer.py` reading the real /sys and starting a real watcher (both patched there). The unit-file point (StateDirectory on the home) is answered above.
