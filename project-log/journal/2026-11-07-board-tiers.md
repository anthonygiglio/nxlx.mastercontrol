## 2026-11-07, Board tiers: Pi models named by their silicon, and no failed starts of the New renderer on a Pi 3

- The board kind came from the regex `Raspberry Pi (\d+)`, so a Pi 400, a Compute Module 4 or 5, a Pi 500, a Pi 2 and a Zero 2 W all became pi-other, which takes the heavy-machine path (full detail, no `--fast`, the careful-but-unmeasured effects table). `pvj/hardware.py` now names them by silicon: Pi 400, Compute Module 4 and 4S are pi4; Pi 500 and Compute Module 5 are pi5; Pi 2, Pi 3 (A+, B+), Compute Module 3 and Zero 2 W are pi3. A Pi 1, a Zero (not 2) and a Compute Module 1 stay pi-other, below the supported floor. The exact model string is unchanged in the board info.
- A small `hardware.tier(kind)` returns lean (pi3), standard (pi4), full (pi5, x86) or unknown (pi-other, arm-other). Nothing reads it yet except the renderer check below; later work builds the profile table on it.
- Callers of the kind were each checked: SMALL_BOARDS and the sources, detail and final tables in `renderer.py`, `shaderlive.AUTO_BOARDS` (the measured 540-line table is a pi4 table, right for a Pi 400 and a Compute Module 4), `shaders.py` heights, `effects.AUTO`, `probe.advice`, `modules` support, `rootfs`, `boxcare`, `api.py`. Each wants the corrected kind. Values for pi4, pi5 and x86 are unchanged.
- `renderer.chosen()` now returns classic at once on a lean board, with a plain reason the Renderer card shows: pvj-render needs OpenGL ES 3 and the Pi 3's graphics chip has version 2 (`render/src/out.c`), where before it burned two failed starts. The Owner's choice of New stays saved, so a card moved to a Pi 4 uses it.
- Tests: every model string through a fake device tree, the tiers, chosen() for a lean board and the others, and the argv of a Pi 400 and a Compute Module 4 byte for byte the Pi 4's. Device rows added to tools/DEVICE-TESTING.md: the real Pi 3B and the Pi 4 regression.
