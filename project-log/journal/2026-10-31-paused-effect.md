## 2026-10-31, an effect over a paused clip (D115)

- **The claim.** HANDOFF said an effect put on a paused clip is not drawn until the next frame, the request waits 4 seconds, and the panel's snapshot shows it anyway (item 2 of "Found" in the effects run on the Pi). I checked it on both paths before changing anything.
- **New renderer: already right.** With pvj-render built with the test hooks and a 3 second clip paused, an invert put into the effect slot changed the capture after 0.033 s, a change of amount after 0.017 s, and taking it off after 0.018 s, the clip still paused. The renderer draws a program again whenever its values or its slot change (`fx_source` in `render/src/fx.c`: `dirty` and a slot that has not run yet), whether or not the clip moves. The panel does not watch the log on that path (it takes the renderer's own verdict), so there is no 4 second wait either. Nothing to change there.
- **Classic mpv: the claim holds, on mpv 0.41 here as well as on 0.40.** Probe: a real mpv on the GPU output, paused, then `glsl-shaders` set. The player's list of passes for the last picture (`vo-passes`, "fresh") had no user shader; only "redraw cached frame". An exact seek of nothing (`seek 0 relative+exact`) put the user shader into the list, and over a real file kept the position (7.5 s before and after). A frame step moved the position by one frame and a frame back step moved it back, so the seek is the cheaper cure. On a live lavfi source the seek moves the clock, which a real file does not.
- **The 4 seconds.** `_watch` in `pvj/shaders.py` waits up to `VERIFY_SECONDS` for a pass that took time. Measured on the unfixed code over a frozen clip: the request took 4.4 s. After the redraw the pass is listed but mpv gives it no time however often the picture is drawn (four more seeks in a row: still 0), so waiting a second for a time cannot end well. Over a frozen clip `_watch` now stops as soon as the pass is listed and answers "unknown", as it does for a GPU that reports no times. A compile error is in the log by then and is still read.
- **Fixed.** `Player._push_shaders` (classic only) asks `Player.redraw_paused` after it sets the list: if `pause` is true, an exact seek of nothing; a refusal (a picture, a live input) is ignored. That covers an effect going on, new values (a swap), coming off, the mapping's list and a generator.
- **Tests.** `tests/test_effects.py` `PlayerLayerTest`: two (the seek follows each of put, swap and clear over a paused clip and not over a playing one; a refused seek changes nothing). `tests/test_effects_gpu.py`: `test_an_effect_over_a_frozen_clip_is_drawn_when_it_goes_on_changes_and_comes_off`, on a real mpv in the existing GLES and desktop GL jobs, reading the player's own pass list and not a snapshot (a snapshot renders the frame anew and says the effect is there whatever the screen holds). It failed on the old code (the put took 4.4 s) and passes now (2.6 s for the whole test); I ran the GLES form here on the WSL display with Mesa's software GPU; the desktop GL form, the one the Pi uses, is CI's. The suites for effects, shaders, player, transitions, mapper, shader engine and pads pass here.
- **Found on the way.** The classic GPU tests' frozen-clip pictures are still snapshots; they prove less than they seem to, as the earlier run said, and this test is the one that reads the pass list.
- **Open.** Nobody has looked at a real screen. Row PC1 to PC3 of `tools/DEVICE-TESTING.md`. An exact seek decodes from the last keyframe, so over a long GOP at 1080p on a Pi 4 the redraw may take longer than a frame; not measured. The effect's `checked` stays null over a frozen clip (no pass time exists to check).
