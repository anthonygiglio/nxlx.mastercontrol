## 2026-11-16, second review of 302

- Decision (coordinator): no node is at the state between rename steps 7 and 8, so install.sh no longer carries out a second pass. On a node that has the new folders and accounts it asks the converter (`nxlx-convert --plan`: "Changes (0)" or not) and, when the converter would still rewrite something, stops with a plain message before any change (so before the same-version in-place replace, which fixes the wrong "nothing was changed"). The installer and the converter cannot disagree any more: `pvj-release-2026` and `MYPVJ_FOO` are left alone by the converter and by the installer. The `--prefix` message now says what is the case (old names, or a conversion not finished). Settings written after `--signer` stay in the one NXLX_ line (tested on a fresh node, twice).
- The converter still does a second pass by hand and says so in plan, run and undo: an undo puts back variable names this release does not read, so the earlier release must be installed again. The journal's start record carries `second_pass`; the "Undone" and "Converted" lines follow it. The "CONVERTED from the old names" line of install.sh only appears for a first conversion or one carried on.
- A partly failed undo (undo-finished with failed > 0) is no boundary for the latest conversion: run, a timed undo that cannot put back the login account (7 changes), `--run`, `--undo` leaves no difference from the old node (it did before: pvj-dev stayed renamed).
- The safety checks look at both names: the player's socket under run/pvj and run/nxlx, the update lock under run/pvj-update, run/lock and run/nxlx-update, the mounts under /media/pvj and /media/nxlx. The USB drives' mount instances (pvj-usb@, nxlx-usb@) are not stopped: their stop unmounts the drive and nothing starts them again; a mounted drive refuses the plan anyway.
- The picture helper's unit named `@NXLX_DIR@/pvj/fonts` as a fallback: the converter takes that name in a fresh install, so the first fresh node said "Changes (1)". The unit now names mctl/fonts only (where the fonts are). New test: a fresh stage install gives "Changes (0)" / "Nothing to convert."
- M2, checked: `nxlx-ndi-runtime install/remove` and the discovery server's setup (mctl/ndisetup.py, mctl/ndiscovery.py) run `systemctl try-restart nxlx-web.service` (and the player) when an owner runs them. The CI real-install job runs them in later steps of the same script, one after the other, never during an installer run, and the installer's own start has no part in them, so they cannot have cancelled the restart in CI. On a node in the field the same cancel could happen if someone sets NDI up while an update installs; the installer's restart is tried a second time, and the update lock keeps updates from running at the same time as each other, not from these commands. Not fixed further (a wait for queued jobs would be a guess without the failing journal).
