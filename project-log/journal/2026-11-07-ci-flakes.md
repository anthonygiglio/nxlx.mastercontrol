## 2026-11-07, four flaky CI tests made reliable

- Each of four tests failed once on a commit that did not touch its code and passed on a rerun. Each had a race in the test, not in the product, and each is fixed by waiting for the thing it checks instead of reading it at a fixed moment. No threshold was loosened and no timeout raised without a reason.
- ShotPaceTest.test_screenshots_do_not_stall_the_screen (tests/test_native_shaders.py): the bound was 0.7 of the quiet rate, taken from one run, and the two rates were taken one after the other (37.6 quiet, 26.0 busy in CI, 0.69). Taking them in turn (five times 1.5 s) did not remove the noise: over 30 runs on a loaded machine, with no stall in the product, the busy rate was 0.64 to 0.97 of the quiet one (median 0.88), and one run in 30 still fell under 0.7. The screenshots' own work takes CPU from a software GPU that already uses all of it, and the machine's load moves while the test runs. A real stall gives 0.26 (15.4 of 60, measured when it was found). The bound is now 0.45, with the data in the test's comment; the rates are still taken in turn.
- GlesEffectTest.test_an_effect_over_a_frozen_clip_is_drawn_when_it_goes_on_changes_and_comes_off (tests/test_effects_gpu.py): after Off the player redraws the frozen frame on its own, after the request has returned, and vo-passes lists the old pass (no count, no samples) until it has. The test read the list once, right after Off. It now reads it until it is empty, for up to 3 s, and still fails if it never is.
- tests/ui/panel.test.js, Try again under the transition card: the test let go of the reason (giveUp = false) before pressing the button, so a status poll in between drew the card without the button and the press waited 30 s; the request wait that nobody awaited then ended the whole run as an unhandled error. The press and the request are now awaited together and the reason is let go of after the press.
- The same unhandled error left the harness and its mpv running, because the run never reached its finally. The harness now turns SIGTERM into an exit so its finally stops mpv, panel.test.js kills the harness on any exit and waits for it, and the harness did not stop mpv on SIGTERM before either, on a passing run too.
- SoundFeedTest.test_a_change_of_rate_ends_the_picture_as_changed_and_the_sound_connection_stays_for_the_next (tests/test_ndi_sound.py): "playing" is the writer's state, while the bytes reach `got` through the test's own reader thread, so the first 400 bytes were read empty. The test now waits for the rate to appear in them. The sibling test with the same read (what_the_sound_source_had_last...) is fixed the same way. The "RuntimeError: bug" earlier in that log is a test of the panel's 500 answer and has nothing to do with it.
- Review of #205: the harness's SIGTERM handler now sets SIGTERM to ignored before it exits, so a second SIGTERM (panel.test.js's exit handler after its 10 s wait) cannot interrupt Player.stop() before its SIGKILL fallback. Also noted and accepted: the 0.45 bound no longer catches a partial stall from a single encoder; 0.7 only caught that on a quiet machine, and the full stall (0.26) is still caught.
