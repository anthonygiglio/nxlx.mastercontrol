## 2026-11-07, Pacing advice for a clip on the screen's rate, and a hidden hardware decoding setting

- `probe.advice(info, board, hz=None)` now adds one plain line on pacing when the screen's real refresh rate is known (`hz`; the API takes it from the mode the player says it uses, and `POST /api/media/info` carries it as `output_hz`). It says only what to expect, as D119 left it (no timing code): 24 and 23.976 on 60 Hz show frames for 3 and 2 refreshes in turn (3:2); 25 (and 24 on 50 Hz, and the like) are shown for 2 or 3 refreshes unevenly; 29.97 on 60.00 Hz (or 30 on 59.94 Hz) slips one frame about every 17 s, with the mode that would make it even; an output that is not a 60 or 50 class mode gets one line for any video clip. The line names the real rate ("At 60.00 Hz ..."). With no rate known (classic player not reporting, a test) the advice is as it was, which the frozen-values test also covers. The panel is untouched: it already shows `advice` as "Note: ..." on the clip's info.
- `renderer.hwdec` (D124), hidden, off by default: `clean` keeps `auto-copy`, `v4l2m2m-copy`, `vaapi-copy`, `nvdec-copy` or `drm-copy` (never `no` or a free word), `command` passes `--hwdec=VALUE` only when set, the supervisor counts it in `_wish_changed`, the Renderer choice keeps it, and the profile shows a row only when set. Copy variants only, as pvj-render has no display parameter. Unmeasured off the Pi 4, where D106's addendum found v4l2m2m-copy did not help.
