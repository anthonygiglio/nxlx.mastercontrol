## 2026-11-18, J-135: the player log without libcuda and pw.conf lines, and the clip's name on decoder warnings

- **The bare libcuda line.** libmpv loads its graphics interops for hardware decoding when it starts, CUDA's among them, and that printed "Cannot load libcuda.so.1" straight to stderr three times at each start (one per core: two video, one text), even with `--hwdec=no`. `mctl-render` (render/src/main.c) now sets `gpu-hwdec-interop=no` on every core before it starts. It only ever asks for copy variants (D124), which need no interop. Checked on WSL (x86, mpv 0.41, FFmpeg 8.0.1, no NVIDIA): 3 lines before, 0 after.
- **The lines through mpv's log.** With `--hwdec=auto-safe` FFmpeg also says "CUDA: Cannot load libcuda.so.1" and "CUDA: Could not dynamically load CUDA" with the module name plain `ffmpeg` (not `ffmpeg/...`; the first version of this change missed it). These two are dropped by module (`ffmpeg` or `ffmpeg/*`) and exact words, only when not `--verbose`. No module is silenced; every other line of the same modules still reaches the log.
- **pw.conf.** libpipewire writes `[E]... pw.conf | ... can't load config client.conf` straight to stderr, not through mpv, so the filter cannot see it (the dead clause was removed). The player's unit sets `PIPEWIRE_DEBUG=0`; the spawn of `mctl-render` (mctl/renderer.py) passes no env, so it inherits the unit's.
- **Not done on purpose.** `--hwdec=auto-safe` was not replaced by a named list for Pi boards: nothing in the repository records which decoder a Pi's mpv really uses for H.264, and a wrong name turns hardware decoding off without a word (the same reason the #80 entry gave).
- **The clip's name.** A line from `ffmpeg`, `ffmpeg/*`, `vd`, `ad`, `demux`, `lavf` or `cplayer` carries the layer's file name in brackets, for example `video 0 ffmpeg/video [clip.mp4]: ...`. The name is read by the event thread when a file starts or loads (not per line), so queued lines keep the name of the file they belong to. It is cut between characters, at 159 bytes; an invalid byte, a control character and `]` become `?`, so a line is always valid UTF-8 (journald keeps one that is not as a blob).
- **Tests.** `tests/test_mctl_render.py` ClipTest: a damaged clip's warning names it; a long accented name is cut between characters and a `]` in it becomes `?`; a good clip logs no bracket; `--hwdec=auto-safe` gives no libcuda or "Could not dynamically load CUDA" in the renderer's stderr (fails on the code before this change; skipped on a machine that has CUDA). `tests/test_hardware.py`: the unit has `PIPEWIRE_DEBUG=0`. A name with invalid UTF-8 bytes could not be tested: the control socket's JSON cannot carry one.
- **Not proven.** Nothing was run on a Pi: that its journal is free of the lines (a Pi's own libraries may say other things), that `gpu-hwdec-interop=no` leaves a Pi's hardware decoding as it was (copy variants only, so it should; not measured), and that the SEI and timescale warnings show the clip's name there. The unknown device at 192.168.0.225 (B19) was not touched.
