## 2026-11-18, J-135: the player log without libcuda and pw.conf lines, and the clip's name on decoder warnings

- **Lines kept out.** `mctl-render` (render/src/main.c) no longer logs two lines when it is not run with `--verbose`: FFmpeg's "Cannot load libcuda.so.1" (an `ffmpeg/` module probing for NVIDIA's decoder) and libpipewire's "pw.conf: can't load config". The filter is by module and exact words for those two lines only; no module is silenced, so every other line of the same modules still reaches the log. The player's unit sets `PIPEWIRE_DEBUG=0`, because libpipewire writes its pw.conf line straight to stderr, which mpv's log filter never sees.
- **Not done on purpose.** `--hwdec=auto-safe` was not replaced by a named list for Pi boards: nothing in the repository records which decoder a Pi's mpv really uses for H.264, and a wrong name turns hardware decoding off without a word (the same reason the #80 entry gave).
- **The clip's name.** A line from a decoder or demuxer module (`ffmpeg/*`, `vd`, `ad`, `demux`, `lavf`, `cplayer`) now carries the layer's file name in brackets, for example `video 0 ffmpeg/video [clip.mp4]: ...` (control characters in a name become `?`; the folder is left out). This is what shows which clip has the SEI or timescale warning.
- **Tests.** `tests/test_mctl_render.py` ClipTest: a damaged clip's warning names it, a good clip logs no bracket. `tests/test_hardware.py`: the unit has `PIPEWIRE_DEBUG=0` and the filter names exactly two lines.
- **Not proven.** Nothing was run on a Pi: that the two lines are gone from the journal of a node, that `PIPEWIRE_DEBUG=0` is what stops libpipewire's pw.conf line, and that the libcuda line reaches the log through mpv's log messages (as in the new renderer) and not some other way. Check `journalctl -u nxlx-player` on a node after a deploy. The unknown device at 192.168.0.225 (B19) was not touched.
