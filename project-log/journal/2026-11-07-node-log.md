## 2026-11-07, Diagnostics that read the journal, and a small log of what happened (D125)

- `pvj-sysd` has a `journal` command (fixed units, at most 500 lines, 1 to 168 hours, this start or the one before, the reply cut to 56 000 bytes because the panel reads 64 KiB). The panel's `read_log` asks it first and scrubs each line with the diagnostics scrubber; with no helper it tries `journalctl` as before. The diagnostics' log says in words whether the journal is kept (read-only root, or no persistent journal: in memory, lines from before the last restart are gone) and, when it is kept, adds the end of the start before.
- `pvj/events.py`: the last 500 events in `events.json` in the panel's state folder; crash-type events at once, the rest within a minute, repeats counted, written whole by a rename. Fed from the places that know: `Player.on_restart` (a pid the panel did not ask for), `Api.events_tick` (update result, renderer fall back and its why, a projector without an answer), the pair route (a refused sign-in, with the address kept apart), `apply_network`, the scheduler (scenes and failures), `Renderer._restart`, and the boot id at the start. `GET /api/events` is the Owner's; the diagnostics carry the lines without names or addresses.
- Under the read-only root nothing on the system disk is kept, settings included; the event log is lost there too and says so. There is no place on the system disk that survives that mode, so none was invented.
