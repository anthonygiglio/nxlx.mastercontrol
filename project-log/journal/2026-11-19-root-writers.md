## 2026-11-19, J-177: root writers in /var/lib/nxlx audited; the updater no longer follows planted names

- The problem: /var/lib/nxlx belongs to nxlx-web and has no sticky bit, so that account can rename, delete or swap any name directly in it, a folder for a link included. Every code path that runs as root (or as another account) and touches that folder was read for what a planted link or rename would make it do.
- The audit (writer, who, verdict):
  - install/install.sh nxlx_state_fix, nxlx_media_fix, nxlx_fd_own: root. Safe since PR 311 (fd walk from /var/lib/nxlx with O_NOFOLLOW|O_DIRECTORY, fchown and fchmod on the held folder). Residual: `find -exec chown -h` on settings.json* tests links and type first, then chowns by name; chown -h never follows the last name, and a swap to a hard link of a root file needs fs.protected_hardlinks off (on by default on Debian and Raspberry Pi OS). Left as is.
  - mctl/update.py backup_settings: root. REAL. Read settings.json with isfile and copyfile (follows a link: a root file such as /etc/shadow was copied into the backups and put back as the panel's settings.json on a rollback; a pipe hung the update). Made backups with makedirs (a link or a panel-made folder at backups redirected the writes), wrote the copy with copyfile and chmod by path (a link planted at the predictable name settings-<version>-<time>.json made root overwrite any file with the panel's chosen settings text, and chmod it 0600), and pruned with glob and unlink (deleted settings-*.json files in the link's target). Fixed.
  - mctl/update.py restore_settings (rollback and failed-update rollback): root. REAL. shutil.move aside, then copyfile, chmod and chown by path to settings.json: a link planted in that gap made root overwrite the target with the backup and chown it to nxlx-web, which hands that file to the panel. Fixed.
  - mctl/update.py latest_backup, _settings_schema: root. REAL but small: a glob over a folder the panel could replace; open() of settings.json followed a link and blocked on a pipe. Fixed with the same descriptor code.
  - mctl/update.py open_inbox, clear_inbox, check (inbox bundles): root. Safe: the inbox is opened with O_NOFOLLOW|O_DIRECTORY, names are opened and unlinked relative to that descriptor, bundles are copied to a private scratch folder in /opt/nxlx before use (PR 308 and earlier).
  - mctl/update.py sweep_scratch, _switch_to, previous, scratch folders, result.json: root. Safe: only /opt/nxlx and /run/nxlx-update, both root's; sweep_scratch is already fd-based.
  - mctl/sysd.py clear_update_backups: root. Safe: opens backups with O_NOFOLLOW|O_DIRECTORY, requires a folder owned by root, unlinks only plain files by name relative to that descriptor (PR 308). The updater now also keeps backups mode 0700 and root's, which is what this checks.
  - mctl/sysd.py other commands (av_output writes /boot/firmware, avahi service file in /etc/avahi/services, clock, reboot, update start): root. Safe for this folder: none touches /var/lib/nxlx. The unit's ReadWritePaths lists only -/var/lib/nxlx/backups there.
  - mctl/usb.py and mctl/clipstick.py claim, forget_claim, write_claim (nxlx-usb as root, a terminal command): root. Safe: files are made with mkstemp (O_EXCL, random name) and renamed over clip-stick.json and clip-stick-label.json (a rename replaces a link and follows nothing); forget_claim unlinks by name; the claim record is read with O_NOFOLLOW and the record must be root's, mode 0600, so a file the panel plants is not accepted. The panel can delete the claim (loses the clip stick), which is its own folder anyway.
  - mctl/clipstick.py own_node_id (read by nxlx-usb@ as root): was REAL, small: O_NOFOLLOW but a pipe planted at node-id blocked the open and hung the unit. Fixed with O_NONBLOCK and a plain-file check.
  - mctl/usb.py mounts, status, peek, mnt: root. Safe: /run/nxlx-usb (root's), /media/nxlx and /media/nxlx-clips.
  - mctl/rootfs.py (nxlx-rootfs): root. Safe: os.stat of the media folder only, writes /etc/overlayroot.local.conf or runs raspi-config.
  - bin/nxlx-convert (root, once, services stopped): renames the old state folder to /var/lib/nxlx (the folder itself, under root's /var/lib), reads settings.json, node-id and others with O_NOFOLLOW and a regular-file check, writes only under /etc, /opt, /var/backups. Its backup tar adds the old state folder files with tarfile.add, which stores a link as a link; a swap between lstat and open in that window could put a root file into backup.tar, which is 0600 root's, so nothing is exposed. Writes nothing into the state folder. Left as is.
  - mctl/netd.py, mctl/supportd.py: root. Safe: their own StateDirectory (/var/lib/nxlx-netd, /var/lib/nxlx-support, 0700, root's), not nxlx-web's; netd checks its folder (safe_state_dir).
  - install/nxlx-tmpfiles.conf: root. Safe: lines are under /run only (links in /run/nxlx/web, made with symlink(2)); no /var/lib line.
  - systemd units (install/*.service, mctl/systemd/*.service, tools/signer): no ExecStartPre anywhere; the StateDirectory lines are nxlx-netd, nxlx-support and nxlx-player/late-screen, none of them nxlx-web's folder. nxlx-player, nxlx-link, nxlx-ndi, nxlx-ndisc, nxlx-sound, nxlx-raster run as their own accounts; the player may pass through /var/lib/nxlx (2750, group) and read, never create or rename in it.
  - TLS and certificates (mctl/httpsbox.py, mctl/handover.py, boxcare): run as nxlx-web, not root; the root installer only writes NXLX_SIGNER_URL into /etc/nxlx/nxlx.env. The NDI, link and net helpers have no state under /var/lib/nxlx.
- mctl/update.py: the state folder is opened with O_NOFOLLOW|O_DIRECTORY and every name is handled through that descriptor. The backups folder is opened the same way and must be a folder of the running user (root) that nobody else can write; anything else (a link, a folder the panel made) is renamed aside and a fresh 0700 folder is made. settings.json is read only as a plain, bounded file (never a link, pipe or device; a bad one means no backup). The backup is created with O_EXCL|O_NOFOLLOW, mode and owner set with fchmod and fchown. Pruning lists the opened folder and unlinks by name relative to it. A rollback reads the backup from the checked folder, writes the new settings.json under a temporary name in the state folder (O_EXCL) and renames it over settings.json, which replaces a planted link without following it; the owner is the old file's owner if it was a plain file not owned by root, else nxlx-web.
- Tests: tests/test_update.py StateFolderLinksTest plants links and proves the targets (a root-owned file, a folder of backup-named files) keep content, mode and file list: a link for settings.json, a pipe for settings.json, a link for backups (set aside, nothing written or pruned through it), a folder the panel made and left writable, a link at the next backup's name, a link at settings.json and at the temporary name on restore, a link for the backup file itself, a link for backups at restore time, a link for the state folder. Against the old code eight of the nine fail or hang (the restore-over-a-link test passes there too, because the old code renamed the link aside first; the old gap was the moment after that, which a test cannot hit without a thread).
- Not proven: nothing ran as root or on a node; fchown to nxlx-web is not exercised (the test user is not root, and the one existing test of the owner needs root and is skipped). The race itself (a swap between two calls) is closed by construction, not shown by a test. The update from an older release still runs the older release's updater for its own backup step until the first update that installs this one. An update with a bad backups folder now sets it aside instead of failing, so a rejected-<time> folder can be left in /var/lib/nxlx for the owner to look at.
- Review round (PR 312): restore_settings failing after `current` was switched no longer skips the restart and the note of the previous release (_switch_to prints the failure and goes on). The aside name for a bad backups folder is random (a planted name cannot block it). A folder is set aside only for a link or not-a-folder (ELOOP, ENOTDIR) or a wrong owner or mode, never on other open errors and never on a read path. The schema read also survives OverflowError and RecursionError. SETTINGS_MAX is 4 MiB: settings.json is JSON text (pictures are separate files, no embedded images), the file is normally a few KiB. A restore writes the new file first, keeps the old one as settings.json.rolled-back-<time> by a hard link, and renames over settings.json, so a failure leaves the old file. latest_backup matches the version exactly. Tests added for each.
- Known and not fixed here: root-owned items kept in /var/lib/nxlx (the update backups across a factory reset, the clip-stick claim) can be hidden or replayed by the panel, which owns the folder (it can rename them away and put an older copy back). J-178 moves root's files out of the panel's folder.
- Second review: a backups folder this call has just made is opened again and checked like any other before it is chmoded or used (a swap right after the mkdir gives an update error, nothing is chmoded or filled). A settings file that cannot be copied (link, pipe, over 4 MiB) is logged, with the note that the schema check is skipped. A failed put-back of the settings is recorded (settings_problem), logged with the caller log, and added to the rollback result and to the failed-health-check message of an update. The dead replace_over branch of _write_new is gone.
