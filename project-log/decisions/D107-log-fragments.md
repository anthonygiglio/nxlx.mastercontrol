## D107. The project log is one new file per pull request, in journal/, lessons/ and decisions/; JOURNAL.md, LESSONS.md and DECISIONS.md are history (2026-10-24)

**Why.** Every pull request added to the top of JOURNAL.md (about 2,800 lines) and often to LESSONS.md and DECISIONS.md, so any two open pull requests conflicted on them. Each merge sent the others back to merge master and run about 50 checks again, and two pull requests now and then took the same "next D". The owner asked for this to come first, since it slows every pull request.

**What.**

- A pull request writes its journal entry, or entries newest first, in `project-log/journal/YYYY-MM-DD-name.md`; its lessons in `project-log/lessons/YYYY-MM-DD-name.md`; a new decision in `project-log/decisions/DN-name.md` (heading `## DN. What (date)`); and an addendum to any decision, old or new, in `project-log/decisions/DN-addendum-YYYY-MM-DD-name.md` (heading `## Addendum to DN (date): what`). The name is the branch's, by habit; each file has the SPDX header (D3). Two new files never conflict.
- JOURNAL.md, LESSONS.md and DECISIONS.md keep every old entry where it is, get one pointer at their top (in this pull request), and are not edited again. A log file of an earlier pull request is not edited or deleted either: add a new one, or an addendum for a decision.
- `tools/project-log.py` (standard library only) prints each as one document: `journal` (newest first: the files' entries by their dates, files of one day in the order they were committed, then JOURNAL.md), `lessons` (LESSONS.md, then the files, oldest first), `decisions [DN ...]` (each decision followed by its addenda, DECISIONS.md's own and then the files'). `new journal|lesson|decision|addendum` starts a file from a template; `next` gives the next free number. No combined file is committed, since every pull request would change it and the conflicts would be back. The numbers are in the names and the headings, so `grep -r D106 project-log` still finds a decision and its addenda.
- **Numbers without a human step.** `new decision` and `next` take the highest number in the tree and on `origin/master`, plus one. The check "project-log" fails a pull request whose new decision has a number master already has, naming the file that has it and the next free number; and the unit tests check the whole tree (`tests/test_project_log.py`), so two files with one number turn every run red until one is renumbered.
- **The check "project-log"** (`.github/workflows/project-log.yml`), on every pull request, and again when a label is added or removed: `python3 tools/project-log.py check --base HEAD^1` on GitHub's test merge, where HEAD^1 is master's tip. It fails, in words that say what to do, on an edit to the three old files (other than adding the pointer, once); an edited or deleted log file of an earlier pull request; a file in journal/, lessons/ or decisions/ with a bad name, a date that is not real or is in the future, no SPDX header, a heading of the wrong form, or the template's placeholder left in; a number used twice or already on master; an addendum to a decision that does not exist; and no journal file added.
- **A pull request with no journal file fails**, unless it has the label `no-journal` (a typo, a version bump). The journal is what a new session reads first, and a missing entry was the easiest thing to forget; the label keeps a one-line change from needing a ceremony.

**Cost / rules out.** A pull request open now that still adds to the three old files must move its additions into files of its own when it next merges master; the check names each file. Reading the log as one takes the tool, or two places. Within one day the journal's order follows commit times, not merge times. A taken number is caught at the latest when the second pull request is tested on master as it is: if a pull request merges on a test merge older than another's merge, the unit tests on master turn red until one file is renumbered. Not built: a bot that renumbers, and a look at the numbers other open pull requests hold. Not done here, because they are the owner's settings: the label `no-journal` itself, and "project-log" as a required check.
