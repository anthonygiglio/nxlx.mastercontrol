## D150. A Rollback button for Owners on the Updates card; never through remote support (2026-11-22)

The Owner can go back to the release before the one that runs from Setup > Updates, without a terminal (owner's decision on J-057, 2026-11-22: "a Rollback button for Owners, ready before the alpha install"; staff Owners at the venue update by USB stick or the panel's upload, guided by phone, and need a way back when an update goes wrong). The card shows the release that runs and the one before it (version and the day it was put on the node), and a button "Go back to N.N.N". The button asks in the page, in place (no browser dialog): the node restarts its services and plays again in about a minute; the settings go back to how they were just before the last update and anything changed since is set aside in a file, not deleted (that is what `nxlx-update rollback` has always done, mctl/update.py). Operators and Guests do not get the card's data or the route (`full`, the same row as the update upload).

**How root is asked.** The panel never runs a root action. `POST /api/system/update/rollback` (`{"version": "N.N.N", "confirm": "rollback"}`) asks nxlx-sysd for `rollback`, which starts the fixed template unit `nxlx-update-rollback@N.N.N.service` (install/nxlx-update-rollback@.service, the update units' pattern: root, started on request only, same `/run/nxlx-update/result.json`). The unit runs `nxlx-update rollback --version N.N.N`, the existing rollback. The version is the previous release the Owner was shown: if another release is the previous one by then (an update ran in between) the updater refuses and changes nothing. Only a version of three numbers reaches systemctl. The update units and the rollback unit exclude each other (sysd lists all three; the updater's own lock holds besides).

**Every refusal says why, in the card and as a 409:** the system disk is read-only (J-174), there is no previous release, the previous release is from before the rename of the system names (the words name `sudo nxlx-convert --undo`), an update or a rollback is running, a care job (import, reset) is running, or the previous release is not the one shown. The panel asks the same question the updater asks as root (`Updater.rollback_view`, one set of words), shows it before the click, and the root side asks again.

**Remote support (D84): refused, which is not what the update upload gets.** A remote session of the Owner's role may upload and start a signed update; the guard is the signature, and nothing in an update outlives the helper's say-so more than the helper could do anyway. A rollback is different: it puts the old settings copy back, which can bring back the PIN, paired devices and the support switch as they were before the last update, letting in a device the Owner removed since or shutting out one he added, and it needs no key of its own. So `POST /api/system/update/rollback` is in `support.REMOTE_DENY` (someone at the studio goes back, and sees the room); a helper may still read the card (`GET /api/system/update` is unchanged). Operators and carried devices follow the route's `full` row as the update upload does (D132).

**The event log (D125).** Pressing the button writes `update`: "A rollback to version N.N.N was started by an Owner.", with the role in `who`, never the device's name. The end is written by the existing watch on the progress file, now as "Rollback finished" or "Rollback failed" because the progress file carries `"action": "rollback"`. **When going back does not work (review of #321).** Before it switches, the updater copies today's settings into root's folder; if the panel does not answer after the switch it goes forward to the release it came from, puts those settings back and the `previous` note as it was, and the card says "Going back did not work; the node returned to N.N.N", the way an update that does not come up returns. A going back that is cut off by the unit's time limit is marked as going back (`finish --action rollback`), not as an update, and the event log says "Going back finished/failed". The card says that the settings, the paired devices and the PIN go back to how they were before the last update (a phone paired since needs pairing again), and dates the previous release "installed around": the date is the release folder's modification time, which is when the installer put the files there (the folder is made by the installer at that moment, and a rename keeps it), not when the bundle was built. The panel cannot read root's settings copies, so the copy's own day is not shown. `nxlx-convert --undo` removes the unit file (its `NEW_NAMES` list, the shape PR 319 uses for its own files). Cost / rules out: one more unit file and one more sysd command; a rollback from the panel cannot go back more than one release (`previous` is one release deep, as it is from a terminal); going forward again is another update. After the rollback the older release's panel runs, which has no button and writes its own line for the end.
