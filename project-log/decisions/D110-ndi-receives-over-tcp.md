## D110. The box receives NDI over TCP, not reliable UDP: live switches took seconds and sometimes failed (2026-10-31)

**The coordinator's decision**, under the owner's standing rule for low to medium risk technical changes (decide by risk); the owner is told in the morning. It reverses no decision of his. It ends a builder's line, that the library's configuration file holds the discovery servers and nothing else.

**The fault.** On the test node 2 of 3 live switches between NDI sources failed with 409 "sent no picture in 6 seconds", and a first play could too; the third took 4.6 s. The cause is the NDI library's reliable UDP transport (QUIC) failing to start between the HP's senders and the node's library. The node connects by TCP in about 5 ms. The sender then opens QUIC back to UDP 5960 and closes it about 5 ms later with CONNECTION_CLOSE, code 7. The node tries again about 55 times a second until one attempt lives (361 of 367 attempts closed so in one capture). So the first picture took from tens of milliseconds to over 7 s, by luck. Why the sender closes is inside closed code and was not found. Nothing of this project is in that path, and raising FIRST_FRAME_SECONDS would only have made the dark longer.

**The change.** `CONFIG_TRANSPORT` in `pvj/ndi.py`, `{"rudp": {"recv": {"enable": false}}}`, always written by `config_text`, with or without discovery servers. Pictures then travel on one TCP connection to the sender. No setting and no schema change.

**The helper starts again by itself when the file says another transport than the library was started with** (`Service.configure`, `config_transport`). The library reads its file once, when it is loaded. Read for this change: `Updater._systemd_restart` starts `pvj-ndi` again BEFORE the panel, and `install.sh` does the same with `--no-start`. Normally that is enough: a new helper is idle until told "on", and the new panel writes the file before it says so (`Input.sync`). But for the moment between the two the OLD panel is still up, and an open page or its status can load the library with the old file. The new panel would then find the same discovery servers and restart nothing, and the box would stay on reliable UDP until the helper next started. Hence the look. No file, or one that cannot be read, restarts nothing, so it cannot go round. A source on the screen goes black for that one restart and the watch brings it back; an update restarts the player anyway.

**If the helper does not get the file** (a box whose NDI set-up has no `/run/pvj-ndi-config`, or the panel cannot write there): the library keeps its default, reliable UDP. Nothing breaks; switches stay slow, as before. To see which a box runs while a source plays: `sudo ss -uanp | grep -c :5960` is 0 with this change in force and 4 without, and `sudo ss -tnp | grep :596` shows the TCP connection. `sudo systemctl restart pvj-ndi` makes the library read the file.

**Measured on the test node** (master 3d4e9ca, the key given by a runtime drop-in, not this code; `measurements/2026-10-31-ndi-switch`). 21 switches through the real panel between 1080p60 and 720p30: before 2 failed, gap at the HDMI dongle median 2.92 s, range 1.38 to 8.14; after none failed, median 0.87 s, range 0.67 to 0.98. The bare library, no code of ours: first picture median 1252 ms, 252 to 7076, 2 of 20 no picture; with the key median 38 ms, 18 to 46, none failed. NDI's own Test Patterns behaved the same (46 to 4857 ms, 3 of 12 no picture; with the key 24 to 42 ms), as did runtimes 5.6.0 and 6.1.1 and a sender held to one adapter. Steady playback did not change: helper 145 against 143 percent of a core on 1080p60, 32 against 31 on 720p30, library drops 0.

**The risk: TCP on a lossy link such as Wi-Fi, not run here.** Every figure above is on a wired network. Reliable UDP is NDI's default for a reason, and TCP may stall worse when packets are lost. A sender on Wi-Fi is the first thing to watch; the owner's Mac has been one.

**Not measured.** A 6.3.2 sender on another machine: none was on the network, so it is not known whether current senders have the fault, or only older ones, or Windows, or that HP. The other way round (the node's 6.3.2 sending to the HP's 6.1) gave 31 to 3719 ms, mostly about 2 s, none failed, and is not explained. Sound over TCP, the box's one sound source, a long run. This code itself on a box: the coordinator repeats the 21 switches after the deploy.

**To put it back.** `CONFIG_TRANSPORT = {}` in a release: the file loses the key and the helper starts again by itself. A rollback to a release before this one writes the file without the key, but that release's helper has no such look, so run `sudo systemctl restart pvj-ndi` if it does not move. On one sender instead of the box: `rudp.send.enable` false in that sender's own file gave about 30 ms, for whoever can change the sender.

**Rejected.** A longer first-picture wait: more dark. A panel setting: nobody can choose this well at a show, and it would be a setting for a fault. Building around it in the helper: the retries are the library's.
