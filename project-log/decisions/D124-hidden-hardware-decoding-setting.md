## D124. A hidden setting for hardware decoding in pvj-render, off by default (2026-11-07)

D95 shipped pvj-render with software decoding (`--hwdec=no`, mpv's own default there), and the addendum of D106 (2026-10-30) tried `v4l2m2m-copy` on the Pi 4 and did not adopt it: with 4 sources the CPU fell by more than half but the flips fell too (53.2 to 35.1 a second with the mapping off), sources 3 and 4 could not consume packets, and four 1080p clips wedged the firmware codec until a reboot. That stays the finding for a Pi 4, and nothing changes there.

Other boards decode differently (a Pi 5 has no H.264 decoder but an HEVC one; a desktop has VAAPI or NVDEC), and nothing there is measured. So `renderer.hwdec` in the settings, with no page, follows the pattern of `renderer.deblock` (D120): `renderer.clean` keeps it, `renderer.command` passes `--hwdec=VALUE` only when it is set, the supervisor counts it in `_wish_changed` (the player restarts once and takes hold), and the Renderer choice keeps it. Allowed values: `no` (the default, which passes nothing), `auto-copy`, `v4l2m2m-copy`, `vaapi-copy`, `nvdec-copy`, `drm-copy`. Copy variants only, on purpose: pvj-render makes its libmpv render context without a display parameter (`render/src/main.c`), so decoded frames cannot be imported without a copy and a zero-copy name would fall back to software without saying so (as the zero-copy runs of D106's addendum did). Anything else in the file is ignored, so a file cannot put a free word on the command line.

It is unmeasured off the Pi 4, and on the Pi 4 D106's addendum found v4l2m2m-copy did not help; the profile shows a row ("Hardware decoding (new renderer)") only when it is set, so the card says when it is on. No argument list changes unless the setting is set, and the frozen-values test holds for every kind. No settings schema change: an older release ignores the key and keeps it on a save.
