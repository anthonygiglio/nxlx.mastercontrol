## D132. A device paired on one node opens the other approved nodes through a one-time ticket that the first node keeps and the second redeems (2026-11-09, decided)

Decided by the owner on 2026-11-09. His request: once one node has paired a user's device, and the user may see other nodes, they should be able to open those nodes without pairing with each one. Design: `design/node-handover_2026-11-09.md`. Nothing is built yet; the build goes slice by slice, each with an independent review.

His answers: "Only owners can lock pairing. Owners can do everything on other nodes once paired to other nodes in the cluster that are approved and signed. Owners stay on other nodes for 24hrs if their first node is switched off." For trust: the signed list plus a one-time acceptance of another node by its fingerprint, shown on both panels, like pairing. The "Accept devices from other nodes" switch is enough as the lock. Nodes pass newer signed lists to each other: yes. For a stolen or retired node: "No, I need something simpler" (not re-signing the list as the cure).

What was decided: node A makes a 128-bit ticket (60 seconds, one use, held in memory on A's monotonic clock, bound to node B and to a secret only the opening page holds). The page posts it to B as a form whose Origin must be A's. B calls A back over TLS, A looks up and deletes the ticket in one step and answers once, and B signs the device in as a device of its own (`via: node`) with the same role or lower, never higher. Only Owners and Operators paired over https carry; guests, presenter codes, controller codes and remote support never do, and a carried device does not chain. **The root alone carries nothing**: a stolen, lent or retired node still holds a key and a certificate. A node is approved if it is on the fleet list that the owner signs with the root on his computer (it sets each node's carry: full, live or none; step 2c) or if B's Owner accepted it once by its key fingerprint. Every peer check binds the node id to a key hash and checks that the certificate covers the address.

**A carried Owner can do everything on an approved node, including making permanent access** (showing or rotating the PIN, codes, guest links, adding and removing devices, the root, the list, a reset). This is the owner's choice and is accepted. The protection is the approval and the removal below; the event log names the carried device on each such action.

A carried device is checked against A every 10 minutes while in use, is removed when A removes it, and lapses 24 hours after A last answered. Only an Owner can change the "Accept devices from other nodes" switch (off by default), which is the lock; turning it off signs out every carried device.

**Remove a node from this cluster.** An Owner presses it on any node. The node's key hash goes on a deny list at once; the deny spreads to every approved peer, which accept a deny from any approved peer because it can only reduce trust, and never accept an allow that way. A deny wins over the list and over an acceptance, signs out every device carried from that node on every node, and lasts until a newer signed list leaves the node out, an Owner allows it again on purpose, or a newer signed list lifts it with `clear` (a small addition for review). Re-signing the list is optional tidying. If a compromised approved node denies everyone, the damage is bounded to hand-overs (PIN pairing keeps working); the Owner removes that node, then allows the others again (one tap per node, or a signed `clear`).

Chosen over a ticket signed by A (no signature checking in Python, no shared clock on a Pi) and over a shared device list (the browser would still have to hand its token to B; it is step 3 in disguise).

Cost / rules out: B must reach A while the browser waits (as discovery already needs); the page's content security policy gains `form-action` for the nodes it may open; the list, the acceptances and the deny file live beside tls/ and stay out of export, import and diagnostics; a new event kind; about 300 lines in `pvj/handover.py`. Rules out hand-over for guests, controllers and remote support, hand-over over http, trust on the root alone, trust on first use of a changed key, and any sync of devices or settings between nodes (step 3).
