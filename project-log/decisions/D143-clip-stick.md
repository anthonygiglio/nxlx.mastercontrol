## D143. The node's own clip stick: an exFAT Nxx-CLIPS partition with a marker naming the node, checked and then writable (2026-11-17)

A node may write to exactly one USB partition: its own clip stick. Every other stick is mounted read-only as before (the mounter, `mctl/usb.py`). The plan is nxlx_shared/specs/usb-sticks-plan_2026-11-15.md (board card J-162).

- **What makes a stick the node's.** Both: an exFAT partition labelled `Nxx-CLIPS` (two digits, `N01-CLIPS`), and a marker file `nxlx-clip-stick.json` at its top level, a JSON object of at most 4 KB, read without following a link: `{"nxlx_clip_stick": 1, "node_id": "<the 32 hex digit id in /var/lib/nxlx/node-id>", "node_name": "nxlx-node-01", "label": "N01-CLIPS", "claimed": "<UTC time>"}`. Only the format, the node id and the label are compared; the name and the time are for a person reading the stick on a computer. The USB serial is never looked at: the two Verbatim sticks both report 0000000005. The label alone is not enough (two sticks can carry the same label, and the label is easy to change on a computer); the marker alone is not enough either (a vfat stick, or an exFAT one with another label, is a plain stick). The id is the fleet id (D127), so the hostname or the node number may change without losing the stick; a node with no id (the panel never ran) has no clip stick.
- **How a stick is claimed.** Root, from a terminal: `sudo nxlx-usb claim /dev/sdX2` (the installer prints the line). It refuses a partition that is not exFAT labelled Nxx-CLIPS, a node without an id, a stick that does not pass `fsck.exfat -p`, and a stick whose marker names another node unless `--force` is given. It unmounts the partition if mounted, checks it, mounts it writable at a private folder (`/run/nxlx-usb/peek/<dev>`), writes the marker (hidden temporary name, fsync, rename, fsync of the folder), makes the `clips` folder, unmounts, keeps a record in `/var/lib/nxlx/clip-stick.json` (the label and the time) and mounts the stick the normal way. `sudo nxlx-usb forget-clip-stick` removes the record. No panel action: a claim is a root action on a device, and UI belongs to the panel coordinator.
- **Mounting.** For an exFAT Nxx-CLIPS partition the mounter first mounts it read-only at the private folder, reads the marker and unmounts. If the marker names this node: `fsck.exfat -p` (exit 0 or 1 passes; up to 10 minutes; the unit's start limit is 15 minutes), then the mount at `/media/nxlx/<label>` with `rw,nosuid,nodev,noexec,noatime,uid=0,umask=0002,gid=<nxlx-svc>,errors=remount-ro`. The kernel's exfat driver takes `errors=` (as far as its source is known here; not checked on the nodes' kernels): if the mount with it fails, it is tried once without it and the log says so. A check that fails, or no fsck.exfat at all, mounts the stick read-only and the panel says why. `NXLX_USB_RW=1` still applies to other sticks only, as before; it never makes a failed clip stick writable. The mounter writes `/run/nxlx-usb/clip-stick.json` (device, folder, label, writable, why) and removes it first thing on unmount.
- **The media folder.** `Api.media_dir` is asked each time (cached for one second): the `clips` folder on the stick while the status file names a real mount point directly under `/media/nxlx` whose `clips` is a real folder (no links), else the folder `NXLX_MEDIA_DIR` names (the SD card's). `/api/media` carries `clip_stick`: `none` (no record, nothing said: node-02), `in`, `read-only` (with why) or `missing` ("The clip stick N01-CLIPS is not plugged in. The library shows the test clips on the node's SD card; plug the stick in to see and add your clips."). The panel shows that text as one line at the top of the library and nothing else.
- **Writes.** Uploads and copies from another stick were already a hidden `.upload-` file, fsync, then a hard link (no overwrite) or a rename, then an fsync of the folder. exFAT has no hard links (EPERM) and refuses chmod to a mode its mount mask does not give (EPERM): on that error alone the file is renamed after checking the name is free, under the media lock every write in the panel holds, and the chmod is passed over (the mount's own mask makes it group readable). Rename of a clip takes the same road and now fsyncs the folder.
- **Sandbox.** nxlx-web gets `ReadWritePaths=-/media/nxlx`: a stick already mounted when the service starts (at boot) would otherwise be read-only inside its namespace. Every other stick under that folder is read-only by its mount, so nothing else becomes writable.
- **Never a recovery file.** Nothing writes `nxlx-recover` (D81) on any stick; a test holds that a claimed stick has only the marker and `clips`.

Why: the clips must outlive an SD card and move between computers (exFAT is the one format macOS, Windows and Linux all read and write with files over 4 GB), and a node writing to a stick that is not its own, or to one with a damaged table, is how a show's clips are lost. Cost / rules out: a stick is the node's only after a root command; a stick that fails its check is read-only until repaired on a computer; a node whose id changes (a read-only root that cannot keep it, a new SD card) must claim its stick again; exFAT has no journal, so a pull during a write can still lose that file; the check delays the mount of a large stick at boot. Not proven: nothing here has run on a node or met a real stick; the mount options, `errors=remount-ro`, the fsck exit codes, the boot-time ordering with nxlx-web and the EPERM behaviour of exFAT are from documentation and source, tested only with stand-ins.
