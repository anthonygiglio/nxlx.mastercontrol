## D148. The read-only disk keeps the node's settings on a small kept disk of its own (2026-11-22)

With the read-only system disk on, the six folders that change at run time (/var/lib/nxlx, /var/lib/nxlx-player, /var/lib/nxlx-netd, /var/lib/nxlx-update, /var/lib/nxlx-support and the saved Wi-Fi in /etc/NetworkManager/system-connections) live on a separate small ext4 filesystem, the kept settings disk, and are bind-mounted over their normal places at boot by the unit nxlx-kept.service, before any service starts. Everything else stays on the protected disk. Why: the owner decided (J-050) that the read-only disk must not cost the PIN, scenes, devices, graphics, settings or Wi-Fi at every restart, and the rootfs spec (J-174, option D-lite) said the only way is a writable place outside the overlay. A bind mount of a folder on a second filesystem is the simplest to test with a fake mount and a temp folder, needs no change to raspi-config or overlayroot (so it works the same on the Pi and the M710q), and the damage of a pulled plug is limited to one small journaled ext4 filesystem that is mounted noatime,nodev,nosuid,errors=remount-ro and checked once (e2fsck -p) if the first mount fails. The disk is named by its filesystem UUID in /etc/nxlx/kept.json, written by `nxlx-kept prepare` (never by the installer), plus a marker and a random secret on the disk that must equal /etc/nxlx/kept.secret (root only; compared in constant time, the files opened without following a link and read with a size cap); a stick that only has the label, or the UUID, is never used. The copying is not done at boot: media in /var/lib/nxlx would be copied with a flush per file before sysinit and could hold every first boot for many minutes. `nxlx-kept prepare` (and `nxlx-kept seed` for a folder added later) is run by an admin with the node up: it makes every check before it writes (a whole disk with a partition table, the disk that holds / or /boot, a blkid error, an existing kept disk, a mount point), stops the nxlx services, copies each folder as root, never following a link (the panel's account owns /var/lib/nxlx and could plant one; a relative link without .. is made again, any other link is left out and said, a hard link becomes a separate file), into a .new folder renamed into place, flushes the disk once (syncfs), binds the folders and starts the services again. The boot unit only mounts and binds; a folder the disk does not hold stays on the system disk and is reported. The boot step never raises and always writes /run/nxlx-kept.json.

If the disk is missing the node still starts on the protected disk and says "missing" in /run/nxlx-kept.json, loudly. Those system-disk copies are older than the kept ones and would bring back a device removed since (decided by the coordinator, review of PR 319), so once a seed has succeeded, while the root is still writable, `prepare` empties them of what grants access: `devices` and `recovery` (the Owner recovery codes) in settings.json, settings.json.bak and its other copies (.rolled-back-N, .before-import-N), pairings.json (handover acceptances), the update folder's settings-*.json copies and the support folder's private.key. The PIN, scenes, graphics, settings and Wi-Fi are left so the room still runs; a fallback boot needs fresh pairing with the PIN. deny.json and the fleet list are left (they only restrict or name nodes). `nxlx-rootfs enable` refuses without a ready kept disk (`--without-kept` is the explicit way to get the old behaviour). `nxlx-rootfs disable` leaves the kept disk in use.

Cost / rules out: a node needs a spare partition or disk of 1 GB or more (this tool does not repartition; the image build, J-168, should leave one), set up once with `nxlx-kept prepare`. Rules out: a single bind mount of a directory on the root (the root is the read-only part), writing through overlayroot-chroot at run time (every write would be a remount of the lower disk, the very thing the overlay protects), and releases or units on the kept disk (option D of the spec: it would leave the node half updated after a restart). Also cost: the services (panel, player, netd, sysd, supportd) stop for the seconds the copy takes at set-up, and a node whose media is large needs a long `prepare` (once). Not decided here: how to stop using the kept disk and copy back (second PR), the journal on the kept disk, and the panel card. Not proven: everything above on a real node; the pull-the-plug test at the box is still to come (tools/DEVICE-TESTING.md KS1 to KS8).
