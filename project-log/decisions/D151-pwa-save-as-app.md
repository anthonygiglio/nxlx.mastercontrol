## D151. The panel can be saved as an app; the service worker only shows an "away" page (2026-11-22)

What: card J-180, rebuilt from master (the draft of PR 116, branch `webapp-install`, was closed; its D76 was never on master, so this is a new decision). The owner decided on 2026-11-22 that staff at a venue add the panel to the home screen of a phone or tablet and open it like an app (iPhone Safari, Android Chrome, the Amazon Fire tablet's Silk), now that a node can run on https:// with his own root (D79). The node serves a web app manifest (`/manifest.webmanifest`, name `NXLX`, standalone, scope and start `/`, colours from the look in use), the icons (an N in the house off-white on the house near-black, drawn by `tools/make-icons.py` from `mctl/icon.py`, 192, 512, maskable, monochrome, and the 180 px Apple one), the Apple tags in the page head, a service worker at `/sw.js`, and a card, Setup, Save as an app, with the steps for the device in hand and the browser's own Install button where it offers one. The page's policy gains `manifest-src 'self'`. Details and the sources for each browser are in `docs/WEBAPP.md`.

The service worker (the choice that needed deciding): it handles only a page being opened (a GET navigation to this node, not under `/api/`) and, when the browser reports that the request failed, shows a plain `/away.html` that says the node cannot be reached, with a button to try again. Its cache holds those two files and nothing else, never a response from the node. There is no timer: a slow node is waited for and its page wins (a review of the first version found that a 10 second timer threw away a real page from a loaded Pi). The away page's style sheet is answered from the cache when the node is away. The away page also says what to do if the node has been moved back to http. Scripts, styles, pictures and every `/api/` call do not pass through it. The node writes the release into `/sw.js` (`nxlx-shell-<version>-<checksum>`), serves it `no-store`, and the new worker takes over at once and deletes every cache that is not its own. It is not asked for over plain http (a browser refuses one there), so http behaves exactly as before. Worker lifetime: on activate and on every page opened, the worker asks the node for `/sw.js`; a 404 or 410 makes it delete its caches and unregister itself (a failure or any other status leaves it). A node that is moved back to http cannot be reached by the https-scoped worker at all, so that case is the away page's line. `/sw.js` is public, so before pairing anyone on the network can read the node's exact version in it (the cache name); accepted, since the version is not a secret worth more than the cost of gating a file a browser fetches without a login.

Why: Chrome's install criteria no longer ask for a service worker, so it is not there to make the app installable. The one thing a person would notice is an app that shows the browser's error page when the phone is off the venue's network, which looks broken; the away page fixes that. A worker that kept the panel's own files was rejected: every control needs the node, so an offline panel could only look signed out (the status call fails and the page falls back to the connect screen), and a kept panel can be shown after an update. A caching worker also risks keeping something per person. This one cannot, by construction, and the tests read its source and run it against stand-ins for the browser to prove the guards.

Signing in: the panel's sign-in is one `HttpOnly` cookie (`mctl_token`, or `__Host-mctl_token` over https), a year long, and nothing about it is in `localStorage`. An app saved from Safari on an iPhone or iPad is expected to have its own storage apart from Safari's, so it asks for pairing once and then keeps it; a code scanned with the camera and a guest link open Safari, not the app, so pairing in the app is by typing the code or the PIN, which the connect screen says when it runs as an app. http:// and https:// are different origins, so a device pairs again after the move to https (D79). Android Chrome's installed app is expected to share Chrome's cookies; not confirmed.

Cost / rules out: nothing here was tried on a real iPhone, iPad, Android phone, Fire tablet or laptop; the words for Silk are not from Amazon. No offline panel, no push, no splash images, no "update available" banner. Over https a device that does not trust the node's root gets a certificate warning and no install offer; the card says to install the root first. A saved app keeps the launch colour of the look it was saved under until it is saved again. The 9 device rows are in `tools/DEVICE-TESTING.md` (WA1 to WA9). The UI tests (`tests/ui`) were updated for the new Setup row and were not run: Playwright is not on the development machine; CI runs them.
