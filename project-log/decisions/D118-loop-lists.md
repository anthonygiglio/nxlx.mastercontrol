## D118. A looping clip plays through a generated ffconcat list on the New renderer, with D22 unchanged (2026-11-01)

A looping clip stalled 113 to 201 ms at each pass on a Pi 4 under load, because loop-file restarts the decoder (measurements/2026-10-31-loop-seam). A generated ffconcat list keeps packets flowing through one decoder: 34 to 57 ms under 4 sources, with `access-references=no` left on (measurements/2026-10-31-loop-concat). So on the New renderer, a single local video with ending `loop`, on Source 1 or sources 2 to N, by a cut or any transition, loads a list. Classic mpv, images, playlists of several clips, streams, capture, NDI, the shader carrier and clips under 0.2 s stay exactly as they were, and so does any failure on the way: a list or the plain load, never an error (`pvj/looplist.py`). The kill switch is `renderer.loop_lists` in the settings, read with defaults, no page, no schema change.

**A cut never waits.** The list needs the clip's length to the microsecond (`duration` lines; without them a seek lands short). A clip whose length is not cached plays plain, and its length is found on a worker thread (`probe.exact`, one bounded mpv), so the next load is seamless. No program starts in the load path, and nothing reloads a clip that plays.

**The files** are in `/run/pvj/web/loops`, the panel's own folder, read by the player through group pvj (D45). For each clip, by a hash of its real path, NAME.ffconcat (1000 pairs of `file` and `duration`) and NAME.mp4, a link to the clip as it was given, so USB and read-only places work and FFmpeg's `safe=1` takes the name. The concat demuxer opens the inner file at every join, so a list and its link stay while any layer plays them. A prune runs only on a list load, only past 32 lists, and leaves what `pvj-sources` names and anything used in the last 180 s, longer than any crossfade; the outgoing side of a crossfade, which no question to the player names, is touched as it leaves. Past 128 lists with nothing to prune the load is plain. A player that cannot say what it plays has nothing pruned under it.

**One translation layer.** `Ipc.request` hands to `looplist.Clips`, and `Ipc.direct` is the player's own word. Above it a list reads as the clip: `path`, `duration`, `time-pos` modulo the length, `percent-pos`, `playlist`, the rows of `pvj-sources`, an absolute seek lands in the pass that plays, a relative seek is left alone. It reads from the files, not from memory, so a panel that started again still understands the list its player plays. The audit of every reader is in the journal.

**Loop off** sets `end` to the next pass boundary with loop-file no, and Loop on clears it. Loop on over a plain clip stays plain until its next load. Endings `next` and `hold` never take a list; in plain mpv a list stopped by `end` under keep-open held its last frame.

**The socket** gains `end` in SETTABLE and the three `vd-queue-*` keys in LOAD_KEYS. They are also allowed in the options of `pvj-crossfade` and of a source's load, where they are split off and given to that one load (`load_part`), as every list load must have the queue and none else may. mpv's loadfile needs an index before its options, so a libmpv before 0.38 refuses such a load, and the plain clip plays.

**The hole of the report is closed for both renderers.** `expand_media`, which every local path passes (source 1, crossfade, sources 2 to N, a list of clips; audited in the journal), drops a file that begins with `ffconcat`. On the node (mpv 0.40, FFmpeg 7.1.5) a UTF-8 byte order mark, a newline, spaces, a tab, a NUL byte, capitals, a comment line, version 1.1, or the word alone before or in place of the header are not detected, so they are not looked for. A leading ID3 tag is: FFmpeg's probe skips one, of any size, with or without a footer, so the check reads past it. Two tags in a row were not followed; the check refuses those too. The generated lists never pass this funnel.

**A stream cannot gain reach this way.** Checked on the node over loopback HTTP, a stand-in for a stream's body: an ffconcat body is followed only to a name on the same server. An absolute path, `file://`, `file:`, `..` and another host are all refused as `Unsafe file name`, and no request reached anything else. The box's own streams are SRT, RTSP and RTMP; those were not run. Stream URLs are out of scope for the check above and stay so. A disguised HLS list was checked too, because the concat demuxer's inner open is outside mpv's block on references: FFmpeg refuses to detect HLS under a name that is not its own, alone and inside a list.

**Where the design changed, because of a fact:**

- `end` is set as `file-local-options/end`, inside the renderer. mpv's plain `end` stays for the next file: read back 2 after a new load, and it would stay on the idle layer through a crossfade and cut a later clip short.
- Three guards, because loop-file=inf must not meet a gone inner file. With the file gone at a join, plain mpv seeks for ever: 7000 turns a second, two cores busy, nothing drawn, never idle. In the renderer it is worse: FFmpeg's concat demuxer can seek through a context it lost and the whole of pvj-render fell with a null pointer in `avformat_seek_file` (FFmpeg 7.1 in CI's Debian 13 job, 8.0 on a desk, most often after a seek from the panel). With loop-file=no it ends cleanly, so: `render/src/main.c` reads the demuxer's own complaint, which comes while frames are still buffered, and takes the loop off that core, so the file ends with no seek at all; 20 restarts in a row with no frame between do the same for any other cause; and `looplist.Clips` sends no seek for a list whose clip is gone. The window left is a file that goes in the moment of a seek. All of it is run against the real renderer in tests/test_pvj_render.py. A deleted clip used to play on from its open file; now it ends at the next join.
- The refusal reads past an ID3 tag (above).
- A clip plays through a list only if mpv calls its container MP4/MOV, mkv (also WebM), MPEG-TS or AVI and it has video. Each was played through a list on the node with no fault. Anything else (`.mpg`, `.wmv`) is unusual in the design's sense and stays plain.

**How exact a `duration` line must be:** a line wrong by up to 10 ms either way changes nothing that can be seen, on clips with and without sound. Too long adds its own error to the hold (50 ms made 67 ms). Too short by more than a frame's time makes mpv warn `Invalid video timestamp` at each join (50 ms), with no dropped frame. So 6 decimals are more than is needed, and a rounded length would nearly do; the cache keeps what mpv says.

Cost: 80 to 100 ms more to open, a 45 KB file per clip in memory, about 12 MB per source for the queue. A clip's first load after a panel start still has today's seam. The end of the list (100 minutes of a 6 s clip) is one seam of today's size.

Rejected: `format_whitelist` in the renderer (every format the box plays would have to be named, and a per-file `demuxer-lavf-o` opened on the socket); `edl://` (reverses D22); a probe in the load path (it would delay a cut); a reload when Loop is switched on (it would jump).
