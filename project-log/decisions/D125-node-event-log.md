## D125. The diagnostics read the node's journal through the root helper, and the node keeps a small log of what happened (2026-11-07)

**The journal.** `GET /api/system/diagnostics` asked `journalctl` for the services' lines from the panel's own account, which is deliberately not in the systemd-journal group (`pvj/boxcare.py`), so it usually answered "No log lines came back". Now the root helper `pvj-sysd` has a `journal` command: `journalctl` for a fixed list of the node's own units (`pvj-web`, `pvj-player`, `pvj-sysd`, `pvj-netd`, `pvj-supportd`, `pvj-sound`, `pvj-link`, `pvj-ndi*`, the update and USB template units), at most 500 lines (300 asked), a window of 1 to 168 hours (24 asked) for this start, or the end of the start before (`boot` -1, no window). The numbers are clamped in the helper, the command line is a list and never a shell, the lines are cut to 400 characters each and the whole reply to what the panel reads (56 000 bytes). The helper returns them raw; the panel scrubs each line whole with the diagnostics scrubber (the PIN, codes, logins in addresses) and only then cuts it. The panel gets no journal group and no new right. Without the helper (a desk), the old direct attempt is made. The diagnostics say whether the journal is kept: with the read-only root (`pvj/rootfs.py`, overlayroot), or without a persistent journal, the system log is in memory and lines from before the last restart are gone; with a persistent journal the end of the previous start is in the file too.

**The event log.** The node keeps the last 500 events, one line each (time, kind, a short plain sentence, a count when the same event repeats within five minutes), in `events.json` in the panel's state folder (`/var/lib/pvj`, beside `settings.json`; no other place is kept across a restart). Under the read-only root nothing on the system disk is kept, settings included, so there the log is lost at a restart too; the Owner is told so on the endpoint and in the diagnostics. What is logged: the node restarting (the boot id changed), the player restarting by itself, the renderer falling back to classic and why, an update's result (a failure at once), a projector that does not answer, a network change, a refused sign-in, and a scheduled scene (and any scheduled entry that failed); the renderer card's own restarts of the player too. A crash-type event (node restart, player, renderer fall back, update failure) is written at once; the others at most once a minute; the file is replaced whole by a rename, never holds more than 500 events, and a count going up on a line already written waits ten seconds between writes, so a loop cannot wear the card.

**Privacy.** `GET /api/events` is the Owner's only (an Operator and a Guest get 403). Sentences never hold a secret by construction (nothing typed into a sign-in is logged), they are cut to one short plain line, and they pass the scrubber again on the way out. A device's name or an address is kept apart (`who`) and only the Owner's endpoint shows it; the diagnostics file, which leaves the node, carries the lines without it.

Cost / rules out: 500 events is about 100 KB and covers days, not weeks, on a busy node; it is not a security audit trail (it records refusals, not every sign-in), and a node on the read-only root has no history across restarts, which is the cost of that mode. The panel's own pages (Health, What happened) read `GET /api/events`.
