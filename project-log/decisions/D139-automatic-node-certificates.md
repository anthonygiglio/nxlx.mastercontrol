## D139. Nodes get their HTTPS certificate by themselves, from a signer under a new root (2026-11-14)

The owner's decision, 2026-11-14: "Fully automatic". A new node must have HTTPS with no step from the owner, so devices that trust his root (the FireTab trusts nothing else, D131) reach it at once. Until now (D79) he made the request on the panel, signed it with his root's passphrase and uploaded the result. How it is done, in plain words for the owner, is in docs/HTTPS.md, "Automatic certificates".

**A new root first (the owner chose this, option A, 2026-11-14).** Every root `boxcert.py make-root` made since 2026-10-10 says `pathlen:0`: it may sign node certificates and nothing else. His root of 2026-10-13 does too (read from its public root.pem). A signer under it is refused everywhere ("path length constraint exceeded"; tested with openssl and Python's ssl). The other options were to keep the root key itself unlocked on the always-on computer (works with every device today, but a stolen computer means a stolen root and a re-root of every device) or to do that now and re-root later. `make-root` now makes `pathlen:1` roots with the same name constraints (.local, 10/8, 172.16/12, 192.168/16, 169.254/16). The old folder is never touched; the new root lives in a new folder (`--dir ~/nxlx-root-ca-2`).

**The signer.** `boxcert.py make-signer` (once per root, where the root key lives) makes "NXLX node signer": ECDSA P-256, CA with `pathlen:0`, keyCertSign and cRLSign, name constraints for `.local` names and the three private ranges only (no link-local), 825 days. Its key is written unencrypted (mode 600) into `<root folder>/signer/`, with signer.pem, a copy of root.pem and an empty pin file; the owner copies that folder to the signing computer. It refuses an existing folder, a wrong passphrase and a `pathlen:0` root. Renewing or retiring a signer is moving the folder away and running it again: new nodes then only get certificates from the new one. A copied signer still makes trusted certificates until it runs out or the root is replaced; there is no revocation, the same as for a stolen node key, and the constraints limit it to local names and private addresses.

**The signing service** (`tools/nxlx-signer.py`, standard library and the system's `openssl`, started at logon on Windows by `tools/signer/install-windows.ps1`, or by `tools/signer/nxlx-signer.service` on Linux). Plain HTTP on the LAN, port 8781: `GET /v1/info` (the public root and signer), `GET /v1/root-move`, `POST /v1/sign` with the request and the node's host name, which returns the node certificate, the signer and the root. Rules: callers from 10/8, 172.16/12, 192.168/16 and loopback only; the request's own signature must hold; names are `.local` only and must include `<hostname>.local`; the subject must be one of the names; an address goes into the certificate only when it is the caller's own private address, because addresses move between nodes with DHCP and are never pinned (other addresses are left out and listed in the answer). First come, first pinned: a name signed once is signed again only for the same public key (SHA-256 of the request's SubjectPublicKeyInfo); another key is refused with the command that releases it (`nxlx-signer.py release NAME`). At most 6 signings an hour per caller and 30 in all. Every signing and refusal goes to signer.log. The node certificate has the profile of `boxcert sign` (serverAuth and clientAuth, 397 days), cut to what is left of the signer's life. The honest trade-off: anyone on the LAN can get a certificate for a `.local` name nobody has taken yet; taken names are protected by the pin.

**Finding the service.** A setting `https.signer_url`, else `PVJ_SIGNER_URL`, which `install.sh --signer URL` writes into /etc/pvj/pvj.env. Not discovered: the fleet discovery (D127) announces nodes through avahi, which the Windows computer that runs the service does not have, and an address the owner gave cannot be answered by a stranger first.

**On the node** (`pvj/autocert.py`, a thread started by pvj-web after its listeners, so install, every deploy and every update run it): at start and every six hours (ten minutes while the service is silent or refused), it asks for a certificate when there is none, it ends within 30 days, or it is not from the pinned root. It makes the request with the existing request code and the node's key, and loads the answer through the same checks as an upload. The pin holds: with a root pinned, the chain must end there. With none, the root in the answer is pinned like the first manual upload, but only after the chain checks out against it, it is the root the service says it works for, and, when `--root-fingerprint` (PVJ_ROOT_FINGERPRINT or `https.root_fingerprint`) was given at install, it is that root. A silent service leaves everything as it was and the Secure connection page says "Waiting for the signer"; the page also shows the URL with "Save and try now" (`POST /api/https/auto`, owner).

**What changed in the checks, and why.** Before this, the code assumed the root signs node certificates directly. A node's certificate file now keeps the signer after the node's certificate (devices need it to build the path), and `check()` tells a root (issuer and subject the same name, byte for byte) from a signer (any other CA); before, the first CA after the node's certificate was taken as the root, which would have pinned the signer. `_issued_by_stored_root` hands the signers to `openssl verify` as `-untrusted`: they help build the path, and the pinned root stays the one anchor whose path length and constraints apply. A peer node's certificate is now checked in the TLS handshake against the pinned root (`HttpsBox.peer_client_context`, dates left out as on the peer listener), because a client sees the node certificate alone after the handshake and so could not see the signer; names, the key and dates are still checked by hand. The peer listener and `present_to_peer` send the whole file, so the signer travels both ways. `boxcert verify`, `show` and `fleet add --cert` read the signer from the same file.

**Moving the nodes to the new root.** Nodes that pinned the old root (node-01 at .169 and node-02 at .174) would otherwise need "Replace the root" over https by an https-paired device, on each node. Instead `boxcert.py move-root --to NEWDIR` (the old root's folder is `--dir`) makes `root-move.json`, `{v, kind, from, to, root, issued}` with both SHA-256 fingerprints and the new root, signed by the OLD root key over `nxlx-root-move-v1` + newline + the exact bytes (the fleet list's signature scheme, D132). It is written into the new signer folder, and the service gives it to any node that asks. A node whose pinned root differs from the service's fetches it and takes the new root only if its own pinned root signed it, `from` is its root, and the root carried hashes to `to`; then it asks for a certificate as above. A move applies once: afterwards it names a root the node no longer pins and is refused. Nobody pairs and nothing is opened over plain http: only the holder of the old key and its passphrase could ever make a move, the same trust the manual "Replace the root" asks for. node-03 (.249) pins no root yet and takes the new root on its first certificate. A fleet list signed by the old root stops checking out after the move; `move-root` copies the working list (same fleet id) into the new folder and prints the two commands to sign and push it.

**The FireTab launcher** (separate repo, nxlx-fire-launcher, D131) bundles the root as its only trust anchor and its `CertCheck` refuses a node certificate not signed directly by that root. It needs the new root.pem, a CertCheck that accepts a node certificate whose issuer is a signer that the bundled root signed (the WebView shows the node certificate only, so signer.pem is bundled too), a rebuild with the same keystore and `adb install -r`. Until then it refuses every node that has moved.

**After the independent review (same day).** Addresses are pinned to a key exactly like names (an attacker holding a node's address got a trusted certificate for it); `release`, `list` and a new `pin --cert FILE` cover both. A node with no root never pins one without an expected fingerprint: `install.sh --signer` requires `--root-fingerprint`, the panel asks for it, and without it the node says "Needs the root fingerprint" and sends nothing; a service working for another root than the expected one is not sent a request, and a root move must lead to the service's root and the expected one before it is checked. The pin file fails closed (missing or damaged means 503, never "nothing pinned"), is written atomically with a `.bak` of the copy before, under a cross-process lock (fcntl, msvcrt on Windows) that `release`, `list`, `pin` and the seeding also take. `make-signer` and `move-root` seed the pins from the root folder's signed.json and the certificate files beside it, so node-01 and node-02 keep their names and addresses before they ever ask. Every `openssl verify` (node and tool) adds `-no-CApath -no-CAstore` (`-no-CApath` alone on 1.1.1, an empty `-CApath` folder on LibreSSL), since `-CAfile` alone also trusts the system's CA folder. The root and the signer carry `extendedKeyUsage = serverAuth, clientAuth`. The service answers only a Host that is an address or one of its names, refuses any request with an Origin header and a POST without `Content-Type: application/json` (cross-site posts, DNS rebinding); refusals count against the caller only and signings against everybody; the request's subject must be exactly one CN and its key EC P-256; at most 16 requests are handled at once. On the node, the automatic request has its own file, so the owner's saved names and a manual request.pem stay as they are, and after a 409 (a taken name) the next try is in six hours.

**After the second review (same day).** An address held by another key no longer refuses the whole certificate: it is left out (listed in `left_out`) and the names are signed, because DHCP reuses addresses. A key's address pins follow its newest certificate (addresses it no longer carries are freed), and an address pin lapses when the certificate it came from ends; name pins never lapse by themselves. Seeding uses the same conflict rule as `pin` and lists what it left alone. `make-signer --pins FILE` carries the signing computer's pins into a replacement signer, and `install-windows.ps1 -From` never overwrites a signed.json already on the HP. P-256 is judged by the SubjectPublicKeyInfo bytes (algorithm and curve), not by openssl's text. A pin file that cannot be replaced (Windows holds files open) is tried again for about two seconds, then the answer is 503 and the log says why. The expected root fingerprint decides the first root only; once a root is pinned, only a move signed by it changes the root, so a fingerprint set at install never blocks a later move. The Windows script prints the address from the same host name the service checks and passes `--host-name` when one is given. The FireTab launcher tries every bundled signer of the issuer's name.

Cost and what it rules out: one evening of the owner's time (a new root and passphrase, the signer, the move, the new root on each device, the launcher rebuilt); the always-on computer becomes something to protect, since its signer key has no passphrase; certificates for new `.local` names are open to anyone on the LAN until taken. Not built: discovery of the service, revocation, IPv6.
