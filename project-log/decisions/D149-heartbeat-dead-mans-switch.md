## D149. The daily heartbeat: an Owner's opt-in ping to a dead man's switch (2026-11-22)

The Owner decided on 22 November that the alpha should push to his phone when a node goes quiet (J-057). Silence cannot be seen from inside the node, so something outside must expect a ping and raise the alarm when it stops; the node's half is a small HTTPS ping to a service the Owner makes (healthchecks.io is one example; any service that takes a ping URL works, and none is built in or required). Rules: (1) off by default, and the node sends nothing anywhere until an Owner switches it on; no earlier decision forbids an outbound call, and this one keeps the node's only unprompted call to the internet opt-in. (2) The Owner alone sets, switches and tests it (`GET/POST /api/heartbeat`, `POST /api/heartbeat/test`, role full); a Guest or an Operator has no route and never sees the card. (3) Never through remote support: both POST routes are in `support.REMOTE_DENY` and the handlers refuse a support device too, so a helper cannot point the pings at a service of his own or silence the owner's phone; a support session of the Owner's role may read the card (masked). (4) The address is a key to the owner's check, so it is checked strictly (https only, at most 300 characters, ASCII, no space or control character, a host name or IPv4 address, no login, no fragment, a path that names the check), shown back only masked (host and the last four characters of the path), and never written to a log, an export or a diagnostics file. The setting `heartbeat` is the node's own (`boxcare.BOX_OWN`): not exported, not set by an import, and also in the defaults so that an import which names it is noted and left, not refused. (5) What is sent is one plain GET to that address with a fixed User-Agent: no body, nothing added to the address, no node name, no network address, no device name; no redirect is followed, so a ping never leaves https; the timeout is 10 seconds (8 for the Owner's test). Ping interval 5, 10, 15 (default), 30 or 60 minutes. The only status the node adds is the option "tell the service when the player is down", off by default, which adds `/fail` to the path while the player is not running (healthchecks.io's convention); with it off every ping is the same plain ping. (6) It runs in its own daemon thread that holds no lock while it waits on the network, turns every error into one plain sentence and never raises; the test ping is one at a time (a second is a 409). The last ping's time and result are shown to the Owner on Setup > Health and kept in memory only; the log gets one line when pings start to fail and one when they work again. Why: a node that has lost power or its network cannot tell anyone, the Owner wants a phone alarm, and the smallest honest answer is a ping to a service that owns the alarm. Cost / rules out: the node trusts the service's TLS certificate against the system's certificates and needs the right date; a service that is down is not noticed by the node; a node that keeps pinging while its show is broken looks healthy unless the player-down option is on and the service understands `/fail`; the Owner must make the account and the phone connection himself (docs/HEARTBEAT.md has the steps); the node does not itself push to a phone, run an alarm server or email anyone, and no device or room data ever leaves the node by this route. Not proven: the node's side has been run against a loopback test server only, not a real service or a phone.
