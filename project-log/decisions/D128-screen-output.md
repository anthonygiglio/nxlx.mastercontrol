## D128. The output: the Owner may pick the connector, and the AV output on a Pi can be switched on from the panel (2026-11-07)

The owner (2026-11-07): "Leave it at one screen per node for now, but include a way for the user to pick the output, including the AV output on Pi's." Until now `screenmode` chose the connected connector itself, an HDMI one first (the review of #139, L5; D91). A node still draws on one screen. What is new is which.

**The setting.** `settings["screen"]["output"]`: absent or "auto" is Automatic, today's behaviour (the Pi 4's arguments are exactly as before); or the kernel's name of one connector as `hardware.drm_connectors` lists it (HDMI-A-1, HDMI-A-2, Composite-1, DSI-1, DP-n and eDP-1 on a desktop; writeback excluded). It rides in `WANTED` beside the mode (`clean_wanted` checks its shape), and the player's `decide` takes it at a start. A chosen output that is not connected at that start is said plainly ("HDMI 2 is not connected, so Automatic is used for now; the player takes HDMI 2 at its next start once it is") and Automatic is used, so the room never goes dark. It never flaps: nothing moves a running player because a chosen output came; the next start takes it. A named output whose card is not known still passes `--drm-connector=NAME`. A skip (D92) bars the very arguments, connector included, so a chosen output that gives no screen falls to the player's own screen like any mode. The mode and its try are unchanged and keep the output; a mode chosen for an HDMI screen is not applied to the AV output, which has its own.

**The AV output.** Under the full KMS driver the composite output is off. The Raspberry Pi documentation (config.txt, video): it is on only with `enable_tvout=1`, "which also disables HDMI output", with `,composite` added to the `dtoverlay=vc4-kms-v3d` line, and the standard is NTSC unless `vc4.tv_norm=` (NTSC, NTSC-J, NTSC-443, PAL, PAL-M, PAL-N, PAL60, SECAM) is added to `cmdline.txt`; the kernel's overlay README says of the parameter that it "disables all other outputs" on a Pi 4. What it costs, exactly: on a Pi 4 and a Pi 5 the HDMI outputs are off while AV is on, so without a screen on the AV connector there is no picture after the restart (the panel still works over the network and turns it off again); on a Pi 3 and older HDMI stays on and the 3.5 mm jack's video is added; a Pi 5 has the signal on a pad (J7) to solder to. Forums add that it slows some clocks on a Pi 4; the official documentation does not say so and nothing here claims it. Both directions need a restart of the node.

**Who writes the boot files.** Only `pvj-sysd`, the root helper (`av_output`), through `pvj/bootcfg.py`, and only the files in `/boot/firmware` (Raspberry Pi OS Bookworm and later; the unit gets `ReadWritePaths=-/boot/firmware` and nothing more, and the older `/boot` is not edited). In config.txt: `,composite` on each active `dtoverlay=vc4-kms-v3d` line (also `-pi4` and `-pi5`) and a marked block (`[all]`, `enable_tvout=1`); in the one line of cmdline.txt: `vc4.tv_norm=`. Turning AV off puts our changes back: the marked block goes, and every `composite` parameter on those overlay lines goes with it (an owner's own `composite` there too); the end of line is kept and the rest of a line is left as it was. It does not give the exact original back: the `<name>.nxlx-original` copy, made once before the first change and never removed, is the exact original, and each change is also copied as `<name>.nxlx-<seconds>` (a counter if two fall in one second), the newest 3 kept. A change already in force is no change: nothing is written and no backup is made. cmdline.txt is written first and config.txt second, because a stray `vc4.tv_norm=` does nothing while config.txt carries the change that switches HDMI off; if the second write fails the first is put back, and if that fails too the error says which file was left changed and under which backup name, and carries what the boot files say now. A config.txt with no `vc4-kms-v3d` line this node knows is refused in words and nothing is written. The boot partition is its own filesystem, so the change holds under the read-only root. NTSC is the default (the owner is in Canada, and it is the kernel's own default); the panel offers the other standards.

**API (Owner only, never through the support tunnel for the writes).** `GET /api/output`; `POST /api/output {"output": "auto" | name}`; `POST /api/output/av {"enable": bool, "norm"?, "confirm": "av"}` (the confirm is the proof that the costs were read). Shapes are in the PR.

Cost / rules out: one screen per node still (no second output at once, no mirroring); the AV mode follows the TV standard, so there is no choice of 480i or 576i beyond NTSC against PAL; with AV on, the kernel always reports the composite output as connected, so it counts as a screen for the late-screen watcher (D95, #201), which is the same notion pvj-render uses: a node (a Pi 3 and older, where HDMI stays on) started with the HDMI projector off stays on AV until it is restarted. That is how it is, not a change made here; nothing of this has run on a node.
