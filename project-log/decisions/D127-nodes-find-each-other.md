## D127. Nodes announce themselves by mDNS through a static avahi file, and list each other with a one-shot question (2026-11-07)

Step 2a of the fleet plan (`design/fleet-and-devices_2026-11-07.md`, approved by the owner). It does not change pairing (D7, D80): each node still pairs its own devices, and a listed node is opened and paired like any other. Presence (D126) is untouched. Numbered D127 because D126 is taken by the presence branch.

**Announcing.** A node says `_nxlx._tcp` on its HTTPS port (the plain panel port while no certificate is loaded) with TXT records `txtvers=1`, `id`, `name` (the host name, which the pin screen and Health already show), `tier` (`lean`, `standard`, `full`, `unknown`, from `hardware.tier`), `version` (`pvj.__version__`) and `https` (1 or 0). It is a static avahi service file, `/etc/avahi/services/nxlx-mastercontrol.service`, not a long-running announcer: avahi-daemon (already on Raspberry Pi OS, and already announcing the host name) serves it and watches the folder, so nothing runs between changes. The panel's account cannot write `/etc`, so the root helper `pvj-sysd` gets two commands, `fleet_announce` and `fleet_withdraw`. It checks every field against a fixed pattern, renders the file from a fixed template, writes it by rename at mode 0644 (the unit's umask would make it unreadable for avahi's own account), leaves it alone when nothing changed, runs nothing, and answers whether avahi is missing, stopped or running. The panel sends a record at start, then only when the name, version, port, https state or the switch changed (a check every 15 s that compares in memory), and again each minute while it is on (the helper skips a file that is right, rewrites one that was deleted, and says whether avahi is missing, stopped or running).

**The node id.** 32 hex digits from the system's random source, made on first use and kept in `node-id` in the state folder (`/var/lib/pvj`, beside `settings.json`), mode 0644. It survives restarts, renames and updates. It is not made at image build, so cards imaged from one master get their own at first start. A node on the read-only root cannot keep it and has a new id at each start (it says so in its log). The id is announced to the whole network, so it is an identifier, never a credential. A card cloned after its first boot would share an id with its twin; the list then shows two rows with one id at two addresses, and the fix is to delete `node-id` on one.

**Listing.** `pvj/fleet.py` sends one multicast DNS question for `_nxlx._tcp.local` from an ordinary UDP port, one socket per address of the node, twice in 1.2 s, and reads the unicast answers (a "legacy unicast" question: avahi answers it to the sender directly, so the panel never binds port 5353 or joins the multicast group, and cannot disturb avahi). If a node's service or text records were not in its answer, one more question per such node asks for them by name. Chosen over `avahi-browse -rpt` because avahi-utils is not on a minimal Raspberry Pi OS and an install must not add packages (`tests/real_install_test.sh` asserts a plain install leaves avahi alone), and over D-Bus because Python has no D-Bus client in the standard library. The cost is about 150 lines that read untrusted packets; they are bounded (packet 9000 bytes, 200 records, 10 pointer jumps and only backwards, names 255 bytes, 64 rows), every field is checked and cut, and an answer from an address that is not private, link-local or loopback is ignored. The scan runs in its own thread only when someone asks, at most every 10 s; the request gets what is cached, and only the very first request waits (at most 2.5 s). A node missed by one scan stays 35 s. The node's own id is dropped from the list. No scan runs when nobody asks, and the announcer is a dictionary compare every 15 s: nothing a Pi 3B notices.

**The API.** `GET /api/nodes` is Operator and up (not a Guest, not a controller, not a support login). Each row: `id, name, address, port, tier, version, https, seen_seconds_ago`; with the node's own `self`, the state of its announcement (`announcing`, `off`, `no-avahi`, `avahi-stopped`, `no-helper`, `error`) with a fixed sentence, `scanning` and `error`. No path, token or setting is in it; the system's own error text goes to the log only. The list comes from strangers on the network: it is a hint for where to knock, and opening a node still needs that node's pairing.

**The off switch.** `POST /api/nodes/discovery {"on": bool}`, the Owner's (its place in Setup comes with the node switcher, 2b). Off removes the service file and sends no questions: one switch for both directions, because a venue that objects to the announcement objects to the multicast questions too. Kept in `settings.json` as `fleet.discovery` (read with defaults, no schema change; in `BOX_OWN`, so an import never carries it). The default is on: the node's name and model already go out in avahi's host announcement, and finding other nodes is the point of the feature. A damaged value reads as off.

**The sandbox.** `pvj-web` needs no change: UDP over IPv4 is allowed (`RestrictAddressFamilies` has `AF_INET`) and the unit has no `IPAddressAllow`. `pvj-sysd` gets one line, `ReadWritePaths=/run/pvj-sysd -/etc/avahi/services` (the `-` makes it harmless where avahi is not installed). That is the one change to a root helper's write rights; the installer writes the unit at the next install or update and the owner approves it by merging. No firewall change: the node has none of its own except the support tunnel's table on `wg-pvj`. A venue's firewall must pass UDP 5353 multicast between the nodes and their unicast answers, and Wi-Fi with client isolation will not.

**Not verified without hardware.** That avahi serves the file as written, answers our question with the records in the same packet, and that two nodes see each other (device rows in `tools/DEVICE-TESTING.md`, section "Nodes find each other"). The packets in the tests are built by hand from the format.

Rules out: a long-running announcer in Python; packages added by an install; any trust in a listed node's claims (signed enrollment is step 2c); announcing through the support tunnel.
