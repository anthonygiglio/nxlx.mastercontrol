## Addendum to D147 (2026-11-22): a QR sticker for people with no login (J-179, slice B)

The owner's decision on J-179, slice B: a sticker in the room carries a QR code; a tester scans it with a phone on the venue Wi-Fi and gets the node's own feedback page with **no login and no pairing**: the three faces, optional words (1000 characters), Send, "Thanks, sent". It is the same store (`feedback.json`), with the same context the node adds (its name and id, the time, what plays on each source), and the sender's role kept as **visitor**, a word of its own (a Guest is someone paired; a visitor is not).

What is public, and only that: `GET /feedback` (and `/feedback.html`), one static page with the Owner's switch written into it (`data-open`), no cookie set and nothing else read from the node; `/feedback.js`, `/app.css` and `/theme.css`, which the panel already serves to anyone; and `POST /api/feedback/visitor`. The POST is answered by the route table with no login (`None`), so everything else about a request still applies: the host check, the CSRF header `X-MCTL-Request: 1` (a cross-site page cannot send it without a preflight the node never answers) and, when the browser sends an Origin, the same origin; a JSON content type (415 otherwise); a body of at most **4096 bytes** (413; the panel's own limit is 64 KB); an object with only `face` and `text` (400 otherwise; a visitor names no screen). A request that carries a device (a paired device, a controller, a support session) is answered 403 and pointed to the Feedback button: the page sends with `credentials: "omit"`, and the box's own callers cannot send a visitor note (the route is in `policy.LEGACY_LIVE` only because it needs no login, with that reason beside it). Through remote support it is refused as a note from someone in the room (`support.REMOTE_DENY`).

**The Owner's switch**, "Let people without a login send feedback (QR sticker)" (`POST /api/feedback/open {"on": bool}`, the Owner's, never through support; kept as `feedback_visitors` in the settings, which is in `boxcare.NEVER`, so an import file cannot switch it on and it is not in an export). **Off by default.** While it is off the page says so in plain words and the POST answers 403 before anything is read. `GET /api/feedback` tells the Owner's panel which way it is (`visitors`).

**Limits for the unauthenticated route.** Each address: one note in 10 seconds and 10 in an hour (429 with `retry_after`), by the connection's own address (never a header), an IPv6 address by its /64 and a mapped IPv4 address as the IPv4 one. The table is bounded in memory: an address with nothing in the last hour is dropped at every call and the table holds 512 addresses at most, the one asked longest ago going first, so a sender that makes up addresses cannot grow it. Visitors have **their own budget** of the node-wide caps of D147: half of each window (15 notes in 10 minutes, 100 a day), counted apart, so visitors can never use up the share of signed-in devices, which keeps the whole 30 and 200; and visitor notes hold **at most half of the kept list** (250 of 500): a visitor note may only ever displace a visitor note: past that half, or with the list full, the oldest visitor note goes, and when the list is full and holds no visitor note the new one is refused (429, "The list of feedback is full just now") and stores nothing. A signed-in note displaces the oldest note of any kind as before, so staff always keep at least half (the independent review showed three addresses could otherwise fill the node's window and lock the staff out). A send the node refused for its own share or could not write gives the sender his turn back. **No address is stored**: the limiter is memory only and the note has no address field; a restart forgets it. The access log lines of the page (`GET /feedback`, `/feedback.html`), of the send (`POST /api/feedback/visitor`) and of the files the page loads name no address either (`-` in its place, `server.log_message`): `/feedback.js`, the type files in `/fonts/` and the shared files the page asks for with `?from=feedback` (`/theme.css`, `/app.css`, `/favicon.ico`; a Referer could not tell, since the page is served with no-referrer). The panel's own page and files, and every other request, are logged as before. Both are refused through the support tunnel.

**The sticker.** The Owner's card under Setup > Health ("Feedback from the room") has **Print the QR sticker**: `GET /api/feedback/sticker` (the Owner's) returns `{"url", "svg", "on"}`, and the panel prints a sheet with "Tell us how the night is going", a large QR code and "Scan to send feedback", through the print path the access sheet already uses. The address is the one the Owner opened the panel by, and only if it is the node's own: its host name or that name with `.local`, a name its certificate covers or one in `NXLX_ALLOWED_HOSTS`, or an address of one of its interfaces now or one the Owner listed in `NXLX_ALLOWED_HOSTS` (an address only the certificate names may be stale and is not taken); localhost in any form, `0.0.0.0`, `::`, a mapped loopback address and every other name are refused with "Open the panel by the node's own address to print the sticker". It is `https://` when the panel was opened over it or the node's certificate names that host (`HttpsBox.trusted_origin`), else `http://`; it ends in `/feedback`. The code holds that address and nothing else: no token, no join code, nothing that pairs. It is made on the node by `mctl/qr.py`, the project's own encoder (standard library only, Apache-2.0, byte mode, level M, versions 1 to 10); no library, no CDN, no outside service, so nothing is added to the third-party list.

Cost / rules out: anyone on the network who can reach the node and sees the sticker can send, while the switch is on (that is the point; the limits keep a flood small and the Owner reads and can switch it off); no reply to the sender; the page cannot tell a real guest from someone who is not in the room (a note from a phone off the venue's network is as possible as the node being reachable from there); a node reached only over https with an untrusted certificate shows a browser warning on the sticker's page, which the https address of a node with its own certificate (D79, D139) avoids. This release keeps a well-formed note of a role it does not know (up to 8 KB) in the file as it was, never shows it, and writes it back untouched, so going back to it from a later release loses nothing. **A rollback to a release before this change still loses the visitor notes**: that release reads the role as damaged, leaves the notes out and its first write drops them; this cannot be fixed backwards (export the notes from the Owner's card first). Not tried in a browser or on a phone yet.
