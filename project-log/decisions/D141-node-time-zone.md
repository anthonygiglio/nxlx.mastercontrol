## D141. A node's time zone is set by an Owner, once confirmed it never changes by itself (2026-11-15)

The schedule fires by the node's local time, so the zone is part of what a show depends on. Rules: (1) only an Owner sets it, from the panel, and never through remote support (the route is in support.REMOTE_DENY); a Guest, an Operator, a controller and the schedule cannot. (2) The only automatic change is the first Owner pairing on a node that is new in every way (still on UTC, no zone confirmed, no other Owner device, no schedule entry): it takes the browser's zone and says so, and says so too if it could not set it or save it. (3) After an Owner has set or kept a zone (`settings["timezone"]["confirmed"]`; "Not now" on the bar keeps it), nothing changes it without an Owner's tap; a different browser zone is only offered ("Use Y?"). (4) The name that reaches `timedatectl set-timezone` is checked in the root helper (safe pattern, a real TZif file under /usr/share/zoneinfo, never `localtime`, `posixrules` or `Factory`, and named by `timedatectl list-timezones`: no list, no change; the name follows `--`) and the zone is read back. Why: a wrong zone moves every entry by hours with nobody in the room to notice, and a phone travelling or on a VPN must not move a node's schedule. Cost / rules out: a node that is first paired from a phone in the wrong zone is set wrong until an Owner corrects it (the Schedule page shows the zone and warns when it differs from the device in hand); a node that is not on UTC, or already has Owners or schedule entries, is left alone and only offered the change; a zone change makes the local clock jump, so entries in repeated hours can fire again and entries in skipped hours are missed.
