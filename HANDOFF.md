# Hand-off notes

For a new person or a new claude session picking this up cold. Read this, then the [project log](project-log/README.md) (decisions, lessons, journal), [README.md](README.md), [ROADMAP.md](ROADMAP.md) and [pvj/README.md](pvj/README.md).

This page is meant to be read once, top to bottom. "State and what is next" is the only part that is about a date; everything after it is by topic.

## What changes when you update: render nodes (D94, #143)

**Nothing changes on the screen or the network until the Owner adds a render node.** A new row, Setup > Render nodes, is there for Operators and Owners; with no node in it the box sends nothing anywhere. The pad editor has a fourth kind, Render cue. A settings file exported from this version has a `render` section, which an older release refuses to import ("sections this version does not know"), as it did for `ndi`; the settings file on the box itself loads on an older release, which keeps the key and sees a render pad as empty. The first profile is Max/Jitter with the companion patch `tools/max/nxlx-render-node.maxpat` (untested in Max; jit.ndi is the owner's to install). Nothing was run with a real render node or on a Pi: `tools/DEVICE-TESTING.md` RN1 to RN8. The open item "a stream whose source drops leaves the player idle" is closed for a render node's picture only (D94): a stream and an NDI source played by hand still behave as before.

## What changes when you update: Automatic picture detail for shaders (D93, #142)

**A Pi 4 where no shader height was ever saved draws each shader at the most lines it held at the box's output**: at 1920 x 1080 (the box's own mode since D90), 720 lines for 41 of the 47 and 540 for nxlx-aurora, nxlx-drift, nxlx-lantern, nxlx-nebula, isf-ridgelines and isf-simplex-noise. A box that saved a height before (the test box has 720 from the first version) keeps it, and the Shaders page and Room offer **Use Automatic**; a height chosen by hand always wins. A computed Ambient or Show leaves out a shader that did not hold at the height it will be drawn at: under Automatic at 1080p drift and nebula are in (at 540); with 720 kept, they, aurora and lantern are out. Above 1920 x 1080 the 1440p numbers count. A heavy mark belongs to the output it was made at. An older release reads `height` (540 under Automatic) and ignores `height_auto`. Not judged by anyone's eye: whether 720 looks better than 540 on the projector (DEVICE-TESTING A1 to A5).

**What the owner may want to change (not his confirmed choices):**
- **Automatic as the default for shaders.** The coordinator's reading of his words "improving shader variety and detail" and "the most economic output for performance and clarity and detail" (D90). The 540 it replaces was an agent's choice of 2026-10-04, not his. One setting either way: Picture detail on the Shaders page.
- **Tide and bloom at 720** (GPU 87 to 90 percent busy). D58 stepped two effects down to 540 for room on his say; nothing like that was done here.

## What changes when you update: the screen's mode (D90, #139)

**Every box chooses its screen's mode at its next update, and the player restarts once to do it.** Until now the player took the screen's own preferred mode, whatever it was. Now Automatic takes the screen's own mode only if it is at most 1920 x 1200 at about 60 Hz, else the largest mode up to that size, of the screen's own shape, at 60 (50 only if there is no 60). **On the owner's 1440p monitor that is 1920 x 1080 at 60 Hz instead of 2560 x 1440 at 75**; an Epson X27 or X39 gets its own 1024 x 768 at 60; a 1080p projector or TV stays at 1080p60. Every number measured on the Pi so far (D28, D51, D56, D58, the crossfade) was at 2560 x 1440 at 75 Hz and will read better now; they were not measured again. To choose another: Setup > Screen output (Owner only), which tries it and goes back by itself after 15 seconds unless Keep is pressed (never from a remote support session). The test pattern is at the screen's own size, with a grid, a red border one pixel wide and the mode in words. A mapping made at another shape (16:9 on the monitor, used on a 4:3 projector) is squeezed to fit and the mapping page says so. The player's service asks mpv for the screen's list before each start (`mpv --drm-mode=help`), passes the screen's card and connector with the mode (`--drm-device=/dev/dri/cardN --drm-connector=NAME`, the card from /sys: on a Pi 4 that is card1; D91, after #139 passed mpv's "0.HDMI-A-1", which mpv took as a name that matched nothing, so on the test Pi Automatic fell back to the monitor's own mode), and writes what it chose to `/run/pvj/player/screen.json`; the panel writes the wish to `/var/lib/pvj/screen-mode.json`. With no screen connected the box does what it did before. Forcing a mode at boot (`video=...D`) is not built and is the owner's choice (D90 says the trade-off). **Nothing of it has run on the Pi or in front of a screen**: `tools/DEVICE-TESTING.md`, S1 to S14, before the next show.

## What changes when you update: Owner, Operator, Guest (D80, #120)

**Guest controls are open by default, so every guest device, guest link and guest code that exists on a box gains them at the update**: scenes, pads and clips on the box, next, previous, stop, blackout, ambience, a shader or its presets, effects on and off, projectors on, input, and off after a second request. **The one way to lock at once: Room or Setup > People and codes, "Lock guest controls for a show"** (`POST /api/guests {"locked": true}`, Operator or Owner; kept in the settings key `guest_controls`, which an older release ignores).

Every `live` device (Presenter) is an Operator after the update and gains the daily work that was the owner's (clips, pads, schedule, autostart, sound, mapper, presets and sets, room set-up, guest links, removing guests, the lock). The exceptions keep exactly what a presenter had (`policy.LEGACY_LIVE`, written out by hand, compared with master's route table when it was written): MIDI, OSC, DMX, room scenes and the schedule, and a support session below `full`. **Phones that joined as presenters from a controller's code are now Guests** (`Auth.role_of`; the record is not rewritten); an owner can invite them as Operators. A controller-drawn "join" code pairs a Guest unless the Owner sets "A controller's join code pairs" to Operator. An Operator also edits the MIDI layout (never a control that shows an access code) and removes other Operators (never himself or an Owner). A scene can be marked "Not for guests". The owner's answers of 2026-10-10 are at the end of D80, in his words. The whole policy is D80 in `project-log/DECISIONS.md`, one row per route; the code is `pvj/policy.py` and `Api.gate`; `tests/test_roles.py` fails for a route without a row. **Nothing of it has run on the box.** The panel's part is carried into the four areas of D72 (master with #121, merged in on 2026-10-10): the lock is a card on Room > Guests and on Setup > People and codes (`guestLockCard`); a guest's own card stands under the scenes on Room > Scenes, or on Play > Pads on a box without the Room (`guestNote`, `guestCard`), and holds only what has no other place; the scene buttons, the pads, the Library's Play, the Vibes button and the strip's Stop, Blackout, Previous and Next are a guest's own while guest controls are open (sent with `guestSend`), with no second copy; the Operator has Setup > Room (the set-up), Schedule, At power-up and MIDI controller, and Mapping as a page. `tests/ui/shell.js` lists the screens of each role (`MENUS`; the key `presenter` is the Operator). **Seen in headless Edge on the Mac at 1366 px and in frames of 390 and 320 px; not in a phone, not in Safari, not on the box.**

## What this is

**nxlx.mastercontrol** by NXLX.Systems (Anthony Giglio, video artist; "NXLX" is his VJ name, now the whole practice). It is a fork of PocketVJ CP v3 by Marc-André Gasser (magdesign), whose upstream is unmaintained and unreachable. Goal: run on Raspberry Pi 3B/4/5, x86 mini PCs and old computers, on Pi OS Bookworm/Trixie and Debian/Ubuntu, and be rugged at gigs (direct Ethernet on a private network preferred).

The repository was renamed from `PocketVJ-CP-v3` to `nxlx.mastercontrol`.

## Decisions already made (do not reopen without a reason)

- Python 3, standard library only, replaces PHP. The legacy PHP and docs stay in the tree until feature parity.
- New code is Apache-2.0 (SPDX headers, `REUSE.toml`). Legacy code stays under the upstream `LICENSE.md`. `LICENSE.md` and `AUTHORS.md` are never edited. Copyright holder in headers: "NXLX.Systems and contributors".
- One long-lived mpv controlled over JSON IPC, supervised by systemd (`pvj-player.service`). The panel (`pvj-web.service`) is unprivileged; anything needing root goes through small helpers (`pvj-netd`, `pvj-sysd`, `pvj-supportd`) that answer only pvj-web over a socket.
- Token auth (PIN pairing, roles view/live/full), CSRF header, strict CSP. Signed updates with rollback.
- NDI and AES67/Dante are separate optional modules. AES67/Dante is not built. NDI receive (picture, and since 2026-10-08 its sound, which nobody has heard yet; D62, `pvj/NDI.md`) is built on the branch `ndi-input`, a draft in pull request #94 (see "State and what is next"). It is **opt-in per box**: a plain install, an update and the image put nothing of NDI on a box (no helper, no account, no avahi added); `sudo pvj-ndi-runtime install <the NDI SDK>` at the box sets it up (NDI's own runtime, which the owner supplies, and the helper), and `remove` takes it off. The module is off by default and needs no settings schema change (the key `ndi` is read with defaults). The owner accepted the NDI SDK licence himself for testing on his own test Pi only (2026-10-08); the venue box stays his question to settle with NDI. ST 2110 is not planned natively; it comes in through a gateway (D30). SRT/RTSP/RTMP streams, DMX, MIDI, the schedule and autostart are built, off by default.
- Naming: the `pvj` package, `pvj-*` services and commands and install paths keep their names.
- Style: no em dashes in written text (commas, semicolons, new sentences). Default document font Inter.

**What it is (#81, D55; measured in #84, D56).** An effect is an ISF filter put on over whatever plays, one at a time, with an Amount mix, live values, presets, Previous and Next and MIDI actions; a strip on Live and a card on Mix. 37 filters come with it: twelve of our own and 25 from ISF-Files. **On 2026-10-05 all 37 ran on the test Pi 4** through the engine, over the owner's clips, judged from snapshots and the player's counters (nobody watched the monitor): every one was taken by V3D and drew the right picture, colours and geometry right, also over the hardware decoder's `drm_prime` pictures; Blackout stays black under an invert. **Over a 720p clip every filter holds 30 frames a second; over a 1080p clip every one drops frames at full size (0.2 to 11 a second) and none does with Half resolution.** So 36 are "medium", isf-duotone is "light", none is "heavy". ## An effect over a generator shader (D74, pull request #113, not merged)

The owner asked on 2026-10-09 for "effects over shaders". **Built, never run on hardware.** Read D74 and "An effect over a generator shader" in `pvj/SHADERS.md` before touching it; the short form:

- **How.** Nothing new in the player's pipeline. A generator and an effect both hook NATIVE, and the order of the player's shader list (source, effect, mapping) makes the effect filter what the generator drew. A spike in CI showed that before any code changed; the old rule (a generator takes the effect off, none goes on over one) was a choice, and it is gone from `Player.play_source`, `Player.put_effect` and `Effects.available`.
- **The effect stays** when a generator is chosen, when Vibes starts and at every Vibes step, as it stays when a clip changes; Vibes' dip takes it along. **Stop takes it off**; so does stopping Vibes, which clears the screen (`last` says "the shader under it was taken off the screen").
- **Sizes.** The player speaks of the carrier (64 x 36 in CI); the effect meets the generator's drawing. `Effects.picture` reads the size from `shaders.playing` when a carrier plays. Effect detail caps the effect only below the generator's lines (Picture detail), and then softens the shader.
- **Refusals.** A refused pair leaves the generator on, takes the effect off, says so, and is remembered in `Effects._bad` under a key that says "over a generator" (`Effects._key`), so it is not sent to the GPU twice. `shaders.about` keeps each engine from taking the other's refusal in the player's one log for its own: both listen at once now, under different locks.
- **The guard.** With an effect on, `Vibes._guard` judges nothing (no heavy mark, no skip, no end of the rotation); the effect's own guard speaks in its card. **The floor:** a pair that drops 2 frames a second for 20 seconds loses its effect (`Effects._floor`, `PairGuard`; the shader stays, nothing is marked, nothing is put back). Both numbers are guesses, `PAIR_LIMIT` and `PAIR_SECONDS` at the top of `pvj/effects.py`. The generators' guard keeps its window by the shader and the effect over it (`LiveEngine.watch`), so it starts over when an effect leaves: **anything new that ends the suspension must leave that in place**, or the shader is marked from the pair's frames (found by a probe, not by the tests of the day).
- **The queue of wishes** (a controller's Next, Previous, On, a preset): a step is a move the worker resolves when it runs, steps that wait add up, and a wish carries `Player.clears`, which only a clearing of the screen moves. A Stop in between drops the wish and says so; a clip, a generator or a Vibes step does not. Only Off and an effect put on by hand move the engine's generation. **If you add a way to ask for an effect, make it through `Effects._wish`, never from a reading of what is on taken at the request** (`QueueTest` in `tests/test_effects.py` has the five windows).
- **No lock was added, nothing is stored**, no settings schema change.
- **First on the Pi:** E1 to E16 in `tools/DEVICE-TESTING.md`. Above all the frame time and the dropped frames of a few pairs at 540 and 720 lines, and whether a shader chosen under an effect ever flashes plain.
- **For the owner to decide:** whether a start of ambience by the SCHEDULE should take an effect off first. It is the one unattended start that can inherit a performer's look (a person starts it from the Room screen; autostart follows a restart, which has no effect on). Nothing was built for it: the floor takes a heavy effect off after twenty seconds whoever started Vibes, and a light one stays. Whether a start of ambience by staff or by the clock should take an effect off first is his call (D74, "Cost").
- **The order of merging: #111, then #114 (shader-pads, D73), then this one.** `shader-pads` is merged into this branch and the two features are tested together (`tests/test_pads_and_effects.py`; D74, "With the shaders on pads merged in"). `area-desks` (#112) removed the effect strip from Live and still asserts the old sentence "A generator shader has the screen" in `tests/ui/panel.test.js`; this branch's part of that test uses the strip's ids (`#livefxname`, `#livefxoff`, `#livefxnext`, `#livefxmore`) for the pair and for a shader pad under an effect. ## Crossfade and transitions (D71)

The owner asked on 2026-10-08 for crossfade and other transitions first. **Built: Crossfade, four wipes and four slides as Mix transitions.** On 2026-10-09 it ran on the test Pi 4 at 2560 x 1440 with nobody at the monitor (a script and timings over SSH; the journal of that afternoon has it all): the first build gave up at the first play (its still took 1.7 s, of which 0.98 s was the unpacking, fixed in cfcacc5); with the fix a crossfade, a wipe from left and a slide up ran with no "given up" line, a play answered after 0.93 to 1.09 s (about a second of standing still before the blend), a 5 s wipe ten times in a row left the player running, Blackout during a crossfade answered in 0.08 to 0.09 s and Stop in 0.11 to 0.14 s, and nothing was left in `/run/pvj/web`. **Nobody has seen it**: whether a blend is smooth, a wipe's edge even, anything lit under Blackout, and how a second of standing still looks, are open. Read D71 before touching it; the short form:

- **How.** At a play the outgoing clip is frozen, the player saves the window as a PNG with plain rows (`Player.still`), the panel turns it into BGRA and lays it over everything as overlay 63 (`Player.overlay`), the new clip loads under it, and from its first frame a thread sends the still again twenty times a second with less alpha (`pvj/transitions.py`, `Transitions.hold`, `run`, `end`). The outgoing picture stands still.
- **Why not a shader**, which the earlier note in `pvj/SHADERS.md` proposed: three findings of the spike (branch `transitions-spike`, CI only). mpv's `frame` number never starts again and stands still over a picture or a frozen clip, so a shader has no clock to start; every kind of screenshot of the video holds the mapping's shader and the brightness, so a still fed in before them is warped and dimmed twice; and a shader draws only where the new clip's picture is.
- **What follows from the overlay.** The player's brightness does not reach it, so Blackout, a fade, an opacity change, Stop, any other play, a generator and a mapping change call `Transitions.end()` (in `pvj/api.py` through `_settle()`). If you add a way to play or to darken the picture, it must call it too.
- **Rollback.** The settings keep `mix.transition: "dip"` with `mix.style: "crossfade"` beside it; `transitions.named()` and `stored()` are the only readers and writers. An older release reads a dip. No schema change.

## Remote support: what a helper may do (D84, pull request #125, a draft; security review before any merge)

- **The principle:** a helper in a remote session with the Owner's role may do anything that ends when the session ends, and nothing that outlives it or locks the owner out. A remote Owner session can already upload a software update signed by a key this box trusts (not any code: `pvj-update` checks `/etc/pvj/allowed_signers`), so the refusals are about persistence and lock-out, not about limiting a trusted helper in the moment.
- **Where it lives:** `pvj/support.py`: `REMOTE_DENY` (route to reason), `REMOTE_DENY_PREFIX_WHY`, `REMOTE_OWNER_OPENED` (the record of what D84 opened), `SupportManager.note` (what a session did, into its entry of `support_log`: `always` for an update, an import and a removed device, which nothing else can displace; `major` for the other opened routes' changes and for refusals, each a fixed text with what a request chose as a counted `detail`; and `did` for routine use by route), `refused` (what it was refused, a major line, written in `Api.gate` and by the handlers' own rules), `upload_line` and `key_renewed`. `Api._remote_owner` is the handlers' own check (a support login counts only through the tunnel of an open session, with the Owner's role). `boxcare.REMOTE_KEPT` and `REMOTE_SETS` (what an import leaves as the box has it for a helper). In the panel: `supportReach` (the two lists), `supportCard` (`#supportoldkey`, `#supportlastdid`, the list under Recent sessions), `SYS_STATE.support`.
- **Rules to keep:** a new route is in neither list, so a remote Owner session reaches it like the Owner: decide on purpose, and if it must be refused add it to `REMOTE_DENY` with its reason and to `REFUSED` in `tests/test_support_reach.py`. A new settings section needs a row in `boxcare.REMOTE_SETS` (a test fails without one) and, if its own route is refused to support, a place in `REMOTE_KEPT`. A handler that an opened route reaches calls `support.note` with what was done and never a value; every other POST of a support login is noted by its route in `Api.handle` (`support.used`), so a POST that changes nothing must be named in `support.NOT_A_CHANGE`, and a path the server answers itself must call `note`. A diagnostics file never holds the OSC state targets (D82), whoever asks.
- **Also held, in the handlers (decided 2026-10-11):** a support session adds no outside network to those OSC accepts from (`Api.remote_allow_refused`, on `POST /api/osc` and in an import) and never adds or changes a MIDI control that shows an access code (`Api.midi_map`, `set_midi`, `BoxCare._remote_parts`); it may remove either.
- **More rules to keep (the security review):** a new thing a session may do that the owner must see is noted as major, with a fixed text and anything a request chooses passed as `detail` (a test reads the source for this), or with `always=True` if it is as heavy as an update; a new refusal for a session calls `support.refused` outside any lock (`midi_map` wraps `_midi_map` for that); a session's import never removes one of the owner's copies of the settings (`BoxCare._backup`).
- **NDI for a session (D85 met D84):** `support.REMOTE_NO_MODULE_ON` (modules no session switches on, by route or by file), `/api/ndi/discovery` and the `ndi-discovery` switch refused whole, `POST /api/ndi` as Streams (the owner's rule, asked again on 2026-10-15 and kept), and `BoxCare._remote_parts` for what a file may not bring (a module switched on, an NDI address or discovery server that is not another device on the box's own networks, D88, `own_discovery`). D84 has the table.
- **Never run through a real tunnel or on a box.**

## Testing

- `python3 -m unittest discover -s tests` (about ten minutes on the Mac, nine in CI; needs mpv for the tests that play). One module: `python3 -m unittest tests.test_qr` (with the `tests.` in front, see the next point).
- **Temp files (D69).** A run of the tests works in a temp folder of its own, `<temp folder>/pvj-t-XXXXXX`, and removes it when it ends: at the end of the run, on Ctrl-C, and on `kill` (SIGTERM). `tests/tmpguard.py` does it, when the `tests` package is imported; `tests/test_000_tmp.py` is named to be loaded first so that the plain `discover` above imports it, and holds the tests that keep this true. A new test needs nothing: call `tempfile.mkdtemp()` and do not think about it. Three things to know:
  - `PVJ_KEEP_TMP=1` keeps the folder and prints its path at the end, to look at what a failing test left. A kept folder is removed by a later run after two days, once its process is gone.
  - A run that is killed outright (SIGKILL, CI's `timeout -s ABRT`, a crash) cannot clean up. The next run of the tests, from any checkout, removes such a folder once it is two hours old and its process is gone. A folder whose process is still there is left for fourteen days (a paused run and a process number given out again look the same). It only ever removes a real folder named `pvj-t-*`, owned by you, holding the marker file `.pvj-test-tmp` that the suite wrote.
  - The guard cannot see a folder made with `dir=` somewhere else (three tests use `dir="/tmp"` because a socket's path may be about 100 bytes long): such a line needs `self.addCleanup(shutil.rmtree, ...)` right after it, and a test checks that. And `python3 -m unittest discover -s tests -p test_qr.py` loads only that file, not the package, so it is not guarded: name the module as above.
  - The run's folder makes every path in it 13 bytes longer, and a socket's path may be 103 bytes on macOS (107 on Linux). The longest the tests make is `<run's folder>/tmpXXXXXXXX/run/player.sock`: 89 bytes with the Mac's own temp folder (49 bytes). If you set `TMPDIR` yourself, keep it under about 60 bytes on a Mac: an agent's scratch folder is about 100. `tests/test_000_tmp.py` then fails first and says so ("the temp folder ... is N bytes too long for the sockets the tests make"), where before a dozen socket tests failed with "AF_UNIX path too long" or a player that never answered.
- **Clearing what the old runs left, by hand.** Before D69 every run left folders named `tmp` and eight more characters directly in the temp folder. Other programs use that name too, so look before deleting and never remove `tmp*` blindly. On the Mac: `cd "$(getconf DARWIN_USER_TEMP_DIR)"`, then count them with `find . -maxdepth 1 -name 'tmp????????' -user "$(id -un)" -mmin +120 | wc -l`, look into a few (one of the tests' holds `run`, `video`, `web`, `settings.json`, or `s.json`, or `pvj`, `bin`, `install`), and when no test is running and nothing else of yours is using a temp folder, remove them with the same `find` and `-exec rm -rf {} +` in place of `| wc -l`. `-mmin +120` leaves alone anything changed in the last two hours. On Linux (and in WSL, where `/tmp` is on the distribution's own disk and may not be emptied at a start) the same with `/tmp` as the folder. Folders named `pvj-t-*` need nothing: the next run of the tests removes the old ones.
- Browser test: `node tests/ui/panel.test.js` (needs Playwright and Chromium). It includes the width sweep (D64, `tests/ui/sweep.js`), which adds a little over a minute, and since D65 the shell's checks (`tests/ui/shell.js`) and the control inventory (`tests/ui/inventory.js` against `tests/ui/fixtures/controls-before.json`, on a second harness started with `PVJ_HARNESS_NO_PLAYER=1`; about three minutes). A step moves about with `go(page, 'area/screen')` from `tests/ui/signal-pages.js`. If the inventory fails, it names each control that is gone and where it was; a control moved on purpose goes into `MOVED` in `shell.js` with the reason.
- On a real board: **Option C** in [tools/DEVICE-TESTING.md](tools/DEVICE-TESTING.md) (flash the CI image, then the numbered checklist). `tools/device-test.sh` and the manual "Device test" workflow are Options A and B. `tools/artnet-send.py` sends Art-Net to test DMX from a laptop.
- Static checks of the systemd units run everywhere (`tests/test_units.py`): the ordering-cycle bug that stopped the player at boot could not be seen in a container.
- Risky features got an independent read-only review; every finding was fixed with a test that reproduces it. Keep doing that for anything touching root, the network, uploads or auth, and have the fixes read again when they change threads or locks.

## Working agreements

- Open a PR per finished branch. When it is green and ready, add a short comment and merge. Do not rewrite git history.
- Ask before destructive or outward actions (deleting remote branches, moving the repository, overwriting a card). Read the check list for failures before merging: zero failures, not just "nothing pending".
- Anything that reads devices, takes network input or handles filenames from removable media gets an independent read-only review before merging, and every finding gets a test.
- Report outcomes faithfully. Do not claim something works on hardware it has not run on.

## Lessons and limits

- The panel browser test once failed only in CI. The cause was real: the Network form kept typed values only through input events and lost one on a redraw; it now reads the page before every rebuild. When a UI test fails only in CI, add a diagnostic that prints the state at failure and rerun until it shows; do not merge over a red check and do not loosen the assertion.
- The first boot on real hardware found two service bugs no container test could (a systemd ordering cycle that dropped the player's start job, and mpv's owner-only control socket) and four Pi-specific defaults (cheap scaling, HDMI sound, USB media, the cost of a live preview). Read `project-log/LESSONS.md` before trusting a green CI run for anything that touches devices.
- A/B measure performance claims on the real device (A, B, A, B, A) and trust the person watching over a counter.
- A licence check belongs before the build: the NDI SDK's licence is only inside its installer, and its exclusions decide whether the feature may ship on the box at all.
- A claude session in the cloud could not push tags or delete branches (HTTP 403 from the proxy). Do those from a normal clone or on github.com.
- The session's GitHub scope is fixed to the repo name it started with; after a rename, start new sessions on the new name.
- A claude cloud session cannot reach devices on your LAN. Use the self-hosted runner in DEVICE-TESTING.md or run the test script by hand.
